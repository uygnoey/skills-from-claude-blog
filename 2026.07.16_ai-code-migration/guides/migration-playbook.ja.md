# プレイブック: エージェントで大規模マイグレーションを進める

すべての diff を読むことが不可能になった時点から、マイグレーションは「大規模」になる。その線を
越えると仕事の性質が変わる。コードを書く作業ではなく、コードを生み出すループを設計し、そのループが
全体として何を produce しているかを見張る作業になる。

元記事はこの原則をはっきり述べている。**直すのはコードではなく、そのコードを生み出したプロセス
である。** 以下のすべてはここから導かれる。

## なぜ仕事の形が変わるのか

大規模な書き直しの典型的な失敗は「終わらないこと」だ。少人数が手作業で移植している間に元のコードは
動き続け、移植版は永久に遅れをとる。エージェントのファンアウトはこのスループット上限を取り払う。
記事が報告する Bun の移植は 2 週間足らずで約 100 万行の Rust を生み出した。しかし代わりに別の問題が
生まれる。1,000 個のファイルをエージェントが翻訳するとき、誤った前提ひとつはバグひとつではない。
ひとつのバグが 1,000 個に複製された状態であり、その一つひとつは単体で見ればどれも妥当に見える。

だからレバレッジの位置が移る。この規模ではファイル単位の丁寧な作業はほとんど何も買ってくれない。
すべてを買ってくれるのは、正しいルールブック、中断に耐えるキュー、そして意見ではない審判である。

## 前提条件: 審判をつくる

最初のファイルを翻訳する前に、元のコードと移植版の両方に対して実行でき、両方に対して同じ答え方を
するものが必要になる。既存のテストを二つに分類する。公開表面を通して表現できるものと、内部実装に
縛られているもの。前者は両側に対して走るアサーションに書き換え、後者は捨てる。それが主張していた
対象はマイグレーション後には存在しないからだ。

そのうえで審判そのものを両方向で検証する。元のコードに対して実行して通ること。わざと壊したコードに
対して実行して落ちること。片方向しか確認していない審判は、ボードは緑なのに製品は壊れている、という
終わり方をする定番の経路だ。

使えるテストスイートがないなら、代わりに実際のエンドツーエンドのシナリオでパリティ・ハーネスを
つくる。記事の Python から TypeScript への移植は 7 個を使い、いかなる挙動の差も「説明すべきもの」
ではなく「直すべきバグ」として扱った。システムを本当に動かす 7 個のシナリオは、移植版がコンパイル
できることしか証明しない浅いテスト数百個に勝る。

## フェーズ 1: 決めて、書き出す

三つの文書を、決まった順序でつくる。

**ルールブック**は翻訳ポリシーである。実装者が人間に尋ねずにファイルを移植するために必要なすべて。
その形は、先に下さねばならない決定ひとつで決まる。同じアーキテクチャを新しい言語に移すのか、それとも
再設計なのか。構造を保つ移植なら、ルールブックはほぼ対応表になる。型、イディオム、エラー処理、
並行性、依存の置き換え。再設計なら、参照すべき対応表そのものが存在しないので、設計文書に近いものに
なる。この決定を飛ばしたチームは、よりによって最も重要な箇所で曖昧なルールブックを書くことになる。

**依存マップ**はスケジュールである。あるファイルは、それが依存するすべてが終わったときに翻訳できる。
つまりマップが、何を並列に走らせられるかを決める。エコシステムがモジュールグラフを提供するなら、
それを読む。提供しないなら——レガシーコード、C/C++、Python——Claude に依存関係を発見させ、その結果を
散文ではなくキューが消費できる機械可読データとして記録する。循環は明示的に記録する。放っておいても
解けない。

**ギャップインベントリ**は最後であり、この順序は好みの問題ではない。ギャップとはルールブックの
デフォルトが届かない場所のことであり、したがってデフォルトが存在して初めて定義できる。先に書けば、
決定の一覧ではなく不安の一覧になる。

## フェーズ 2: 壊しにいく

小さく代表性のあるサンプルに対してミニ・マイグレーションを走らせる。記事はこれを試験航海と呼ぶ。
役割は三つ。ルールブックだけを見て作業する翻訳者、別コンテキストでシニアエンジニアのように結果を
評価するレビュアー、diff を読んでルールブックに欠けていた規則を提案するルール抽出役。

そして、翻訳されたファイルを削除する。

人が抵抗するのはこの指示であり、そして重要なのもこの指示だ。このフェーズの成果物は進捗ではなく、
より良いルールブックである。ファイルを残せば、そこに埋め込まれた判断を維持しようとする圧力が生じる。
このフェーズはまさにその圧力を取り除くために存在している。サンプル実行から新しい規則がほとんど出なく
なるまで繰り返す。その収束が、規模を上げてよいという合図だ。

フェーズ 1 と 2 が人間の時間を投じる場所である。それ以降は、ほとんどがキューの消化になる。

## フェーズ 3 以降: 同じ形をした四つのループ

翻訳、コンパイル、実行、挙動の一致。違うのはキューに何が流れ込むかだけだ。依存マップ上のファイル、
次にビルドエラー、次にクラッシュ、次に元のコードとの差分。ToDo リストはひとりでに書かれる。
コンパイラのエラーが次の作業項目であり、翻訳者が残した `// TODO(port)` マーカーが次の作業項目である。

これらのループを支える設計上の選択が三つある。

**「完了」は機械的でなければならない。** 記事の定式化は、完了とは出力ファイルがディスク上に存在する
ことを意味する、というものだ。長いマイグレーションは必ず中断する。レート制限、再起動、捨てると
決めたバッチ。完了判定に判断を要するキューは再開できない。キューの状態はエージェントのコンテキスト
ではなくディスクに置き、バッチの再生成を安価な日常操作にしておく。規則が変わるたびにやることになる
からだ。

**不確かさは印をつける。決して推測しない。** 確信のない実装者は `// TODO(port): <理由>` を残して
先に進む。これが、見えている作業項目と見えない正しさのリスクとの違いである。理由の文字列は見た目
以上に重要だ。後続のパスが 50 個のマーカーを 50 回の場当たり対応ではなく 1 つの決定にまとめられるのは、
その文字列があるからだ。

**レビューは敵対的に行う。** 作業単位ごとにレビュアーを二人、互いにアンカリングしないよう別々の
コンテキストで走らせ、意見が割れたら三人目のエージェントにエスカレーションする。記事はこれがトークン
消費に見合うことが多いと述べているが、その理由は構造的である。レビュアーが一人だと実装者のフレームに
収束し、そのフレームの中で検討された系統的な誤りは 1,000 回連続で承認される。

## この手法を定義する一手

レビュアーが多数のファイルで同じ誤りを捕まえ続けているなら、ファイルを直してはいけない。ルールブックに
一文を足し、該当バッチを再生成する。

ファイル単位のパッチは、生成器がその誤りを produce し続ける状態をそのまま残す。だから次のバッチでも、
その次のバッチでも同じ代金を払うことになる。ルールブックの変更は誤りを源で止め、すでに触れてしまった
ものまで一緒に修復する。安価なバッチ再生成が利便性ではなく設計要件として挙げられていたのはこのためだ。

同じ論理があなたの注意力にも当てはまる。個別の失敗はフィクサー・エージェントのための仕事である。
消化フェーズにおけるあなたの仕事は、どの種類の失敗が繰り返されているか、そしてどの一つの変更が
その種類全体を消し去るかに気づくことだ。

## 意図をもって使う

トークンの支出はループに集中する。したがってモデル選択が実際に効いてくるのもループである。実装者は
物量が多くルールブックに拘束されるので、小さいモデルが合う。記事は Python から TypeScript への移植で
Sonnet のサブエージェント 12 個を並列に走らせたと報告している。レビュアー、裁定者、委譲役は物量が
少なく判断が重いので、大きいモデルが合う。どこでも最大のモデルを使えば、予算の大半をそれを最も
必要としない役割に費やすことになる。

Bun のマイグレーションで報告された数字が規模の感覚を与えてくれる。入力 59 億トークン、出力 6 億
9,000 万トークン、API 価格でおよそ 16 万 5,000 ドル。その対価として、100 万行の移植が Linux と
Windows でバイナリ 19% 減、実ワークロードで 2〜5% 高速という結果で出荷された。トークンがどこに
集中するかを把握していれば、このコストは事前に見積もれる。

並列化できないものは直列化する。ワークスペース全体のコンパイルは、ビルドを一度走らせてエラーを
バッチにまとめ、フィクサーがそこへファンアウトできるよう、オーケストレーター・スクリプトの背後に
置く。エージェントが各自でビルドを呼べば、せっかく設計した並列性を自分で食い潰すことになる。

## 成功はどう見えるか

Bun は既存テストスイート 100% パスの状態でマージされ、その後 19 件のリグレッションが出て、すべて
修正された。この規模で成功したマイグレーションの現実的な姿はそういうものだ。マイグレーションが答える
べき問いは、リグレッションが存在するかどうかではなく、それが見つけられて安く直せるかどうかである。
これは言い換えれば、前提条件の段階でつくった審判こそが、この全体が機能するかどうかを決めるという
ことだ。

## 自分の状況に合わせる

記事は、すべてのマイグレーションは異なり、これはレシピではなく出発点だと明言している。着手する前に
自分のマイグレーションを Claude と一緒に計画すること。とりわけフェーズ 1 のアーキテクチャ上の決定は、
ルールブックが対応表の集まりになるのか設計文書になるのかを決め、したがってそれ以降のすべての形を
決める。
