## 이 글이 뭔가요
Anthropic이 Claude Code로 대규모 코드 마이그레이션을 수행할 때 쓰는 6단계 프로세스를 설명한다. 예전에는 몇 년짜리 프로젝트였던 일이 몇 주 단위 작업으로 바뀐다. 조직 원리는 서두에 명시되어 있다. **코드를 고치는 것이 아니라, 코드를 만들어낸 프로세스(루프)를 고친다.**

6단계는 (1) 룰북·의존성 맵·갭 인벤토리 작성, (2) 버릴 각오로 하는 미니 마이그레이션으로 규칙 스트레스 테스트, (3) 병렬 에이전트로 전체 번역, 이어서 (4) 컴파일, (5) 실행, (6) 원본과의 동작 일치다. 두 개의 마이그레이션이 글의 근거를 이룬다. Jarred Sumner가 Bun을 Zig에서 Rust로 옮긴 사례(2주가 채 안 되는 기간에 약 100만 줄, 머지 전 기존 테스트 스위트 100% 통과)와 Mike Krieger가 주말 동안 진행한 Python → TypeScript 16만 5천 줄 포팅이다.

## 언제 유용한가요
- 포팅이나 재작성이 파일 단위로 리뷰하기에는 너무 커서, 손으로 옮겨서는 원본을 결코 따라잡을 수 없을 때.
- 마이그레이션이 그럴듯해 보이지만 원본의 동작에서 조용히 벗어나는 코드를 만들어내고 있을 때.
- 번역 작업을 병렬 에이전트에 어떤 순서로 어떻게 나눌지 결정해야 할 때.
- "완료" 또는 "정확함"의 합의된 정의가 없어서 재작성이 계속 멈춰 설 때.
- 이런 형태의 마이그레이션이 실제로 토큰과 시간을 얼마나 쓰는지 가늠해야 할 때.

## 핵심 포인트
- **심판을 먼저 만든다.** 기존 테스트를 이식 가능한 것과 내부 구현에 묶인 것으로 분류하고, 앞의 것을 두 코드베이스 모두에 대해 실행되는 어서션으로 다시 쓴 뒤, 심판 자체를 양방향으로 검증한다. 원본에 대해 통과해야 하고, 일부러 망가뜨린 코드에 대해 실패해야 한다. 테스트 스위트가 없다면 실제 엔드투엔드 시나리오로 패리티 하네스를 만든다.
- **갭 인벤토리보다 룰북이 먼저다.** 갭 인벤토리는 룰북의 기본값이 닿지 않는 지점으로 정의되므로 먼저 쓸 수 없다. 그리고 룰북의 형태는 그보다 앞선 결정에 달려 있다. 구조를 보존하는 포팅이면 룩업 테이블이 되고, 재설계면 설계 문서가 된다.
- **스트레스 테스트의 산출물은 진척이 아니라 더 나은 룰북이다.** 번역자·리뷰어·규칙 추출자로 미니 마이그레이션을 돌린 뒤 번역된 파일을 버린다. 파일에 박힌 결정들이 그것을 유지하려는 압력을 만들지 못하게 하기 위해서다.
- **완료는 기계적이어야 한다.** 큐의 완료 판정은 출력 파일이 디스크에 존재하는지다. 판단이 필요한 판정은 재개될 수 없는데, 긴 마이그레이션은 반드시 중단된다.
- **추측하지 말고 표시한다.** 확신 없는 구현자는 `// TODO(port): <이유>`를 남기고 넘어가, 보이지 않는 정확성 리스크를 보이는 작업 항목으로 바꾼다. 이유 문자열이야말로 나중 패스가 마커 50개를 결정 하나로 묶게 해주는 것이다.
- **적대적 리뷰.** 작업 단위마다 별도 컨텍스트의 리뷰어 둘, 의견이 갈리면 세 번째 에이전트로 에스컬레이션. 리뷰어가 하나면 구현자의 프레임에 수렴해 체계적 오류를 1,000번 연속 승인한다.
- **리뷰어가 같은 실수를 계속 잡아내면, 룰북에 문장 하나를 추가하고 배치를 재생성한다.** 파일 단위 패치는 생성기가 여전히 그 오류를 만들어내도록 내버려 둔다.
- **모든 곳에 가장 큰 모델을 쓰지 않는다.** 토큰 지출은 루프에 집중된다. 구현자는 작은 모델에(TypeScript 포팅에서는 Sonnet 서브에이전트 12개 병렬), 리뷰어와 위임자는 큰 모델에 둔다. Bun 마이그레이션은 입력 59억·출력 6억 9천만 토큰, API 가격 기준 약 16만 5천 달러를 써서 19% 작은 바이너리와 실제 워크로드 2~5% 향상을 얻었다.
- **성공에는 회귀가 포함된다.** Bun은 깨끗하게 머지되고 이후 19건의 회귀가 나왔으며 전부 수정되었다. 질문은 회귀가 없느냐가 아니라 찾아낼 수 있고 값싸게 고칠 수 있느냐다.
