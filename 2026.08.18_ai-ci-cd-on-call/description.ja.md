## この記事について
Anthropic の継続的インテグレーション（CI）チームのエンジニアが、自分たちで作ったオンコールエージェントを一人称で紹介する記事です。数か月にわたり、Claude Tag は Anthropic の CI/CD 障害における一次対応者として動いてきました。状況報告が出た最近のインシデントでは、その最初の報告をすべて Claude が書いており、通常は 15 分以内に最初の分析を公開しています。

記事はまず全体構成を示し、その後インシデントのライフサイクル各段階 — 検知、トリアージ、解決、検証と引き継ぎ — をたどりながら、各時点でエージェントが何をし、何が人間の担当として残るかを説明します。

## どんなときに役立つか
- オンコール当番が、持続的な信頼性向上の仕事ではなくアラートの仕分けと時間外の割り込みで埋まっているとき。
- 空のチャンネルではなく、根拠のある仮説からすべてのインシデントを始める一次対応者がほしいとき。
- インシデントの知識が人の頭の中にしかなく、レビュー可能でバージョン管理された指示に変える必要があるとき。
- エージェンティックなコーディングでマージ量が増え、CI プロセスも一緒にスケールさせる必要があるとき。

## 主なポイント
- **エージェントはオンコールがすでにいる場所にいる。** Claude Tag はオンコールの Slack チャンネル全体でメモリを保ち、文脈を得るために隣接チャンネル（サービスアラート、設定変更、PR の更新）を見ており、インシデント中はターンごとに指示を受け取ります。ルーティンのスケジュールも同じチャンネルで自然言語で行われます。
- **アクセス権は管理者が一度だけ付与する。** チームのツール（例：Datadog や Grafana）に MCP コネクタで接続したサービスアカウントを通じて設定します。
- **常設の指示は GitHub リポジトリにスキルとして置かれた markdown ファイル。** 複数のメンバーが手を入れられ、変更はコードと同じように管理されます。
- **アラートは決定的なまま、エスカレーションは決定的な経路とエージェンティックな経路の両方を持つ。** ルートの指示ファイルがページするか翌朝まで待つかの基準を持ち、新しいサービスの初期には、うるさすぎる／狭すぎるアラートルールの調整に Claude を使います。
- **トリアージは動的ワークフローとして走る。** オーケストレーションエージェントが実行役のサブエージェントを立ち上げ、各依存関係と情報源を並行して調査し、統合した状況報告を返します。根拠に基づく最初の分析までの中央値はインシデント発生から約 14 分、最速の例では最初の報告で約 4 分で根本原因を指摘しました。
- **調査は手探りではなく導かれている。** バグクラスごとの調査スキルが人間の踏む手順を符号化しており、ある例は 617 行に達し、実際のインシデント中にターンごとにトラブルシュートしながら作られました。
- **蓄積される教訓ログが記憶になる。** インシデントごとに、何が起きたか、根本原因、修正、覚えておくべき落とし穴を Claude が追記し、新しい調査のたびに最初に読みます。繰り返し現れるパターンは調査スキル本体へ昇格します。
- **解決の範囲は権限で区切られる。** フィーチャーフラグ配下の段階的ロールアウトは、エンジニアの権限で動く別エージェントが担当し、オンコールエージェントはそれ以外では PR、緩和手順、クラスタ操作を人間の承認向けに提案します。
- **コミュニケーションは別のエージェント。** `ci-weather` がインシデントチャンネル、ビルド指標、マージキューの統計、デプロイ遅延をまとめ、公開チャンネルにニュースルーム風のレポートを投稿します。チームは形式を何度も作り直しました。読みやすさは配管ではなくチーム固有の感覚だからです。
- **量が増えてもガードレールは維持された。** エンジニア一人あたりの四半期出荷コード量は 2021〜2025 年比でおよそ 8 倍ですが、すべての PR には名前のある人間のオーナーがいて、マージには承認が必要で、同じ CI ゲートを通ります。
