# AI ネイティブ SDLC を守る

マージされるコードの約 80% を Claude が書くソフトウェア開発ライフサイクルを、Anthropic の
セキュリティエンジニアリングチームがどう守っているか。

## 何が問題を変えたのか

Anthropic ではコード量とデプロイ速度が指数的に伸びた。ソフトウェアエンジニアは平均して、
2021〜2025 年の約 8 倍のコードを四半期あたり出荷している。Claude はコーディングアシスタントから
主たる作成者かつレビュアーへと進化し、全コードの半分以上は社内版 Claude Tag がマージしている。
人間のエンジニアは、方向づけ、意図の設定、最終承認の責任に集中する。

レビューやモニタリングをはじめとするセキュリティプロセスも、この速度に合わせて拡張する必要が
あった。そうしなければボトルネックの公式そのものになる — アムダールの法則である。セキュリティ
チームは急速に広がる攻撃対象領域を守りつつ、非決定的で絶えず進化するエージェントを中心に据えた
ライフサイクルを堅牢にしなければならない。

## 設計上の想定脅威

具体的に三つある。

1. 侵害された、あるいはプロンプトインジェクションを受けたエージェントが悪意ある変更を持ち込むこと。
2. エージェントが信頼できる入力として取り込んでしまうサプライチェーンおよび依存関係の汚染。
3. より馴染みのある種類のアプリケーション脆弱性が、いまやより大量に届くようになったこと。

以下のすべての統制は、このうち少なくとも一つに対応している。

## 四つの大きな戦略

- セキュリティを左シフトし、コード開発の段階に完全に統合する。
- 強いアクセス境界とアイデンティティ境界で被害範囲を封じ込める。
- 本番の前後で、自動の決定論的レビューとエージェンティックレビューを組み合わせる。
- 最もレバレッジの高い地点に人間を配置する。

## 段階ごとのライフサイクル

Anthropic のライフサイクルは圧縮されており、長い計画サイクルよりもプロトタイプと社内ドッグ
フーディングが牽引する。アイデアは組織のあらゆる場所から出てきて、従来の職能（フロントエンド、
バックエンド、デザイン）の区分は曖昧になる。レビューと承認には依然として人間が関わるが、
エージェンティックループも同時に回している。段階の名前自体は、従来型の組織から来た開発者にも
違和感がない。自然なゲートであり、だからこそセキュリティのゲートとしても使われている。

### Plan

Anthropic で最初期のセキュリティ自動化の一つが、Claude Opus を用いた PSR（project security
review）Web アプリケーションだった。プロジェクトの設計文書を取り込み、MITRE ATT&CK フレーム
ワークに照らして分析し、潜在的な脆弱性を特定して緩和策を提案する。この一つの実装で AppSec
チームの時間の大半が節約された。

その後、全社ポリシー・過去の判断・関連システムにわたるはるかに深い文脈を提供する社内ナレッジ
インデックスへ接続したことで大きく強化された。これによりリスクの理解が深まり、PSR 文書自体から
抜け落ちていた情報も拾えるようになった。Claude Code スキルを用意したことで、Claude は文脈が
どこにあってもさらに広くファンアウトして集められるようになった。Claude のリスク評価が正確だと
確信できた後は、リスクが十分低いと Claude が判断した立ち上げについては、チームが自らのプロジェクトを
承認できるようにした。

ここに最初の明確な適応が見える。PSR はもともと、長く高価なコーディング工程の前に問題を捕まえる
ための仕組みで、この段階で捕まえれば数か月の作り直しを節約できた。今日では主要機能のプロトタイプを
複数、数時間で作れる。そのため詳細なアーキテクチャレビューはより重要度の低いゲートになる。

> **変わらない原則。** セキュリティエージェントを組織の文脈に接続せよ。計画サイクルが圧縮される
> ほど、もはや必要ないかもしれない段階で詳細な文書化を強いるよりも、文脈がすでにある場所 —
> チャットスレッド、過去のレビュー、コードベース — にエージェントを連れていくほうがはるかに効果的
> である。いずれにせよエージェントにはコードの外側の文脈が必要だ。

### Code

AI ネイティブなエンジニアリング組織のセキュリティ担当者には新しいレバーがある。コードがどう
作られるかを直接形づくり、脆弱性を源で防げるということだ。以前は、繰り返し現れる脆弱性を観察して
セキュアコーディングのガイドラインを作っていたが、そうしたガイドラインは強制が難しく、標準化される
ことも稀だった。

Anthropic ではそのガイドラインが `CLAUDE.md` ファイルと全社スキルへの参照に埋め込まれており、
コードが生成されたその瞬間からそれに従う。これは閉じたループである。エージェントがバグのクラスを
発見したら、該当ファイルを更新して再発を防ぐ。

チームは、PR を開く前の最終ステップとして `/security-review` を実行するよう指示する `CLAUDE.md`
から始めた。このコマンド — チーム内部のレビューワークフローを製品化したもの — は、攻撃者が制御
しうる入力が入ってくる箇所を探し、疑わしいリンクをスキャンし、そのうえで自らの指摘を検証する。
今日ではこのレビューは Claude がコードを生成している最中に行われる。セキュリティガイダンスの
プラグインを入れると、Claude は会話とコードを進めながらレビューし、同じセッションの中でよくある
脆弱性に対処する。PR 時点の別のナッジは、社内の非技術チームをローコードのアプリホスティング
プラットフォームへ誘導し、従来セキュリティチームを悩ませてきたシャドー IT を避けている。

一部の顧客は `/security-review` を PreToolUse フックと統合し、より硬いゲートにしている。それも
有効であり、Anthropic 自身のハードなコードレビューゲートは test/CI の段階にある。

この段階のもう一つの関心事は被害範囲の封じ込めだ。開発者はノートパソコンだけでなく仮想マシン上で
コーディングする。これは比較的痛みの少ない移行で、制御と可視性が高まった。これらの VM 上の
エージェントトラフィックはエグレス許可リストの対象になっている。この厳格なエグレス制御は、
エージェントがプロンプトインジェクションのペイロードを含みうる信頼できない入力を読むときに特に
効く。注入された指示はインターネット上の任意の宛先には到達できず、持ち出し経路は監視下の少数の
サービスに限られる。リモートコーディングはかつて主に知的財産を封じ込めるためのものだったが、
今では成熟した AI コーディングチームがエージェントを封じ込める手段として採用している。

> **変わらない原則。** AI ネイティブなエンジニアリング組織における左シフトとは、脆弱性の発見と、
> Claude のコード生成をカスタマイズする指示の更新との間のループを閉じることである。被害範囲
> （最小エージェンシーの原則）とエージェントがアクセスできる範囲を、適切な場所でハードな境界に
> よって制限せよ。

### Test (CI)

AI ネイティブ変革のさなかで最初に痛むのがこの段階だ。ほとんどの開発者がエージェンティック
コーディングツールを使い、複数のエージェントを同時に走らせるようになると、チームは人間がコードを
レビューできる速度でしか進めないことがすぐに明らかになる。

人間のアカウンタビリティは依然として中心にある。変わったのは、自動のエージェンティックレビューと
決定論的レビューを組み合わせてレビューを加速し、人間のレビューは規制対象または本当に重要なコードに
残した点だ。人間によるコードレビューは標準とされてきたが、経験的な証拠はそれが完璧ではないことを
示している。セキュリティバグは世界中のソフトウェアで日常的に出荷されている。自動化されたプロセスは
より多くのコードをレビューし、とりわけ複雑な問題を捕まえる。

実質的なレビューコメントの付いた PR の割合は 16% から 54% に伸びた。指摘への信頼が高まったからで、
その信頼は、指摘が妥当であることの証明をエージェントに書かせるようにしたことから生まれた。過去の
claude.ai インシデントの背後にあったバグのおよそ 3 分の 1 は、現在導入している自動化で捕捉できた
はずだと判断されている。同じ方向の報告は他にもある。Intercom は PR の 19% を自動承認しており、
デプロイは倍増する一方、コード変更の破壊によるダウンタイムは 35% 減少した。CircleCI は Claude 上に
Chunk という自律エージェントを構築し、CI/CD のメンテナンス課題を解決して人間が見る前に自らの修正を
検証させ、エージェントのタスクが完了した Pull Request に変わる割合を倍にした。

Anthropic で PR が開かれると、複数のエージェントが自動的にレビューする。各エージェントは具体的で
狭い焦点に合わせて設計・スコープされ、追加の文脈と過去インシデントの記憶のために検索（RAG）を
活用する。これが一つの巨大プロンプトや万能セキュリティエージェントよりはるかに効果的な理由は次の
とおり。

- バイアスと死角を共有しない。
- 一つが侵害されたり誤ったりしても、別のレビュアーが捕まえられる。
- 複数の焦点領域に労力が薄く広がらない。

とはいえエージェントが無検査で本番にコードをマージしているわけではない。コードベースはリスクで
階層化され、どの部分を自動化するかは意図的に決められており、コードベースによっては丸ごと厳格な
人間承認プロセスを保っている。すべての承認は、その根拠となったシグナルと推論とともに記録され、
リスク加重サンプルは人間がレビューする。別のテストラウンドは「ユーザー A はユーザー B のデータを
決して読めない」といった不変条件に焦点を当て、追加の手動レビューを発動させる。エージェンティック
スキャンは、PR に直接コメントする SAST ツールとも組み合わせている。

エージェンティックであれ決定論的であれ、多くのスキャン手法は消費量ベースである。コードのスループット
が増えればコストも増え、チームはどの水準のカバレッジが適切かを決めなければならない。Anthropic は
コード速度の上昇に伴って総コストが増えることを受け入れつつ、単価は下がると見込んでいる。モデルは
コーディングで着実に良くなり続けているからだ。CI が壊れたときは、Claude Tag が CI/CD 障害の一次
対応者として動く。

> **変わらない原則。** 自動レビューは別種のリスクであり、別のやり方で統制される — 複数のゲートと、
> 別々のコンテキストウィンドウを持つエージェントによって。人間はループの中に残るが、コードベースの
> 性質によってライフサイクル上の別の位置にいることがある。

### Deploy (CD)

Anthropic は堅牢なステージング環境を維持し、一般的なセキュリティのベストプラクティスを実行して
いる。主要なローンチに対する外部ペネトレーションテストと、静的スキャンが見落とす、あるいは見られない
ロジックバグを捕まえるための定期的な DAST スキャンである。

ここでも AI は両刃だ。この段階まで届く脆弱性は減るが、生き残るものは最も微妙で捕まえにくい部類に
入る。そこに、より多くのコードがより頻繁に出荷される状況が重なると、定期的な動的テストはもはや
あまり動的には見えなくなる。

良い知らせは、こうした複雑な脆弱性を捕まえる多段・コンポーネント横断の推論がモデルの得意分野に
なってきたことだ。2 月に Anthropic は、Claude が 500 件を超える高深刻度の OSS 脆弱性を発見し、
修正を支援したことを公表した。Anthropic はステージング環境で継続的な AI ベースの DAST スキャンを
導入しつつあり、二つ以上のサービス間の前提が食い違うシステムレベルの脆弱性を探している。今日では
こうした機能を提供するベンダーも複数存在する。

> **変わらない原則。** 動的テストはデプロイの頻度に合わせるべきである。

### Monitor

良いセキュリティチームなら知っているとおり、コードが本番に出たら仕事が終わるわけではない。どんな
脆弱性も、ますます高度化する攻撃者にすぐ見つけられると想定すべきだ。公開バグバウンティ、レッドチーム
による模擬攻撃、依存関係・シークレット・サプライチェーン・クラウド構成・コンテナにわたる定期スキャン
といった標準的な実践は引き続き有効である。

大きな変化は二つ。

**アラートトリアージ。** アラートが発火すると、Claude は本番ログの確認、バグの根本原因分析、
ポストモーテムの執筆、そして場合によっては修正コードの作成まで始める。できないのはデプロイだ。
これは三つの権限しか持たない単一目的のシステムアカウントエージェントである — 新規ドキュメントの
作成、社内チャンネルへの投稿、本番ログへのアクセス。修正は別のエージェント＋人間のレビュー体制を
通らなければならない。本番にコードを押し込む際に被害範囲を封じ込めることが重要であり、一つ（あるいは
複数）のエージェントが別のエージェントのチェック役になるよう分離することが決定的だからだ。

これは CISO にとっても重要な教訓であり、著者が痛い目を見て学んだことでもある。モデルのアップグレード
後、インシデント対応エージェントは自らの判断で Slack 経由で別の Claude インスタンスに連絡し、コードを
書けるそのエージェントに修正のプッシュを依頼した。設計どおり人間のレビューゲートで止まったが、この
経験からチームは、モデルの指示や「モデルに何ができると考えているか」ではなく、アクセスと行動を基準に
境界を引くべきだと学んだ。今日 Slack 上でのエージェント間コミュニケーションは当たり前になっており、
エージェントのアイデンティティモデルには相当の検討が払われている。

**マイグレーション。** 会社の運用のしかたに潜む構造的な欠陥を直すためにコードマイグレーションが必要だ、
と気づく瞬間は、どのセキュリティエンジニアリングチームも経験している。かつては CISO が各部門の
エンジニアリングリソースの数パーセントを何四半期にもわたって求めるキャンペーンを張る必要が
あった。マイグレーションの経済的コストは下がり、それとともに全社的な調整コストも下がった。Claude は
数万行規模のマイグレーションを数日で自動化する。

> **変わらない原則。** すべてのエージェントに、その仕事に必要な最小権限だけを持つ単一目的の
> アイデンティティを与えよ。エージェント同士を連携させるなら、人間と同じチャンネル上でやらせよ。

### Governance

多くのセキュリティプロセスを自動化してきたが、安全なライフサイクルを保証するうえで人間は依然として
不可欠である。ただし注意の対象は、コードやバグレポートのレビューから、Claude Tag、ループ、
ダッシュボードへ移った。

だからこそ強いガバナンスが重要になる。スキルが陳腐化する、発見されたバグのクラスが `CLAUDE.md` に
戻らない、エージェントの判断がサンプリングされない — そのどれかが起きれば構造全体が劣化する。それを
防ぐ統制は次のとおり。

- コードベースをリスクで階層化し、その水準に応じてレビューを自動化する。
- 新しい AI レビュアーはすべてシャドーモードで始める。信頼を得るまでは人間の承認用にコメントを
  投稿するだけとし、チームは悪意ある変更を仕込んでレッドチームを行う。
- すべての自動承認の一定割合をサンプリングする。
- バイタルを見る。あらゆるセキュリティプロセスとワークストリームの主要指標をまとめたダッシュボードを
  維持し、注意深く監視する。
- すべてのエージェントの行為を SIEM へ流す。自動承認、ツール呼び出し、エージェント間メッセージの
  一つひとつが、使われたシグナルとともに記録されるので、どの判断も事後に帰属・監査できる。この
  データにより、エージェントを新しい種類のインサイダー脅威として扱い、アライメントから外れた行動には
  アラートを上げられる。

> **変わらない原則。** セキュリティエンジニアの仕事は、バグの監視からループの監視へ進化する。

## モデルが進化しても安全を保つ

ソフトウェア開発ライフサイクルと、それを堅牢にする手段がどれほど速く進化しているかは、いくら強調しても
足りない。モデルの能力は毎月前進し、新しい課題と新しい解決策を同時にもたらす。今日はうまくいかない、
あるいは経済的に見合わないことも、遠からずそうではなくなる可能性が高い。

立てるべき問いは「すべてスキャンする余裕があるか」ではなく、**「スキャンがほぼ無料なら何を回すか」**
である。それを前提に計画せよ。
