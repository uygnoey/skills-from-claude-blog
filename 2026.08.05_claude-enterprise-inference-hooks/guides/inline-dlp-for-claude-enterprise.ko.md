# Claude Enterprise를 위한 인라인 DLP

**inference hooks** 배포 가이드입니다. 모델이 내용을 다루기 전에 프롬프트와 도구 호출 응답을 검사하는 실시간 데이터 유출 방지 기능을 다룹니다.

## 무엇을 메우는가

보안팀은 대체로 데이터 이동에 관해 하나의 원칙을 지킵니다. 직원이 민감 데이터를 옮길 수 있는 모든 경로는 보안팀이 통제하는 검사 지점을 통과해야 한다는 것입니다. 이메일에도, 엔드포인트에도, 웹 트래픽에도 그런 지점이 있습니다.

AI 표면에는 없었습니다. 최소한 네이티브로, 그리고 모든 곳에는 없었습니다. 코딩 에이전트 내부에서는 그 에이전트의 클라이언트 측 훅으로 강제가 가능했지만, 이는 제품 하나만 덮고 클라이언트에서 설정되며 채팅과 에이전틱 워크스페이스는 경계 밖에 남깁니다.

inference hooks는 검사 지점을 제품의 속성이 아니라 조직의 속성으로 만듭니다.

## 아키텍처

```
사용자 / 에이전트
     │
     │  추론 요청
     ▼
Claude Enterprise ──── 서명된 WebSocket ────▶ 자사 보안 서버
     │                                              │
     │ ◀──────────── allow / deny 판정 ─────────────┘
     ▼
모델 생성
     │
     │  도구 호출 (MCP 커넥터 / 스킬 / 플러그인)
     ▼
도구 응답 ──── 동일 검사 ────▶ 판정 ────▶ 모델이 보거나 보지 못함
```

이후 배포 판단의 대부분은 두 가지 성질에서 나옵니다.

1. **동기적입니다.** 생성이 판정을 기다립니다. 자사 서버의 지연이 곧 모든 사용자의 지연이 됩니다.
2. **생성 이전에 일어납니다.** 모델이 출력을 만든 뒤가 아니라 내용을 읽기 전에 검사합니다. 탐지가 아니라 예방인 이유입니다.

## 무엇을 검사하는가

| 지점 | 대상 | 왜 중요한가 |
|---|---|---|
| 생성 이전 | 프롬프트와 주변 컨텍스트 | 사람이 데이터를 모델로 옮기는 직접 경로 |
| 모델이 도구 결과를 읽기 전 | 도구 호출 응답 | 커넥터가 아무도 입력하지 않은 제한 데이터를 끌어올 수 있음 |

설계 단계에서는 도구 응답 경로에 특히 주의해야 합니다. 문서 저장소, 티켓 시스템, 데이터베이스에 읽기 권한이 있는 커넥터는 분류된 내용이 자동으로 컨텍스트 윈도에 들어오는 경로입니다.

## 배포 형태

### 이미 쓰는 서버를 가리키게 하라

프로토콜은 공개 스키마를 갖춘 webhook 기반입니다. 실무적으로는 판정 지점이 이 용도로 새로 만든 무언가가 아니라 이미 운영 중인 플랫폼 — Netskope, Palo Alto Networks, Proofpoint, Zscaler 또는 사내 AI 보안 서버 — 인 경우가 대부분이라는 뜻입니다. 재사용이 권장 경로입니다. 정책 집합 하나, 감사 추적 하나, 규칙을 관리하는 장소 하나면 됩니다.

보안 벤더 입장에서는 같은 성질이 반대 방향으로 작동합니다. 문서화된 스키마에 맞춰 통합을 만들면, 고객은 설정만으로 조직을 해당 플랫폼에 연결할 수 있습니다.

### 조직 수준에서 한 번 설정한다

스위치 하나가 채팅, Claude Code, Claude Cowork, 그리고 MCP 커넥터·스킬·플러그인을 통한 도구 호출을 포함한 Claude Enterprise 표면을 덮습니다. 제품별 통합도, 제품마다 함께 배포할 별도 에이전트도 없습니다.

### 단계적으로 확대하라

제공되는 제어 항목들은 인라인 강제를 한 번에 전체 적용하는 것이 롤아웃 실패의 전형적인 방식이기 때문에 존재합니다.

- **Shadow 모드** — 서버는 평가하되 항상 허용합니다. 측정 단계이자 규칙을 조정하는 단계입니다.
- **역할 기반 예외** — 통제 장치가 그것을 운영하는 사람들을 잠가버리지 않도록 break-glass와 관리자 역할을 제외합니다.
- **비율 기반 롤아웃** — 일부 인원에게만 강제를 적용해, 잘못된 규칙이 전사 장애가 아니라 국소 사건이 되게 합니다.
- **실패 정책과 타임아웃** — 서버가 제때 응답하지 않을 때 무슨 일이 일어나는지 명시적으로 정합니다.

## 실패 정책 결정

기본값을 물려받기보다 의식적으로 결정할 가치가 가장 큰 항목입니다.

**Fail closed.** 판정이 없으면 추론도 없습니다. 커버리지는 완전하지만, 정책 서버 장애가 조직 전체 AI 장애가 됩니다. 데이터 민감도가 우선일 때 적합합니다.

**Fail open.** 타임아웃 내에 판정이 없으면 요청이 진행됩니다. 가용성은 유지되지만, fail-open 이벤트 하나하나가 검사되지 않은 요청입니다. 가용성이 우선일 때 적합하되, fail-open 이벤트를 로깅·알림·검토하는 경우에만 그렇습니다. 그렇지 않으면 구멍이 보이지 않습니다.

무엇을 택하든 타임아웃 값이 결정의 일부입니다. fail-closed에서 넉넉한 타임아웃은 느린 서버를 느린 제품으로 바꾸고, fail-open에서 빡빡한 타임아웃은 느린 서버를 조용한 구멍으로 바꿉니다.

## 운영상의 결과

- **정책 서버가 프로덕션 의존성이 됩니다.** 그 서버의 용량 계획, 온콜 소유권, 점검 시간이 이제 모든 AI 표면에 영향을 줍니다.
- **모든 규칙이 모든 요청에 지연을 더합니다.** 데이터 유출과 무관한 규칙은 다른 곳에 있어야 합니다.
- **차단에는 사람이 갈 길이 필요합니다.** 앞으로 나아갈 경로가 없는 차단은 업무를 감시되지 않는 채널로 밀어냅니다. 바로 이 통제 장치가 막으려던 실패 양상입니다.
- **커버리지 주장에는 증거가 필요합니다.** shadow 모드 상태, 비율, 예외, 실패 정책, 타임아웃을 날짜와 이유와 함께 설정 이력으로 남기세요.

## 이름에 대한 주의

"inference hooks"와 Claude Code의 라이프사이클 훅은 단어를 공유할 뿐 거의 공통점이 없습니다.

| | inference hooks | Claude Code 훅 |
|---|---|---|
| 실행 위치 | 서버 측, 추론 경로 안 | 클라이언트 측, 코딩 에이전트 안 |
| 설정 주체 | 조직 관리자 | 개발자 또는 팀, 설정 파일에서 |
| 통제 대상 | 여러 표면의 프롬프트와 도구 응답 | PreToolUse, PostToolUse 등 라이프사이클 이벤트 |
| 범위 | 조직 전체 | 에이전트 설치 하나 |

둘은 대안이 아니라 보완재입니다. 조직은 둘 다 운영할 수 있습니다.

## 시작하기

inference hooks는 Claude Enterprise 고객 대상 베타로 제공됩니다. 설정 세부 사항, webhook 스키마, 현재 제공 상태는 플랫폼 문서에 있습니다. 롤아웃 일정을 확정하기 전에 그곳에서 확인하세요.
