# Claude Enterprise のためのインライン DLP

**inference hooks** の導入ガイドです。モデルが内容を扱う前にプロンプトとツール呼び出し応答を検査する、リアルタイムのデータ損失防止を扱います。

## 何を埋めるのか

セキュリティチームはデータの移動について、たいてい一つの原則を持っています。従業員が機微データを動かしうるすべての経路は、自分たちが管理する検査点を通らなければならない、というものです。メールにもエンドポイントにも Web トラフィックにも、その検査点があります。

AI サーフェスにはありませんでした。少なくともネイティブには、そしてすべての場所には。コーディングエージェントの内部では、そのエージェント自身のクライアント側フックで強制できましたが、それは製品ひとつを覆うだけで、クライアント側で設定され、チャットやエージェンティックなワークスペースは境界の外に残ります。

inference hooks は、検査点を製品の性質ではなく組織の性質にします。

## アーキテクチャ

```
ユーザー / エージェント
     │
     │  推論リクエスト
     ▼
Claude Enterprise ──── 署名付き WebSocket ────▶ 自社セキュリティサーバー
     │                                              │
     │ ◀──────────── allow / deny の判定 ───────────┘
     ▼
モデルが生成
     │
     │  ツール呼び出し（MCP コネクタ / スキル / プラグイン）
     ▼
ツール応答 ──── 同じ検査 ────▶ 判定 ────▶ モデルが見る（または見ない）
```

導入に関する他の判断は、ほぼこの二つの性質から導かれます。

1. **同期的である。** 生成は判定を待ちます。自社サーバーのレイテンシが、そのまま全ユーザーのレイテンシになります。
2. **生成前に行われる。** モデルが出力を作った後ではなく、内容を読む前に検査します。これが検知ではなく防止である理由です。

## 何を検査するのか

| 地点 | 対象 | なぜ重要か |
|---|---|---|
| 生成前 | プロンプトと周辺コンテキスト | 人がデータをモデルへ移す直接の経路 |
| モデルがツール結果を読む前 | ツール呼び出しの応答 | コネクタが、誰も入力していない制限データを引き込みうる |

設計時には、ツール応答の経路に特に注意が要ります。文書ストア、チケットシステム、データベースに読み取り権限を持つコネクタは、分類済みの内容が自動でコンテキストウィンドウに入る経路です。

## 導入の形

### すでに使っているサーバーを指す

プロトコルは公開スキーマを備えた webhook ベースです。実務上は、判定地点がこの用途のために新設したものではなく、すでに運用中のプラットフォーム — Netskope、Palo Alto Networks、Proofpoint、Zscaler、あるいは自社構築の AI セキュリティサーバー — になることが多い、という意味になります。再利用が推奨される道です。ポリシーの集合はひとつ、監査証跡もひとつ、ルールを保守する場所もひとつで済みます。

セキュリティベンダーにとっては、同じ性質が逆向きに働きます。文書化されたスキーマに沿って統合を作れば、顧客は設定だけで自組織をそのプラットフォームに向けられます。

### 組織レベルで一度設定する

スイッチひとつが、チャット、Claude Code、Claude Cowork、そして MCP コネクタ・スキル・プラグイン経由のツール呼び出しを含む Claude Enterprise のサーフェスを覆います。製品ごとの統合も、各製品に併せて展開する別エージェントもありません。

### 意図をもって段階展開する

用意されている制御は、インライン強制を一度に全体へ適用することが導入失敗の典型的な形だからこそ存在します。

- **シャドーモード** — サーバーは評価しつつ常に許可します。測定のフェーズであり、ルールを調整するフェーズです。
- **ロールベースの除外** — 制御を運用する当人たちを締め出さないよう、ブレークグラスや管理者ロールを対象外にします。
- **割合ベースの展開** — 一部の集団にだけ強制を適用し、悪いルールが全社障害ではなく限定的な事故で済むようにします。
- **失敗時ポリシーとタイムアウト** — サーバーが時間内に応答しないときに何が起きるかを、明示的に決めます。

## 失敗時ポリシーの決定

既定値をそのまま引き継ぐのではなく、意識的に決める価値が最も高い項目です。

**フェイルクローズ。** 判定がなければ推論もありません。カバレッジは完全ですが、ポリシーサーバーの障害が組織全体の AI 障害になります。データの機微性が優先される場合に適します。

**フェイルオープン。** タイムアウト内に判定が来なければリクエストは進みます。可用性は保たれますが、フェイルオープンのイベントはひとつひとつが未検査のリクエストです。可用性が優先される場合に適しますが、それはフェイルオープンを記録し、アラートを出し、レビューする場合に限ります。そうでなければ穴は見えません。

どちらを選ぶにせよ、タイムアウト値も決定の一部です。フェイルクローズで長めのタイムアウトは遅いサーバーを遅い製品に変え、フェイルオープンで短すぎるタイムアウトは遅いサーバーを静かな穴に変えます。

## 運用上の帰結

- **ポリシーサーバーが本番依存になります。** そのサーバーの容量計画、オンコールの所有、メンテナンス枠が、すべての AI サーフェスに影響します。
- **ルールはひとつごとに、すべてのリクエストへレイテンシを足します。** データ損失に関わらないルールは別の場所に置くべきです。
- **拒否には人が進める道が要ります。** 前に進む経路のないブロックは、業務を監視外のチャネルへ押しやります。まさにこの制御が防ごうとした失敗の形です。
- **カバレッジの主張には証拠が要ります。** シャドーモードの状態、割合、除外、失敗時ポリシー、タイムアウトを、日付と理由とともに設定履歴として残してください。

## 名称についての注意

「inference hooks」と Claude Code のライフサイクルフックは、単語を共有するだけでほとんど別物です。

| | inference hooks | Claude Code のフック |
|---|---|---|
| 実行場所 | サーバー側、推論経路の中 | クライアント側、コーディングエージェントの中 |
| 設定する人 | 組織の管理者 | 開発者またはチーム、設定ファイルで |
| 制御対象 | 複数サーフェスのプロンプトとツール応答 | PreToolUse、PostToolUse などのライフサイクルイベント |
| 範囲 | 組織全体 | エージェントのインストールひとつ |

両者は代替ではなく補完です。組織は両方を運用できます。

## はじめかた

inference hooks は Claude Enterprise の顧客向けにベータで提供されています。設定の詳細、webhook スキーマ、現在の提供状況はプラットフォームのドキュメントにあります。展開日を確定する前に、そちらで確認してください。
