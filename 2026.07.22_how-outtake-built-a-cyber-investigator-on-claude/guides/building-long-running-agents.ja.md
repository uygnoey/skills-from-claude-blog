# 長時間稼働エージェントを構築する

Outtake が自律型サイバー調査官 Recon Agent をどう構築したか、そしてセッションが数時間に及ぶようになったとき何が持ちこたえたか。

## 1. 問題

Outtake は 2023 年、以前 Palantir のムーンショットチームにいた Alex Dhillon によって創業された。同社はデジタルトラストの攻撃チェーン全体を単一の防御へ統合し、2025 年だけで 2,000 万件を超える潜在的なサイバー攻撃をスキャンした。

Dhillon は状況を攻撃者の側から提示する。

> 「悪意ある者の帽子をかぶってみれば、いまは実のところ攻撃を仕掛けるには絶好の時期です。平均的な攻撃は AI のおかげで実行が速くなっただけでなく、AI のおかげでより深いアクセスまで手に入れます。」

攻撃は三つの段階で進む。公開データの収集、おとりとしてのなりすましの構築、内部システムの侵害である。従来のツールは各段階を別々に扱うが、そこにこそ空白がある。三つの段階は一つの敵対的ネットワークに属しているからだ。

## 2. Recon Agent がすること

**複製されたログインページ一つ**から出発し、証拠を収集・分類し、接続されたインフラ——たとえば「カスタマーサポート」を名乗る偽の Telegram アカウント——へ手がかりをたどり、敵対的ネットワークをグラフとして地図化し、攻撃者プロファイルと攻撃タイムラインを含む調査報告を作成する。

コードを読み、書き、実行し、盗まれた認証情報の行き先を追うために悪意あるログインページと直接やりとりする。

| 指標 | 値 |
| --- | --- |
| セッション実行時間の中央値 | 16 分 |
| 通常の範囲 | 1 時間以上まで |
| 観測された最長 | 2 時間 |

## 3. 開発の四段階

### 段階 1 — まず専門家になる

チームは自ら実際のサイバー調査を行い、顧客とデザインパートナーからドメイン知識を引き出して、「良い」とは何かを定義した。

> 「長時間稼働エージェントを作るうえで最も重要なのは、*良いとはどういう状態か？ エージェントは何をすべきなのか？* を本当に理解することです。」 — Jack Hayford、エンジニアリングリード

### 段階 2 — Claude Code でプロトタイプする

従来のエージェントフレームワークでは足りなかった。

> 「どの調査も異なり、深く技術的です。エージェントにはコーディングの筋力と能力が必要で、Claude Code は強力な初期ハーネスでした。」

ここで定まった中核の設計原則はこうだ。**オーケストレーションは厳しく制約する**——常に X、Y、Z を実行する——**が、判断を要する場面では即興を許す。**

### 段階 3 — 本番水準のハーネスへ卒業する

> 「Claude Code が導入したパターンはとても気に入っていましたが、より低レベルのプリミティブへの追加のアクセスが必要でした。」

チームは本番のために **Claude Agent SDK** へ移行し、エージェントループを作り直すことなく、メモリ・コンテキスト・ファイルシステムへのより厳密な制御を得た。

### 段階 4 — eval に駆動される緊密な反復ループを作る

自動評価スイートによって、チームは大きな変更を安全に加えられるようになった。別のコーディングエージェントが調査から出た提案を読み、新しいツールを書き、テストシナリオを構築する。人間は最終結果だけを評価する。

> 「こうした長く複雑なエージェントを作るときは、フィードバックループが自動化されていることが非常に重要です。」

## 4. 長時間稼働エージェントについての四つの学び

### ツール：ファイルシステムと bash で足りる

ファイルシステムは、コンテキスト圧縮を生き延びる記憶を与える。ファイルシステムに bash が加わることで、エージェントは障害に創造的に応じられる。

> 「ああした極めて強力で開かれたツールと能力をエージェントに手渡すことは、大きな段階的変化です。ネットワークの不調か何かでツールが失敗したのに、エージェントが適切な回避策を見つけてそのまま進んだ例をいくつも見てきました。」

### プロンプトは提案である

システムプロンプトは柔軟性を与えるが、長時間稼働エージェントでは持続力を欠く。

> 「時とともに複雑になっていくこの種の長時間稼働エージェントを作っていると、プロンプトは提案になります。そのプロンプトの一語一語が、いずれおそらく無視されるでしょう。」

対応はアーキテクチャ的である。振る舞いの要件をプロンプトから取り出し、**オーケストレーション層のハードコードされたガードレール**へ移す。これは高度な判断を要するタスクのためのコンテキスト領域を温存することにもなる。

### eval は信頼性のためだけでなく速度のためにある

30 分のトランスクリプトを手作業でレビューするのは規模に耐えない。eval は振り返りを構造化された採点項目へと自動化し、開発サイクルを劇的に加速する。

> 「どれだけ公式でなくとも『完璧』でなくとも、ごく最初から何らかの形の eval を作っておけば、そのエージェントをより速く作れるようになります。」

### エージェントを守る

プロンプトインジェクションは現実の脅威である。Outtake はプロンプトインジェクション攻撃への強さもあって Claude を選んだが、防御そのものはアーキテクチャ的だ。

> 「Recon Agent を作るうえでセキュリティは私たちにとって大きな論点です。ファイルシステムと bash を与えて、敵対的環境へ送り込んでいるのですから。」

戦略はこうだ。エージェントが乗っ取られうると想定し、周囲のシステムを被害が封じ込められるように設計する。Outtake はエージェントがインターネットへ手を伸ばすまさにその地点で信頼度を採点し、エージェントが触れようとしているものを評価するチェックポイントを置く。「このページはなりすましか？ マルウェアか？ いままさにエージェントにプロンプトインジェクションを試みているか？」

## 5. ベストプラクティスのまとめ

**「良い」とはどういう状態か、わかっているか。**
まず自分でそのタスクをやってみること。顧客とデザインパートナーからドメイン知識を引き出すこと。あらゆる反復に適用する固定の基準を定めること。

**それぞれの複雑さは見合うだけのものか。**
動く最も単純な版を見つけること。段階的に自動化すること。結果がそれを正当化するときにのみ複雑さを足すこと。

**ハーネスは作業量に見合っているか。**
Claude Code で仮説を検証すること。より低レベルの制御が必要になったら Agent SDK へ卒業すること。エージェントループを自分で作り直さないこと。

**エージェントはどこで制約すべきか。**
ガードレールはオーケストレーション層にハードコードすること。低レベルの判断には制約を置かないこと。即興の余地が最良の結果を生む。
