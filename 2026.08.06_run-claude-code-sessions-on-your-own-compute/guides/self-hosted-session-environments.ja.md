# 自前のコンピュート上でエージェントのコーディングセッションを動かす

2026年8月6日の Claude Code セルフホスト環境（パブリックベータ）告知から導いたデプロイガイドです。

## 何が変わるか

既定では、エージェントのコーディングセッションはベンダー側のインフラで実行されます。セルフホスト環境を使うと、組織が自ら用意したマシン — 自社ネットワークの内側、社内サービス・ツールチェーン・セキュリティ統制のすぐ隣 — で実行されます。Web、モバイル、デスクトップ、ルーティンのどこから開始しても、セッションはすべて同じ環境に入ります。

## まず判断する: 本当に必要か

告知はほとんどの企業にホステッド提供を推奨しています。運用・保守すべきインフラがないためです。セルフホストは、ネットワーク・ツール・コンプライアンス要件によってローカル実行が必須となるチームのためのもので、人員面のコミットメントが伴います。

プレビュープログラムの組織が採用した理由は 3 つでした。

1. **ネットワークアクセス** — 社内サービス・データベース・レジストリを公開インターネットに晒すことなく、セッションから到達できる。
2. **カスタマイズ性** — コンパイラ、SDK、内製 CLI が事前導入され、すべてのセッションがすぐビルドできる状態で始まる。
3. **コンプライアンス** — ソースコードとビルド成果物が、自組織の管理下のインフラに留まる。

いずれも必須要件でないなら、ホステッドのままにしてください。

## データ境界を正しく理解する

組織内で最も誤解されやすい点です。

| 自分でプロビジョニングしたインフラに残るもの | 推論のため送信されるもの |
|---|---|
| リポジトリのチェックアウト | プロンプト |
| ビルド成果物 | 応答 |
| シークレット | ツール結果（モデルが読んだコードを含みうる） |
| セッションが作成・変更したファイル | |

セッションのトランスクリプトは、どの表面からでもセッションを引き継げるよう保存されます。

セルフホストが移すのは**実行と成果物**です。会話までネットワーク内に留めるものではありません。セキュリティレビューには最初からそう説明してください。

## アーキテクチャ

### ランナー

**ランナー（runner）** をデプロイします。ランナーは長時間稼働するプロセスで、セッションを受け取り、セッションごとにエージェントのプロセスを起動します。イメージを作り、デプロイし、更新し、運用する対象がランナーです。

### 2 つのキャパシティモード

- **Fixed** — 一定数のランナーを常時稼働させ、セッションを分散します。運用負荷は最小ですが、アイドル容量が固定コストになります。
- **On-demand** — オーケストレーターがキュー中のセッションを監視し、到着に応じてランナーを起動、作業完了で停止します。容量が需要に追従する代わりに、オーケストレーター自体も運用対象になります。

アイドル容量が支配的なコストになるほど需要が変動しないなら、fixed を選んでください。

### 分離

1 つのランナーが複数セッションを処理できますが、**各セッションは専用のチェックアウトで実行されます**。開発者間・アカウント間の分離境界はランナーではなく、このセッション単位のチェックアウトです。

## Remote Control とは別物

Remote Control は、開発者自身のマシンで動いているセッションをスマートフォンやブラウザから継続する機能です。そのマシンがセッションの実行を止めればセッションも終了し、開始したユーザーに紐づきます。セルフホスト環境はプラットフォームチームが運用する共有インフラ上で動作し、どのユーザーでも利用できます。

## 利用条件

- パブリックベータ、Team・Enterprise プランの組織が対象。
- 既定では無効。
- ZDR を利用する組織では利用不可。

## 責任分担

プラットフォーム、開発者体験（DevEx）、開発生産性のいずれかのチームがセットアップと継続運用を担うことを前提に計画してください。

- ランナーイメージの構築と保守
- ランナーの更新
- on-demand モードを使う場合はオーケストレーターの運用

これを担うチームがないなら、正解はホステッド提供です。
