# 자체 컴퓨트에서 에이전트 코딩 세션 실행하기

2026년 8월 6일 Claude Code 셀프 호스팅 환경(퍼블릭 베타) 공지에서 도출한 배포 가이드입니다.

## 무엇이 달라지나

기본적으로 에이전트 코딩 세션은 벤더가 호스팅하는 인프라에서 실행됩니다. 셀프 호스팅 환경을 쓰면 조직이 직접 프로비저닝한 머신 — 자사 네트워크 안, 내부 서비스·툴체인·보안 통제 바로 옆 — 에서 실행됩니다. 웹, 모바일, 데스크톱, 루틴 중 어디서 시작하든 세션은 모두 그 동일한 환경으로 들어갑니다.

## 먼저 판단하기: 정말 필요한가?

공지는 대부분의 엔터프라이즈에 호스팅 방식을 권장합니다. 운영·유지보수할 인프라가 없기 때문입니다. 셀프 호스팅은 네트워크·툴링·컴플라이언스 요구사항 때문에 로컬 실행이 필수인 팀을 위한 것이며, 인력 투입 약속이 따라옵니다.

프리뷰 프로그램 참여 조직들이 채택한 이유는 세 가지였습니다.

1. **네트워크 접근** — 내부 서비스·데이터베이스·레지스트리를 퍼블릭 인터넷에 노출하지 않고도 세션이 접근할 수 있습니다.
2. **커스터마이즈** — 컴파일러, SDK, 내부 CLI가 미리 설치되어 있어 모든 세션이 곧바로 빌드할 수 있는 상태로 시작합니다.
3. **컴플라이언스** — 소스 코드와 빌드 산출물이 조직이 통제하는 인프라에 남습니다.

이 중 어느 것도 필수 요구사항이 아니라면 호스팅 방식을 유지하세요.

## 데이터 경계를 정확히 알기

조직 내부에서 가장 오해받기 쉬운 지점입니다.

| 직접 프로비저닝한 인프라에 남는 것 | 추론을 위해 전송되는 것 |
|---|---|
| 리포지토리 체크아웃 | 프롬프트 |
| 빌드 산출물 | 응답 |
| 시크릿 | 툴 결과 — 모델이 읽은 코드가 포함될 수 있음 |
| 세션이 생성·수정한 모든 파일 | |

세션 트랜스크립트는 어느 표면에서든 세션을 이어받을 수 있도록 저장됩니다.

셀프 호스팅은 **실행과 산출물의 위치를 옮기는 것**입니다. 대화까지 네트워크 안에 가두지는 않습니다. 보안 검토에는 처음부터 이렇게 설명하세요.

## 아키텍처

### 러너

**러너(runner)** 를 배포합니다. 러너는 장시간 살아 있는 프로세스로, 세션을 받아 세션마다 에이전트 프로세스를 시작합니다. 이미지를 만들고, 배포하고, 업데이트하고, 운영하는 대상이 바로 러너입니다.

### 두 가지 용량 모드

- **Fixed** — 정해진 수의 러너를 계속 띄워 두고 세션을 분산합니다. 운영 부담이 가장 적지만, 유휴 용량이 고정 비용이 됩니다.
- **On-demand** — 오케스트레이터가 대기 중인 세션을 감시하다가 세션이 도착하면 러너를 띄우고, 작업이 끝나면 내립니다. 용량이 수요를 따라가지만, 이제 오케스트레이터도 운영 대상이 됩니다.

유휴 용량이 지배적인 비용이 될 만큼 수요가 들쭉날쭉하지 않다면 fixed를 선택하세요.

### 격리

러너 하나가 여러 세션을 처리할 수 있지만, **세션마다 자체 체크아웃**에서 실행됩니다. 개발자 간·계정 간 격리 경계는 러너가 아니라 이 세션별 체크아웃입니다.

## Remote Control과 다릅니다

Remote Control은 개발자 본인 머신에서 돌아가는 세션을 휴대폰이나 브라우저로 이어서 쓰는 기능입니다. 그 머신이 세션 실행을 멈추면 세션도 끝나고, 세션을 시작한 사용자에게 묶입니다. 셀프 호스팅 환경은 플랫폼 팀이 운영하는 공유 인프라에서 돌아가며 누구나 사용할 수 있습니다.

## 사용 조건

- 퍼블릭 베타, Team·Enterprise 플랜 조직 대상.
- 기본은 비활성.
- ZDR을 사용하는 조직에서는 사용할 수 없음.

## 소유권

플랫폼, 개발자 경험(DevEx), 개발 생산성 팀 중 한 곳이 셋업과 지속 운영을 맡는다고 계획하세요.

- 러너 이미지 빌드 및 유지보수
- 러너 업데이트
- on-demand 모드를 쓴다면 오케스트레이터 운영

이를 맡을 팀이 없다면 정답은 호스팅 방식입니다.
