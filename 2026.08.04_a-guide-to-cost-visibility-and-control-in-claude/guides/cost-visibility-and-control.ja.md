# Claude におけるコストの可視化と制御

## コストの捉え方

測るべきはトークン消費量ではなく**成果あたりのコスト（cost-per-outcome）**だ。トークンは入力にすぎない。機械がどれだけ回ったかは教えてくれるが、持ち帰る価値のあるものが出たかどうかは教えてくれない。

どのプロジェクトでも、問う価値のある質問が 2 つある。

1. **AI 無しでこの仕事をしたらいくらかかったか** — リソースで、時間で、あるいはそもそも着手すらされなかったかどうかも含めて。3 つ目が抜け落ちやすい。決して始まらなかったはずの仕事には、比較対象となる「より安い前任者」が存在しない。
2. **モデルは判断と推論を要するタスクを扱っているのか、それとも大量の単純作業を処理しているのか。** 両者では正解が違い、その違いは物量の問題ではない。

2 つ目が効いてくるのは、モデルのミスマッチが双方向にコストを生むからだ。複雑な推論に能力の低いモデルを充てると、最終コストはしばしば**上がる**。トークンはリトライに費やされ、続いて人間の時間が訂正に費やされる。トークン単価は下がるのに、成果あたりのコストは上がる。逆方向では、基本的な文書処理にフロンティアモデルを投入すれば、そのタスクが要求してもいない能力に金を払うことになる。

## モデルファミリー

仕事の種類に対応した 4 つの主力モデル：

- **Fable** — 最も難しい問題
- **Opus** — 長期にわたる作業とコーディング
- **Sonnet** — 日常業務と分析
- **Haiku** — 大量・定型のタスク

さらに 2 つの道具が、この選択を二者択一でなくする。**Effort コントロール**は問題を解くときにモデルがどれだけ「考える」かを調整する。能力の高いモデルを低い effort で回すのは、同じモデルを高い effort で回すのとは別のコスト地点だ。**アドバイザー**方式は、小さいモデルが難しい問題にぶつかったときにだけフロンティアモデルに相談させる。ワークロードの大半は安く回り、難所だけがエスカレーションされる。

## Claude Enterprise のコストコントロール

IT 管理者には 3 つのコントロールがあり、推奨される順序には意味がある。各層が、次の層の統治対象を縮めてくれる。

**アクセスゲーティング**は、どのグループとカスタムロールが Claude Code や Claude Cowork といった製品にアクセスできるかを決める。これを最初にやることで、全社一斉のスイッチではなく部門単位の段階的ロールアウトが可能になる。狙いは恒久的な制限ではなく、次の部門が加わる前に、ある部門の実際の使われ方を学ぶことだ。

**モデルコントロール**は 2 階層で働く。*エンタイトルメント*はチームがそもそもどのモデルにアクセスできるかを定め、*デフォルト*は新しい会話がどのモデルで始まるかを定める。組み合わせれば、複雑な仕事を担うチームにだけ最も能力の高いモデルを開き、それ以外は Sonnet をデフォルトにできる。デフォルトは見た目以上に効く。利用の大半はデフォルトに従うので、妥当なデフォルトを 1 つ設定するほうが、どんなエンタイトルメント制限よりも多くの支出を動かす。

**ハード支出上限**は、組織・個人ユーザー・グループの各レベルに利用の天井を置く。グループのセマンティクスは丁寧に読む価値がある。各メンバーが指定された上限を受け取るので、グループ上限は「最も速く使う人が枯らす共有プール」ではない。上限は即座に有効になる — この点が予算アラートとの決定的な違いだ。

管理者はさらに、支出上限の引き上げ申請を自動化し、上限に近づいているユーザーを特定し、急変する利用パターンを追跡できる。

## 利用状況を観測するツール

**利用分析（Usage analytics）**は支出を人・チーム・モデル別に分解する。データのエクスポートは請求書と整合するため、請求の突合にはとくにこのツールが向く。

**Analytics API** は同じデータを既存の業務システム — BI ツール、財務システム、社内ダッシュボード — に供給する。定期的にエクスポートを繰り返している作業は、こちらに移すべきものだ。

**Analytics Chat** はフルレポートを生成せずに、自然言語で利用に関する質問に答える。

> Who are our top spenders this month?

> Which team's usage grew fastest this quarter?

別の作業の途中でふと湧く質問のためのツールだ。質問と答えのあいだにレポーティングのサイクルが挟まらないことに価値がある。

## API 上で構築するときのコントロール

Claude Console には 4 つのレバーがあり、いくつかは重ねて効く。

**プロンプトキャッシュ**はリクエスト間で再利用可能な内容を保存し、キャッシュヒット時の再処理コストを通常の入力単価の約 10% 程度まで下げる。大きく安定したプレフィックスが多数の呼び出しで繰り返される場面 — システムプロンプト、分類体系、スキーマ、参照ドキュメント — で効く。

**バッチ処理**は急ぎでないジョブを半額で回す。夜間のカタログ分類が典型例だ。バッチ割引はキャッシュと重ねて効くため、繰り返し走る大量ジョブをバッチに移すことが、単独の施策としては最大の節約になることが多い。

**effort パラメータ**は呼び出しごとに推論の強度を制御する。低い設定はルーティングや抽出に、高い設定は最終的な推奨に向く。要点は、パイプライン全体に一律でピーク単価を払うのではなく、**いつ**ピーク単価を払うかを選ぶことにある。

**アドバイザー戦略**は、大半の作業を Sonnet のような小さめのモデルで行い、重要な意思決定点でだけフロンティアモデルに相談する。プレミアム単価は、判断の重い瞬間にだけ支払われる。

大量処理のパイプラインなら、これらは順に積み重なる。バッチに移し、安定したプレフィックスをキャッシュし、機械的なステップを低い effort に落とし、実際に何かを決めている箇所でだけフロンティアモデルへエスカレーションする。各層は請求書の別々の部分に効くので、節約分どうしが食い合うことはない。
