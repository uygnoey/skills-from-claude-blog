# Claude Code のセッションからより多くを引き出す

エージェンティックなコーディングツールはシート単位ではなくトークン単位で課金される。つまり同じ作業でも、
セッションの回し方次第でコストは大きく変わる。あるセッションはテストファイルと実装を読んでバグを直す。
別のセッションはまずリポジトリを grep し、12 個のファイルを開き、それらすべてを — その朝に読んだものも
含めて — 残りのすべてのターンに引きずっていく。

著者 Lydia Hallie 氏の捉え方を覚えておくとよい。トークンを効率よく使うとは、総量を減らすことではなく、
使ったトークンが実際に頼んだ仕事に向かうようにすることだ。

請求額を決める変数は 2 つ。トークン 1 個の値段と、セッションが送るトークンの量である。

## パート 1 — トークン 1 個の値段

### モデル

大きなモデルは入力・出力どちらのトークンにもより多くの処理を行い、価格もそれに応じる。問題にモデルを
合わせること。本当に難しい、あるいは曖昧な作業には大きなモデルを、定型的な変更には小さなモデルを。

### 入力と出力

すべてのターンには 2 つのフェーズがある。**プリフィル** では、モデルは与えられたもの — システム
プロンプト、ツール定義、`CLAUDE.md`、ここまでの会話、新しいメッセージ — を読む。これが入力トークンだ。
**デコード** では応答を 1 トークンずつ書く。これが出力トークンで、入力のおよそ 5 倍の価格になる。

思考トークンは出力トークンなので、effort レベルは高い側を直接動かすダイヤルである。新しいセッションで
`/model` と `/effort` を実行して両方を確認しておくとよい。どちらも前のセッションから引き継がれるため、
今かかっている設定が意図したものとは限らない。1 セッション丸ごと思考を切りたい場合は
`MAX_THINKING_TOKENS=0` が `/effort low` の一段下に降りる（Fable 5 には適用されない）。

### プロンプトキャッシュ

長い会話が成立するのはキャッシュのおかげだ。キャッシュ読み出しは入力価格のおよそ 0.1 倍、書き込みは
最大 2 倍でトークンあたり一度だけ。一度書けば、以降のすべてのターンで安く読める。

だからこそキャッシュの無効化が高くつくイベントになる。

| きっかけ | 影響 |
|---|---|
| `/model` | モデルが変わればキャッシュも変わる — 全体を再プリフィル |
| `/effort` | キャッシュキーの一部 — 全体を再プリフィル |
| 高速モード | これもキャッシュキーの一部 |
| `/compact` | 会話を置き換える。システムプロンプトは残る |
| 時間 | サブスクリプションでは 1 時間、API キーでは 5 分で失効（`ENABLE_PROMPT_CACHING_1H=1` で API キー側も 1 時間に） |
| セッション再開 | 通常は失効済み。システムプロンプトは起動時に再構築される |

知っておく価値のある例外: `/rewind` はコストがかからない。会話の末尾を切り落とし、それより前は
キャッシュされたまま残す。一方 `/compact` は会話を書き直すので必ずコストがかかる。だから席を外す
*前* に、まだ温かいうちにコンパクトせよ、という助言になる。キャッシュが切れた後ではなく。

## パート 2 — セッションが送るトークンの量

一度きりで済むものは何もない。読んだファイルも実行したコマンドの出力も、セッションが終わるまで毎ターン
再送される。キャッシュされているので安いが、そこに在り続け、コンテキストを占有する。

### 入力する前からロードされているもの

新しいセッションで `/context` を実行すると常設の負荷が見える。接続中の各 MCP サーバーのツール定義、
システムプロンプト、`CLAUDE.md`、起動時の読み込み項目。そのすべてを毎ターン支払っている。

減らす方法は 2 つ。`CLAUDE.md` を具体的に保ち、ワークフローの指示は使うときだけ読み込まれるスキルへ
移すこと。そして使っていない MCP サーバーを `/mcp` で無効化すること。

### 作業中に足されるもの

**ファイル。** 訊き方が流入量を決める。「テストが落ちている」は grep と大量の読み込みを招く。ファイルを
名指しすれば Read は 1 回。`@` メンションすれば 0 回になる — Claude Code がメッセージ送信前にファイルを
添付するからだ。ファイル自体が占める領域はどちらでも同じで、節約できるのは往復のほうである。メンション
は 1 会話につき 1 回に。再度メンションするとコピーがもう 1 つ添付される。

**コマンド出力。** ファイルと同じように追記され、そのまま残る。饒舌なテストランナーは数百行を残し、それが
一日中再送される。おおよそ 3 万文字を超える出力はファイルに書き出され、会話にはプレビューが残る
（`BASH_MAX_OUTPUT_LENGTH` がしきい値を決める）。極端なケースは防げるが、じわじわした蓄積は防げない。

対処は、一日中使うコマンド 2〜3 個を静かにするフラグ込みで、自分がタイプするとおりに `CLAUDE.md` へ
書いておくことだ。たとえば単一のテストファイルを `--reporter=dot` で走らせる、といった具合に。呼び出し方を
割り出すためのターンと、残りのセッションずっとコンテキストに居座る出力の両方を節約できる。

### どれだけ残るか

40 ターン目は、それ以前の 39 ターンを再送する。だから 1 本の長いセッションは、同じ作業を短いセッションに
分けた場合より高くつく。

- 新しいタスクを始めるなら `/clear`。後で戻るかもしれないなら先に `/rename`。
- ひとまとまりの作業が終わったが、そこで確定した内容が必要なら `/compact`。何を残すかを伝える。答えが
  いつも同じなら、`CLAUDE.md` にコンパクト指示のセクションを置く。
- 1M コンテキストのモデルでは `/autocompact 200k` で自動コンパクトの安全網が戻る（Claude Code
  v2.1.221+）。

落とし穴が 1 つ。`/loop` はそれを開始したセッションの中で完全なターンとして発火し、毎回会話全体を
引き連れていく。しかも発火の間隔が 1 時間を超えると、毎回キャッシュミスにもなる。ループは別ターミナルの
新しいセッションで始めること。

### サブエージェント

サブエージェントは自分のコンテキストを持つ — システムプロンプト、ツール、`CLAUDE.md`。ただしあなたの
会話は持たない。自分のターンを消費し、戻ってくるのは答えだけで、それ以外は破棄される。

トレードオフは双方向に実在する。メインセッションが既に持っているものを読み直すかもしれないし、自分の
ターン分のコストも払う。割に合うのは、残す必要のない出力が大量に出る作業で、ログ解析が最も分かりやすい
例だ。ログではなくレポートだけが返ってくる。繰り返し任せる騒がしい作業なら、サブエージェントの設定で
小さめのモデルを固定しておく。指定がなければメインセッションのモデルで動く。

## どこから見るか

おおよそ影響の大きい順に:

1. **セッションの長さ** — 毎ターンどれだけの会話が再送されているか。
2. **コマンド出力の大きさ** — その中にどれだけノイズが溜まっているか。
3. **読んだファイル** — 必要なものをどれだけ正確に指し示せているか。
4. **モデルと effort** — 最初に意図して決め、途中で切り替えない。

たいていは前の 2 つのほうが最後の 1 つより効く。
