# 政府機関の中でエージェンティック・コーディングツールを展開する

Claude Code と Claude Cowork が Claude for Government Desktop を通じてパブリックベータとして
提供され、FedRAMP High 認証環境を介して配信される。本ガイドは、それを認可し、予算をつけ、運用し、
配布しなければならない人たちにとって、それが実務上どういう意味を持つのかを追う。

## 計画の形を変える二つの事実

計画の大部分は、この提供物が持つ二つの性質から導かれる。どちらも最初に読んだときに見落とされやすい。

**会話履歴は機関が管理する端末にローカル保存される。** 推論は FedRAMP High 認証環境の中で走るが、
やり取りの記録はノート PC 上に残る。これによりエンドポイントが審査範囲に入る。システムセキュリティ
計画書上、これは機関のエンドポイントポリシー(ディスク暗号化、バックアップの取り扱い、保存期間、
端末紛失時のワイプ手順)に従う機関保有データであり、ベンダー側の保持として記述してはならない。
ベンダー側の保持スケジュールを期待して来た審査担当者は、評価の途中でこの範囲の移動に気づくよりも、
最初から明示された方が納得が早い。

**使用量エクスポートに含まれるのはメータリングデータのみである。** これによって機関は、機微な資料を
境界の外に出すことなく、ATO の照会や監察官(IG)からの使用状況の求めに答えられる。反論が出る前に
それを取り除けるので、早い段階で示しておく価値がある。

## 認可

提供物は FedRAMP High 認証環境を通じて配信され、推論もその内部で実行される。審査を支える文書は
三つあり、公開レベルは二段階だ。FedRAMP Secure Configuration Guide と正式な変更通知は公開されて
おり、ペネトレーションテストの要約は Anthropic のトラストセンターを通じて NDA のもとで入手できる。

証跡マップは評価会議の最中ではなく、その前に作っておく。審査担当者のどの質問にも名前のついた成果物が
裏づけとして存在すべきであり、発表が答えていない質問は推測で埋めずに未決事項として記録すべきである。

記録に含めるべきものがもう一つある。この提供物はパブリックベータとして発表されている。これは審査中に
発見する細部ではなく、リスク登録簿の項目である。

## 権限委譲による管理

設計上の前提は、省庁が一度認可したうえで運用を委譲することであり、構成機関ごとに調達と設定を繰り返す
ことではない。省庁レベルの管理者が下位機関にシートを割り当て、制限はアイデンティティに紐づいて動く。

SCIM のグループマッピングが、グループごとのレート制限、ドル上限、許可モデルを設定する。階層型構成が、
下位機関のデフォルト——Claude が何に接続できるか、どの機能が使えるか——を定める。したがって、リスク
姿勢の異なる三つの下位機関を一つの認可の下に置くことは、三本の別々の契約ではなく設定作業になる。
ただし、誰かをプロビジョニングする前にグループ構造が正しく定まっていることが条件だ。

まずその構造を固め、下位機関ごとにグループを一つ対応させ、プロビジョニング解除を明示的にテストする。
グループからユーザーを外せばアクセスが消える必要があり、これは仮定するのではなく検証する事柄である。

## 予算

従量課金と歳出予算は、一つの仕組みで折り合う。使用量は固定単位で購入され、超過不可(not-to-exceed)
の上限がハードにかかる。財務部門が青天井の請求を何が防ぐのかと尋ねたとき、その上限が答えになる。

組織は標準シートを選ぶことも、支出とモデルの制限を設けたカスタムティアを選ぶこともできる。管理者は
管理コンソールでユーザー別・モデル別の使用量を追跡でき、残高が尽きる前に自動のバーンダウン通知が
警告する。

セットアップの際、この通知には少し注意を割く価値がある。通知のない上限は、予算統制をサービス停止に
変えてしまう。通知は補充の権限を持つ人に届くようにし、最初の残高が尽きた後ではなく尽きる前に補充
経路を合意しておくこと。

## 監督

管理操作はハッシュチェーンされた監査ログに記録され、組織管理者が製品内で直接レビューできる。ベンダー
側では、機微な操作に二名承認が必要とされる。Anthropic による一方的な操作を何が防ぐのか、と審査担当者
に問われたときの答えがこれである。

展開の段階で、監査ログのレビュー担当者と頻度を指名しておく。誰も読まない監査ログは、統制が存在する
証拠ではあっても、統制が機能している証拠にはならない。

## 配布と変更

デスクトップアプリケーションは標準的な機関の MDM プラットフォームを通じて配布されるため、機関が
すでに持っている仕組みをそのまま使える。全体展開の前に一つのリングでパイロットを行い、そのリングを
出す前に、ローカル保存される会話履歴をエンドポイントポリシーが確実にカバーしていることを確認する。

機関は商用顧客と同じリリーススケジュールで機能を受け取る。これは目玉となる利点であり——商用製品の
数四半期遅れで待つ必要がない——同時に義務でもある。変更が商用のペースで到着するため、機関の変更管理が
それを吸収しなければならない。正式な変更通知がそのための仕組みなので、通知されるべき相手に届くよう
経路を設定しておくこと。

## 契約

新規顧客は claude.com/solutions/government からアクセスを申請する。請求上の契約当事者は Anthropic
のままであり、クラウド事業者との別途の契約関係は必要ない。

## 実行可能な順序

1. 認可境界を確定し、処理がどこで行われ、データがどこに残るのかを書き出す。
2. 三つの文書を集め、証跡マップを作る。
3. グループ構造を設計してから、プロビジョニングする。
4. ライセンス形態を選び、上限を設定し、通知の宛先を決める。
5. 監査ログのレビュー担当者と頻度を割り当てる。
6. MDM 向けにパッケージ化し、エンドポイントポリシーを確認し、一つのリングでパイロットする。
7. ベータであることと未決の論点をリスク登録簿に記録する。

やり直しが高くつくのはステップ 1 と 3 である。残りは最初のリングが動き出してから調整できる。
