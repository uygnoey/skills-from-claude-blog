# Claude Codeでモデルとエフォートレベルを選ぶ

## 要点

- **モデル選択は固定された重みのセット**、つまりモデル全体の能力レンジを選ぶことだ。コンテキストを与えたり
  方向づけたりはできるが、モデル全体の知識ベースと能力そのものはすでに決まっている。
- **エフォートは「考える時間」以上を意味する。** 読むファイルの数、使うツール、あなたに確認を返すまでに
  踏むステップ数を含め、Claudeがあなたのリクエストに対して全体としてどれだけの作業をするかを制御する。
- **定型的なタスクには小さいモデルを、複雑または曖昧なタスクには大きいモデルを選ぶ。** 各モデルの既定の
  エフォートレベルから始め、タスクごとではなく、自分が扱う仕事の種類に応じた一般的な好みとして調整する。
- **Claudeが関連するコンテキストをすべて持ち、明らかに試みたうえで間違えたなら**、より高性能なモデルを
  選ぶ合図だ。**ファイルを飛ばした、テストを実行しなかった、リファクタリングを途中で投げ出したことで
  間違えたなら**、エフォートレベルを上げる。

## 二つの設定

Claude Codeには「答えをよくする」ように見える設定が二つある。モデル設定とエフォートレベルだ。Claude Fable 5
のような大きいモデルはClaude Sonnetより賢い出力を返し、エフォートレベルが高ければ答える前に長く考える、と
予想するかもしれない。

最初の想定は正しい。最大のモデル群は業界標準のベンチマークにおいてより高性能だ。

しかしエフォートは単なる思考時間以上を意味する。エフォートレベルは、Claudeがあなたのリクエストに対して
全体としてどれだけの作業をするかを制御する。そこにはモデルがどれだけ長く考えるかも含まれるが、**何個の
ファイルを読むか**、**どれだけ検証するか**、**複数ステップのタスクをあなたに確認するまでどこまで押し進めるか**
も含まれる。

エフォートが高いほど、Claudeはあなたのところへ戻る前にそうした行動 — ファイルを読む、テストを走らせる、
二重にチェックする — をより多く取る。エフォートが低ければ、自分でトークンを費やして解き明かすより、あなたに
もっとコンテキストを求めるほうを選ぶ。

## モデル選択の仕組み

エンターを押すと、Claude Codeはあなたのメッセージを、システムプロンプト、ツール定義、`CLAUDE.md`、会話履歴、
コンテキストにあるファイルとともに組み立てる。そのすべてが一つのリクエストとしてAPIへ送られる。

ただしモデルはそれをプレーンテキストとしては見ない。サーバー上で最初に起きるのは**トークン化**だ。テキストが
断片に分割され、各断片がモデルの学習時に固定された語彙の整数へマッピングされる。`const` は `1978` に、
`await` は `4293` にマッピングされるかもしれない。ここから先、あなたのプロンプトは整数の配列である。

モデルの仕事は、その配列を受け取って次に来るトークンを予測することだ。語彙内のすべてのトークンについて確率を
計算し、上位から選ぶ。`const x = await` のあとなら、よく訓練されたモデルは `fetch` に高い確率を、`banana`
にはほぼゼロの確率を置く。

入力トークンをその確率へ変えるのが**重み**(パラメータとも呼ばれる)だ。大きな行列として組織された数十億個の
数値である。1トークンを予測するために、モデルは入力をそれらの行列 — 長い行列積の連鎖 — に通し、最後に確率を
読む。モデルが「知っている」ことのすべては重みの中にある。

各モデルの重みは学習時に定まり、あなたがリクエストを送る頃には読み取り専用だ。プロンプトも `CLAUDE.md` も
コンテキストも、それを変えることはない。(*推論(inference)* という言葉が意味するのはそれだけだ。学習が
終わったあと、重みを固定したままモデルを使うことである。)

ClaudeがTypeScript、人気のフレームワーク、慣用的なGo、その他の一般的なプログラミング知識について知っている
ことはすべて、学習時にその重みへ符号化された。プロンプトとコンテキストは予測を**方向づける(steering)**
ことはできる — 実際のコードをClaudeの前に置くことが方向づけであり、非常によく効く — が、重みそのものに何かを
加えることはない。

モデルの学習時に存在しなかったライブラリなら、それは重みの中にない。ドキュメントをコンテキストに入れれば
Claudeはそれを使うが、**それは方向づけであって教えることではない**。応答はそのリクエストに限って影響を
受けるだけで、基盤となるモデルが情報を保持したわけではない。だからClaudeが存在しないAPIを自信たっぷりに
呼び出すハルシネーションは、検索に失敗したのではなく、学習パターンからもっともらしく見えるトークン列を重みが
生成した結果である。

では、モデルを変えると実際に何が起きるのか。**あなたのリクエストをどの凍結された重みのセットが処理するかが
入れ替わる。**

モデルは答え全体を一度に生成しない。1トークンを予測して列に追加し、次の1トークンを得るために計算全体をもう
一度走らせる。200トークンの応答は、重みを通る200回の別々のパスだ。待ち時間と出力コストの大半はこのループから
来る。

つまりモデル設定は、どの重みがリクエストを処理するか、そして出力トークン1個あたりのコストを決める。決めない
のは**何トークン生成されるか**だ。その数は同じプロンプトでも、Claudeがどれだけの作業をすると決めるかによって
大きく変わる — そしてそれこそがエフォートの制御するものである。

## エフォートレベルの仕組み

Claude Codeがタスクに取り組んでいるとき、生成されるトークンはいくつかのカテゴリに分かれる。

- **思考(thinking)** — 行動の前や行動の合間にストリーミングされる推論。
- **ツール呼び出し** — `Read` や `Edit` のようなツール名と引数を含む構造化ブロック。Claude Codeがこれを
  パースして実行する。
- **あなたへのテキスト** — 計画、進捗の更新、最後の要約。

これらはすべて同じループから出る通常の出力トークンであり、同じレートで課金される。思考トークンも他の出力
トークンとまったく同じように生成され、そのターンの残りの間コンテキストに留まる。Claudeがコードを書く段に
移るとき、それ以前の推論は読み込んだファイルと同じく入力の一部になる。

エフォートレベルは、プロンプトと並んで**リクエストの一部としてモデルに送られる**。モデルは各エフォート
レベルでどう振る舞うべきかを学習しており、その学習済みの振る舞いは凍結された重みに焼き込まれている。
リクエストが到着すると、エフォートレベルはモデルが反応するもう一つの入力であり、プロンプト本文に反応するのと
同じことだ。これは、タスクを完了と見なす前にどれだけ徹底し、どれだけ確信している必要があるかというClaudeの
振る舞いを設定する。毎ターン考慮され、より高い確信の答えを出すためにより多くのトークンが費やされる結果に
なる。同じプロンプトでも、高エフォートの経路は低エフォートの経路のおよそ7倍のトークンを生成しうる。

高いエフォートレベルでは、Claudeはしばしば計画を立てることから始め、エフォートの水準がその計画の深さと広さに
影響する。ただし**計画は固定されるわけではない**。行動の結果を受け取るにつれ、Claudeはどこまで進んだか、
積み上がった結果にどれだけ確信があるかを更新する。だから三つの仮説からなるデバッグ計画のステップ1でバグが
見つかれば、「仮説2と3を調べる」はもう必要ないかもしれない。Claudeは通常それを明示的に述べ — *最初の確認で
見つかったので、残りの確認は不要だ* — 先へ飛ぶ。Claude Codeでタスクリストが実行途中に書き換わるのがこの場面だ。

高いエフォートレベルではClaudeは追加の仮説を二重に確認したり正しさを検証したりする方へ傾くが、単純なタスクで
使用量を人為的に膨らませることは一般的にない。チームはモデル学習時に「考えすぎ」に細心の注意を払っている。
それが有効性を損なうからだ。

## エフォートレベルの選び方

ほとんどのタスクでは、モデルの**既定のエフォートレベル**を使うこと。既定値とは、Claudeが大多数の人がその
タスクに費やしたいと思うであろう水準に合わせてトークン使用量をスケールする地点だ。

エフォートは、Claudeがどれだけ強く、どれだけ長く働くかを調整する**手動のオーバーライド**だと考えるとよい。
自分の領域や仕事の種類ゆえに徹底さや速さへの強い好みがあるときに、意図的に選ぶ。タスクごとの判断というより、
一般的な好みとして扱うほうがよい。

Claude Opus 4.8のローンチ後の実務的な補足がひとつある。Anthropicのテストでは、同じタスクにおいてOpus 4.7の
既定エフォート設定を使う場合と比べ、Opus 4.8の既定エフォート設定を使うと、ほぼ同じトークン数でより良い結果が
得られた。

## Claudeが間違えたとき、何を変えるか

Claudeが何かを間違えたとき、最初の本能はつまみを回すことではなく、自分が与えたコンテキストを点検することで
あるべきだ。プロンプトが曖昧すぎないか。Claudeは正しいツールに接続されているか。適切なスキルを備えているか。
必要ないはずのタスクでエフォートを上げているなら、直すべき場所はたいてい上流 — コンテキスト、`CLAUDE.md`、
あるいはタスクの切り方 — にある。

明確なコンテキストを与えたうえでなおClaudeが間違えたなら、こう問う。**十分に頑張らなかったのか、それとも
十分に知らなかったのか。**

### モデル:問題が難しすぎた

問題が本当に難しいときは大きいモデルを選ぶ。微妙なバグ、不慣れなドメイン、アーキテクチャの判断といったものだ。
どれだけコンテキストを与えても小さいモデルが自信を持って間違える状況では、大きいモデルが助けになる。大きい
モデルは曖昧さの扱いにも優れている。一方、小さいモデルでは実行を導く具体的な指示のほうが成功のレシピとして
優れている。

作業が定型的なときは小さいモデルを選ぶ。正確に記述できる編集、機械的な変更、すでにコンテキストにあるコードに
ついての質問などだ。タスクが必要としない能力に対価を払う理由はない。Claudeが関連コンテキストをすべて持ち、
明らかに試みたうえで間違えたなら、大きいモデルを選ぶ合図だ。大きいモデルを使っていて、しばらく作業が定型的
だったなら、下げれば速度が上がり、たいていコストも下がり、出力品質には影響しない。

### エフォート:Claudeが十分に頑張らなかった

ファイルを飛ばした、テストを実行しなかった、自分の作業を二重に確認しなかったことでClaudeが間違えたなら、
エフォートレベルを上げる。モデルの既定値より低いエフォートを選んでいた場合に特に当てはまる。

## Fable、Opus、Sonnet:スペシャリスト、エキスパート、ジェネラリスト

二つの設定の関係を捉える一つの見方。**Fable**はほとんど誰も見たことのない問題を見てきたスペシャリスト、
**Opus**はエキスパート、**Sonnet**はとても優秀なジェネラリストだ。エフォートレベルは、そのうちの誰であれ
あなたのタスクにどれだけの時間を費やすかを決める。

**低エフォートのOpus**は、あなたのものと似た問題に深い経験を持つエキスパートと5分間だけ話すようなものだ。
彼らはあなたのコードベースのどこにもない知識をもたらす。以前に見たパターン、確認すべき落とし穴、似た問題を
数多く解いてきた者だけが持つ類のものだ。ただし5分というのは、コードを丁寧に読む時間ではなく、ざっと読む
時間である。

**高エフォートのSonnet**は、とても優秀なジェネラリストに午後をまるごと渡すようなものだ。すべてを読み、実際に
動かし、自分の作業を二重に確認し、最終的にあなた固有のコードを徹底的に理解する。相対的に薄いのは、「これは
まさに前に見たことがある」という認識のほうだ。

**低エフォートであってもFable**は、皆が行き詰まっている問題をちらりと見ただけで、それでも誰も気づかないもの
を言い当てるスペシャリストだ。その認識こそがあなたが最も高く支払っているものなので、本当に必要なタスクの
ために取っておく価値がある。

どれかが普遍的に優れているわけではない。モデル設定はおおよそ**どれだけ有能か**であり、エフォート設定は
おおよそ**どれだけ徹底するか**である。現実のタスクの多くは、その両方をいくらか必要とする。

## エフォート、モデル、トークン消費

三者がどう相互作用するかはタスクによる。

**同じエフォートレベルでの定型作業**では、どちらのモデルもたいてい正解にたどり着く。大きいモデルは追加の検証
ステップでより多くのトークンを、より高い単価で消費する。定型的な区間で小さいモデルに落とすことが、品質を
損なわずに実際のコストを節約する理由がこれだ。

**より難しい複数ステップの作業**では方程式が変わる。小さいモデルは自らの能力の限界に向かって反復を燃やしながら
進むしかない一方、大きいモデルはより少ないステップで同じ品質水準に到達する。大きいモデルはトークン単価が高い
が、小さいモデルを本当に限界まで引き伸ばすタスクでは、タスクあたりの総コストのほうが低く出ることがある。さらに
重要なのは、大きいモデルは小さいモデルがどんな高エフォート設定でも達成できないタスクを達成できるという点だ。

これはFableで最も顕著になる。長く複数ステップにわたる作業でこそ最も大きく抜け出し、テストではOpusとSonnetが
どのエフォートレベルでも到達できなかった仕事を完了させた。トークン単価も最も高く、それが本当に必要な作業の
ために取っておくもう一つの理由である。

エフォートレベルはClaudeがその曲線をどこまで進む用意があるかを選ぶが、タスクを完了するために実際にそこまで
進む必要があるという意味ではない。

もう一つのニュアンス。**エフォートはトークン消費の形を決めるが、上限を課すわけではない。** システム内で唯一の
ハードキャップは `max_tokens` であり、到達すると応答をストリーミングの途中で切り落とす。これは鈍い道具で、
主にAPI開発者に関係する。タスクの予算や、プロンプトで簡潔にするよう頼むといった、より柔らかい制御のほうが
役に立つ。それらはモデルが従うよう訓練されたガイダンスとして働き — 上限に近づけばタスクを締めくくろうとする —
ぶつかる壁ではない。

## まず既定値から始め、それからつまみに手を伸ばす

ほとんどの場合、どちらの設定についても考えていないのが望ましい。結果が的を外したときにこう問う。**Claudeは
十分に知らなかったのか、十分に頑張らなかったのか。** そして、それに応じて調整する。
