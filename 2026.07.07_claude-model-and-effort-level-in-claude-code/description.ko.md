## 이 글이 뭔가요
Claude Code 팀의 Lydia Hallie가 "답을 더 좋게 만드는 것처럼 보이는" 두 설정, 즉 모델과 effort level이 실제로 무엇을 바꾸는지를 설명한다. 모델 설정은 당신의 요청을 어떤 고정 가중치 세트가 처리할지를 바꾸고, 출력 토큰 하나의 비용을 정한다. effort level은 프롬프트와 함께 요청의 일부로 모델에 전달되며, Claude가 작업을 끝났다고 간주하기 전에 얼마나 철저하고 확신해야 하는지를 설정한다. 얼마나 오래 생각하는지, 몇 개의 파일을 읽는지, 얼마나 검증하는지, 여러 단계 작업을 당신에게 확인하기 전까지 얼마나 밀고 나가는지가 여기에 포함된다.

글은 그 메커니즘 — 토큰화, 가중치, 한 번에 한 토큰씩 생성하는 루프, 컨텍스트로 유도하는 것이 왜 가르치는 것이 아닌지, 환각이 왜 조회 실패가 아니라 가중치가 그럴듯해 보이는 시퀀스를 만들어내는 것인지 — 을 훑은 뒤, 이를 실무 규칙으로 바꾼다. 결과가 기대에 못 미치면 먼저 당신이 제공한 컨텍스트를 확인하라. 컨텍스트가 명확했는데도 틀렸다면, *충분히 열심히 하지 않은 것*(effort를 올린다)인지 *충분히 알지 못한 것*(더 큰 모델을 고른다)인지를 물어라.

## 언제 유용한가요
- Claude Code 세션이 틀렸거나 얕은 결과를 냈고, 본능적으로 다이얼에 손이 갈 때.
- 작업마다 정하는 대신 팀이나 특정 영역을 위한 상시 effort 선호를 정할 때.
- 길게 이어지는 일상적 작업 구간을 품질 손실 없이 작은 모델로 낮출 수 있는지 판단할 때.
- 프롬프트의 컨텍스트가 왜 모델이 아는 것을 바꾸지 못하는지 동료에게 설명할 때.
- 비용을 따질 때. 주어진 작업 형태에서 "토큰당 더 유능함"과 "전체 토큰이 더 적음" 중 무엇이 이기는지.
- 출력이 원하는 것보다 길어서 `max_tokens`가 올바른 레버인지 궁금할 때(대개 아니다).

## 핵심 포인트
- **모델 선택은 고정된 가중치 세트, 즉 모델의 전반적 능력 범위를 고르는 일이다.** 컨텍스트는 예측을 유도할 뿐 가중치에 무언가를 더하지 않는다.
- **effort는 단순한 생각 시간이 아니다.** 읽는 파일, 사용하는 도구, 당신에게 다시 확인하기까지의 단계 수를 포함해 전체 작업량을 통제한다.
- **모든 종류의 출력은 같은 종류의 토큰이다.** 생각, 도구 호출, 당신에게 보내는 텍스트가 모두 같은 루프에서 나오고 같은 요율로 과금된다. 생각은 그 턴 동안 컨텍스트에 남아, Claude가 코드 작성으로 넘어가면 입력이 된다.
- **effort는 요청과 함께 전달된다.** 모델은 각 effort 수준을 이해하도록 학습됐고 그 행동은 고정 가중치에 새겨져 있다. 같은 프롬프트라도 높은 effort는 더 높은 확신의 답에 도달하기 위해 약 7배의 토큰을 생성할 수 있다.
- **계획은 맹목적으로 실행되지 않고 수정된다.** 가설이 셋인 디버깅 계획의 1단계에서 버그를 찾으면 Claude는 보통 그렇게 말하고 나머지를 건너뛴다. 높은 effort가 단순한 작업의 사용량을 인위적으로 부풀리지는 않는다. "과잉 사고"는 효과를 떨어뜨리기 때문에 학습 과정에서 면밀히 관리된다.
- **다이얼보다 컨텍스트를 먼저 확인하라.** 필요 없을 작업에 effort를 올리고 있다면 해결책은 대개 상류에 있다. 프롬프트, `CLAUDE.md`, 도구, 스킬, 혹은 작업 범위 설정이다.
- **진단.** 파일을 건너뛰고, 테스트를 돌리지 않고, 리팩터링을 중간에 그만뒀다면 → effort를 올린다. 컨텍스트가 있었고 분명히 시도했는데도 자신 있게 틀렸다면 → 더 큰 모델.
- **더 큰 것이 기본 답은 아니다.** 정확히 서술 가능한 일상적 작업은 작은 모델의 몫이다. 큰 모델은 모호함, 미묘한 버그, 낯선 도메인, 아키텍처 결정에서 값을 한다.
- **스페셜리스트 / 전문가 / 제너럴리스트.** Fable은 다른 누구도 거의 못 본 문제들을 봐온 스페셜리스트, Opus는 전문가, Sonnet은 아주 좋은 제너럴리스트이며, effort는 그들 중 누구든 얼마나 시간을 쓸지를 정한다. 모델은 대략 *얼마나 유능한가*, effort는 대략 *얼마나 철저한가*다.
- **비용은 작업 형태에 따라 뒤집힌다.** 같은 effort의 일상 작업에서는 작은 모델이 품질 손실 없이 비용을 아낀다. 더 어려운 여러 단계 작업에서는 큰 모델이 더 적은 단계로 기준에 도달하므로 작업당 총비용이 더 낮게 나올 수 있고, 작은 모델이 어떤 effort로도 못 하는 작업을 해낼 수 있다.
- **effort는 토큰 소비의 형태를 잡을 뿐 제한하지 않는다.** 유일한 하드 캡은 `max_tokens`로, 스트리밍 도중 잘라낸다. 작업 예산이나 간결함 요청은 모델이 따르도록 학습된 지침이지 벽이 아니다.
