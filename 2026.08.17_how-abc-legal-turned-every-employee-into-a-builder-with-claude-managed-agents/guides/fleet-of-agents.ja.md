# ガバナンスの効いたエージェント艦隊を展開する

ABC Legal が、散在するデスクトップ自動化から 50 以上の本番エージェントへ移行した過程。そしてその大半を、ソフトウェア開発者ではない人々が作ったという話。

## 出発点の課題

ABC Legal は従業員 1,100 名の米国の法務文書配達企業です。CTO の Brandon Fuller が Claude Enterprise を展開すると、導入は自然に進みました。送達（service of process）、電子提出（eFiling）、出廷代理オペレーションに加え、マーケティング・コンプライアンス・財務まで、頼まれてもいないのに各チームが自動化を作り始めたのです。

> 「ユーザーが本当に殺到しました。コネクタとツールの使いやすさを見るなり、突然、組織のあちこちで、これまで一日を食いつぶしていた作業を自動化する人たちが現れたんです。」

どの CTO も望む導入の姿ですが、問題が始まるのもここです。**初期のエージェントは、作った人が置いた場所にそのまま存在していました。個人のデスクトップ上のスケジュールタスクとして。** つまり無人での実行ができず、何が作られたのかを見る単一のビューがなく、いくらかかっているのか、昨夜動いたのかを誰も知りませんでした。

Claude Managed Agents への移行によって、会社は共通のデプロイ構造、共有ワークスペース、単一の監査・課金面、そして個人のノート PC ではなくクラウドで常時稼働するエージェントを手に入れました。

2026 年 7 月時点:

- Managed Agents で構築した本番稼働エージェント **50 以上**
- 一部エージェントが担う人手作業のコストを、本格的な最適化前でも **最大約 50% 削減**
- 全部門で **約 310 名** が日常業務に Claude を使用

## 原則 1 — すべてのエージェントをソフトウェアとして扱う

> 「エージェントは実のところ構造化されたテキスト、つまりプロンプトと設定にすぎません。テキストであるものは何でも、全社が見てレビューし改善できるリポジトリに置けます。」

エージェントのプロンプト、ツール一覧、スケジュール、認証情報、メモリは、すべて会社のソフトウェアと同じ git リポジトリの設定ファイルに入ります。**エージェントについて何かが変わるのは、誰かが承認したプルリクエストを通じてのみです。** これによりすべてのエージェントがバージョン履歴、コードレビュー、ロールバック、監査証跡を持ちます。

## 原則 2 — まずスターターキットを作る

Fuller は 1 週間かけてスターターキットを作りました。専用の git リポジトリに置かれた 2 つのテンプレートです。

- **イベント駆動エージェント** — 新しいジョブが届く、裁判所から文書が返ってくるなど、何かが起きた瞬間に始動します。
- **スケジュールエージェント** — タイマーで実行されます。毎時、毎日、または毎週。

各エージェントは標準構造を持つ自分のフォルダに置かれます。**JSON の設定ファイル、Markdown のシステムプロンプト、デプロイスクリプト、運用ドキュメント。** main ブランチに変更をマージすると、エージェントが自動的にデプロイされます。

ビルダーの経路は意図的に短くしてあります。リポジトリをクローンし、スターターテンプレートをコピーし、Claude Code にエージェントが何をすべきかを伝えれば、必要なもの一式 — 設定、プロンプト、認証情報ストア、メモリ — が返ってきます。**ビルダーはソフトウェアを書く必要が一切ありません。**

## 原則 3 — 非開発者が出荷できることを証明する

Fuller は社内の 15 名のステアリングコミッティ — 財務・マーケティング・オペレーション・開発から集まり、**ソフトウェア開発者はゼロ** — を集め、リポジトリをクローンして Claude Code でエージェントを構築させました。

狙いは、非開発者が自力で本番エージェントを構築できると示すことでした。すべてのエージェントが開発チームを経由しなければならないなら、そのボトルネックが全社の速度の上限になります。安全だった理由は、彼らがソフトウェアを書いていなかったからです。設定とプロンプトを埋めただけで、ランタイムは Managed Agents が供給しました。

> 「PR とは何かを説明する必要がありました。開発者でない人の多くは、走るほうの、自己ベストみたいな意味だと思っていたんです。いまでは互いにプルリクエストを送り合っています。」

1 週間で、15 名全員が動くエージェントを持ちました。そのビルダーたちが自分のチームに戻って他の人を教えました。**1 か月でおよそ 50 以上のエージェントが稼働していました。** それぞれに名前と所有者、そして 1 つの役割があります。

## 艦隊が担っていること

ABC Legal は現在、法務提出プロセスとその周辺オペレーションのほとんどの段階にエージェントを置いています。

- **AI Code Reviewer** — 4 つのコードベースのすべてのプルリクエストをマルチモデル解析でレビューし、セキュリティバグ、性能リグレッション、コミットされた認証情報を検出します。エンジニアはマージ前にこのレビューを待つようになりました。
- **EvidenceChain™ Delivery Agent** — アカウントマネージャーが毎週手作業でしていた仕事を引き継ぎました。条件に合うジョブのデータベースレポートを取得し、エージェントに組み込まれたブラウザで各 PDF を取得し、毎日顧客の FTP サーバーへ届けます。設定したアカウントマネージャーは自動化の経験が一度もなく、Claude Code に説明する形で約 1 時間で構築しました。
- **eFiling Rejection Diagnoser** — 裁判所が提出を却下すると自動で起動し、ジョブ詳細を読み、裁判所の規則を確認して、約 1 分で Slack に診断を投稿します。以前は従業員の 1 日のうち数時間を消費していた作業です。
- **ジョブ検証エージェント** — ブラウザで裁判所のウェブサイトを操作し、審理や事件が適切に提出され、記載された日付に実際に行われることを確認したうえで、管轄・裁判所・時効期間をフラグしながらジョブを調整します。
- **Attorney Coverage Agent** — 弁護士ネットワークに働きかけて審理のカバーを確保します。空き状況を確認し、メールを送り、空きと価格に関する返信を読んでコーディネーターがカバーを確定できるようにします。
- **AR 送金エージェント** — 送金メールを解析し、NetSuite の入金適用ファイルを作成し、ワンクリック承認のため Slack に投稿してからインポートします。別の日次エージェントが、エンジニアリングチケットごとに資産計上か費用計上かの判定を出します。
- **Google 広告アナリスト** — チャネル責任者向けに週次の推奨を投稿します。
- **Charvis** — 完了した送達ジョブをレビューし、コンプライアンスチームと約 **98%** 一致します。
- **Service-Overdue-Nudger** — 運用バックログのティア 1 層、つまり人がやるであろう反復的な一次対応を担い、人の承認用に段階別の日次アウトリーチ文面を起草します。

## 原則 4 — 収集し、調整し、繰り返す

エージェントは人の監督下で働き、何をしたか・何を推奨するかを Slack に投稿します。人はスレッドで返信し、絵文字でリアクションします。社内のコードレビューエージェント **Hank** はすべてのレビューを共有チャンネルに投稿し、対象のプルリクエストと結果の件数を明示するので、エージェントが何を判断したかの軌跡は公開され検索可能です。

そのリアクションデータは、集める仕組みがなければ無駄になる学習シグナルです。**すべてのエージェントに必要なわけではありません。** 艦隊の大半は誰も採点しない単一タスクのランナーで、単独で動きます。

採点付きのフィードバックを実際に集めるエージェントには、ABC Legal は **3 ロールのアーキテクチャ** を使います。1 つのワークスペース・環境・認証情報ボールトを共有しつつ、異なるスケジュールで走る別々のエージェントです。

| ロール | 実行頻度 | 何をするか |
|---|---|---|
| **Initial Agent** | リアルタイム | ジョブが来た、文書が戻ったタイミングで作業し、各アクションの監査証跡を記録 |
| **Harvester** | 毎時または毎日 | Slack から人のフィードバック（スレッド返信と絵文字リアクション）を集め、それぞれをラベル付きデータポイントに変換 |
| **Tuner** | 週次 | 全体を一度に見渡し、**モデルの重みではなく** プロンプトや設定の変更を提案。起草のみで、人がレビューしてプルリクエストをマージ |

このパターンは Slack のメッセージを、バージョン管理され人が承認したエージェントの変更に変えます。エージェントは、開発者がすでに使っているのと同じワークフローで改善されます。

### 「deliveries-as-code」: 4 エージェントの変形

同じループは、プロンプトだけでなくビジネス設定も調整します。ABC Legal の 50 名規模の姉妹会社 Docketly では、業務がデリバリー単位で組織され、各デリバリーがルーティングと処理の独自ルールセットを持ちます。**約 145 のルールセットはすべて、管理画面のレコードではなく git 上の単一 YAML ファイル** なので、デリバリーの調整とはファイルを編集してプルリクエストを開くことを意味します。

4 つのエージェントがループを構成します。1 つが週次の判定を Slack に投稿し、Harvester がリアクションをラベルに変え、Tuner が YAML にプルリクエストを開き、4 つ目のエージェントがマージ済み設定を本番データベースへ反映します。この 4 つ目は、人がすでにレビューし承認したものだけを実行します。

実際、誤ルーティングされたデリバリーを指摘した絵文字リアクションが、その週のうちにそのデリバリーのルーティング規則のマージ済み変更になり得ます。**ループの中で手作業なのはレビューだけです。**

## ランタイムの選定

Fuller は複数のフレームワークを評価したうえで、組織のエージェンティック・ハーネスとして Claude Managed Agents を選びました。基準は具体的でした。バージョニング、観測可能なセッション、ワークスペース単位の課金、モデル選択、メモリのプリミティブ、MCP 配線、そして最も重要な点として **世話の要らないインフラであること。**

責任の分担はきれいに対応します。

| マネージドプラットフォームが持つもの | ABC Legal が持つもの |
|---|---|
| 実行ループ | プロンプト |
| セッション | ツール一覧 |
| メモリ | トリガーロジック |
| コンソール | 監査証跡 |
| モデル | 成果に対するフィードバックループ |

規模の面で特に効いた機能:

- **バージョニング** — プッシュごとに楽観的ロック付きの新しいエージェントバージョンが作られます。ロールバックは容易です。
- **モデルの柔軟性** — 多くのエージェントは Claude Sonnet を既定に、大量・高速なタスクには Claude Haiku、より深い推論がコストに見合う場合は Claude Opus。モデルの入れ替えは 1 行の変更です。
- **MCP 配線と認証情報ボールト** — エージェントは ABC Legal 自身のプラットフォーム（100 を超えるツールが利用可能）、レポーティング用の Metabase、人間介在のための Slack、プロジェクト管理の Atlassian に接続します。
- **スケジュールデプロイ** — 反復エージェントは Bitbucket Pipelines の cron スケジュールで実行され、リポジトリアクセス・シークレット・課金はすでにそこで処理されています。

## 計測されるコスト

ABC Legal は AI 支出の 1 ドルまでを、ベンダー・ツール・チーム・ユースケース別に追跡しています。春を通じて艦隊が本番稼働する中で支出は上昇し、その後 **7 月には利用が伸び続ける中で下がり始めました。** 下記の効率化作業の結果です。

コストへの姿勢は意図的です。リターンが計測できる垂直的・運用的なツールとエージェントへ支出を寄せ、水平的なチャットとアイデア出しの利用は広く保ちつつコストは抑えます。

**指標は効率比です。エージェントが生む価値を、運用コストに対して測ります。** すべての Managed Agent が実行ごとに自身の価値を時間と金額でデータウェアハウスへ報告します。エージェントは **J カーブ** を描きます。新しく大きなモデルで走っている間は赤字で始まることが多く、チームが eval を書き、より安く速いモデルへ移し、トークンを削るとプラスに転じます。

## 獲得される信頼

大半のエージェントは人が介在した状態で始まります。エージェントがジョブやチケットを見て推奨を出し、人がレビューするまで何も実行されません。推奨はジョブに保存されてバナーで示され、担当者が自分の作業の流れの中で受け入れるか却下するか、あるいは Slack チャンネルに投稿されてスレッドで議論されます。

その反応が良い判断と悪い判断のラベル付きデータセットを作り、ハーベスタとチューナのループに供給され、チームが eval を書きフロンティアモデル間でエージェントをベンチマークできるようにします。**その特定のタスクで人と同等かそれ以上だと示して初めて、エージェントは自動モードに移り自ら行動します。** その後も同じ計測フレームワークの中に留まり、性能の変化が監視されます。

## Fuller の実務原則

- **すべてをコードとして考える。** *「コードは単なる構造化されたテキストです。LLM はテキストのエンジンです。ビジネスのうちリポジトリのテキストに変換できる部分が多いほど、エージェントが与えるレバレッジは大きくなります。」* これは従来のソフトウェアだけでなく、プロンプト、スキーマ、ディスパッチ規則、通知テンプレート、業務設定にも等しく当てはまります。
- **人を介在させた状態から始める。** すべてのエージェントは人のレビュー用に推奨を投稿することから始まります。人の判断と一貫して一致することを示して初めて、単独で動く権利を得ます。*「すべてのエージェントは、単独で動く前に信頼を勝ち取ります。最初から与えられてはいません。」*
- **PR をコントロールサーフェスとして使う。** *「エージェントを意思決定に関わらせたいなら、その決定をプルリクエストの形にしなさい。」* 行単位のコメント、承認ワークフロー、不変の監査証跡はバージョン管理に無料で付いてきて、AI レビューと人のレビューの双方に自然に組み合わさります。
- **フィードバックループに投資する。** ハーベスタ・チューナのパターンにより、エージェントは再学習なしに改善します。Slack の返信と絵文字リアクションが構造化されたシグナルとなり、人がすでに使っているのと同じプルリクエストのワークフローを通じてプロンプトと設定の変更へ還ります。
- **スケジュールタスクの回り道は飛ばす。** ABC Legal は Managed Agents へ移る前に、スケジュールタスクとローカルルーチンの構築に実際の時間を費やしました。製品がベータで出たばかりだったことが大きな理由です。今日の Fuller の助言は、最初から Managed Agents に行けというものです。
- **AI のハードルではなく git のハードルを見込む。** 難しかったのは、AI そのものよりも、業務ユーザーがリポジトリのクローンと Git・プルリクエストに慣れることでした。うまくいったし、速かったものの、本物のハードルであり、Fuller はツール側でこれがもっと容易になることを望んでいます。
- **すべてのタスクにエージェントの価値があるわけではない。** コストは実在するので、どのチームもコスト対価値で考える必要があります。本当に時間を節約する、あるいは自動化を生む、扱える問題を選ぶこと、そして「このタスクにエージェントは見合わない」と言えることが仕事です。

## 次に来るもの

艦隊は成長を続けています。進行中のプロジェクトには、送達写真のレビューエージェント、PagerDuty のトリアージエージェント、日次 KPI ダイジェスト、既存エージェントへの Tuner ループの拡張があります。チームはさらに「X as code」の候補も探しています。通知テンプレート、イベントルーティング規則、ディスパッチロジックなど、エージェントが読み、推論し、改善を提案できるリポジトリへ移せるものです。

> 「私たちは、AI が自走できるビジネスを支え、従業員はそれを操縦することに専念できる状態を望んでいます。」— Brandon Fuller, CTO, ABC Legal
