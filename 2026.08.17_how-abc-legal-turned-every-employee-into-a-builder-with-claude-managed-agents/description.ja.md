## この記事について
従業員 1,100 名の米国の法務文書配達企業 ABC Legal の顧客事例を、CTO の Brandon Fuller の語りを中心に伝える記事です。Claude Enterprise を展開すると各チームが自発的に自動化を作り始めましたが、初期のエージェントは個人のデスクトップ上のスケジュールタスクとして散在していました。Claude Managed Agents へ移行したことで、共通のデプロイ構造、共有ワークスペース、単一の監査・課金面、そして個人のノート PC ではなくクラウドで常時稼働するエージェントが手に入りました。

2026 年 7 月時点で、本番稼働のエージェントは 50 以上、一部のエージェントが担う人手作業のコストは本格的な最適化前でも最大約 50% 削減、全部門でおよそ 310 名が日常業務に Claude を使用していると集計されています。

記事の主題は運用モデルです。すべてのエージェントをコードとして定義し、非開発者にプルリクエストで出荷する方法を教え、Slack のリアクションをマージ済みのプロンプト変更に変えるフィードバックループを閉じること。

## どんなときに役立つか
- AI 導入の熱意はあるのに散在しているとき。自動化が個人のノート PC 上にあり、何が存在し、いくらかかり、昨夜動いたのかを見る共通の場がないとき。
- 開発チームをボトルネックにせず、非開発者に本番自動化を作らせたいとき。
- エージェントに管理画面ではなく、バージョン履歴・コードレビュー・ロールバック・監査証跡が必要なとき。
- エージェントの出力に対する人間のフィードバックはあるのに、それを改善に変える仕組みがないとき。
- そもそもどの業務にエージェントを充てる価値があるのかを、説明可能な形で判断する必要があるとき。

## 主なポイント
- **すべてのエージェントをコードとして定義する。** 「エージェントは実のところ構造化されたテキスト、つまりプロンプトと設定にすぎません。テキストであるものは何でも、全社が見てレビューし改善できるリポジトリに置けます。」プロンプト、ツール一覧、スケジュール、認証情報、メモリのすべてが、会社のソフトウェアと同じ git リポジトリの設定ファイルに入ります。承認されたプルリクエストを経ずに変わるものは何もありません。
- **1 週間で作ったスターターキットが普及の決め手でした。** 専用の git リポジトリに置かれた 2 つのテンプレート — イベント駆動エージェント用と、スケジュール実行エージェント用。各エージェントは標準構造を持つ自分のフォルダに置かれます。JSON 設定ファイル、Markdown のシステムプロンプト、デプロイスクリプト、運用ドキュメント。main ブランチへのマージで自動デプロイされます。ビルダーはリポジトリをクローンし、テンプレートをコピーし、エージェントが何をすべきかを Claude Code に伝えるだけで、設定・プロンプト・認証情報ストア・メモリが返ってきます。
- **非開発者こそが証明でした。** 財務・マーケティング・オペレーション・開発から集まった 15 名のステアリングコミッティ（ソフトウェア開発者はゼロ）がリポジトリをクローンし、Claude Code でエージェントを構築しました。1 週間で 15 名全員が動くエージェントを持ち、そのビルダーたちが自分のチームを教育して、1 か月で 50 以上のエージェントが稼働しました。各エージェントには名前と所有者、そして 1 つの役割があります。
- **難しかったのは AI ではなく git でした。** 「PR とは何かを説明する必要がありました。」業務ユーザーがリポジトリのクローンとプルリクエストに慣れることが、本当のハードルでした。
- **エージェントは Slack で監督され、そのリアクションが学習シグナルになります。** 出力を人が評価するエージェントには 3 ロールのアーキテクチャを使います。1 つのワークスペース・環境・認証情報ボールトを共有しつつ、異なるスケジュールで走ります。Initial Agent はリアルタイムで作業し、各アクションの監査証跡を記録します。Harvester は毎時または毎日実行され、スレッド返信と絵文字リアクションをラベル付きデータポイントに変えます。Tuner は週次で実行され、モデルの重みではなくプロンプトや設定の変更をプルリクエストとして提案し、人がレビューしてマージします。すべてのエージェントに必要なわけではありません。艦隊の大半は誰も採点しない単一タスクのランナーです。
- **「X as code」は一般化します。** 姉妹会社 Docketly では、約 145 のデリバリールールセットが管理画面のレコードではなく git 上の単一 YAML ファイルなので、デリバリーの調整はファイルを編集して PR を開くことを意味します。4 つのエージェントがループを構成し、4 つ目はマージ済み設定を本番データベースへ反映します。人がすでに承認したものだけを実行します。誤ルーティングを指摘した絵文字リアクションが、その週のうちにマージされたルーティング規則の変更になり得ます。
- **プラットフォーム選定基準は具体的でした**: バージョニング、観測可能なセッション、ワークスペース単位の課金、モデル選択、メモリのプリミティブ、MCP 配線、そして世話の要らないインフラであること。Anthropic のマネージドインフラが実行ループ・セッション・メモリ・コンソール・モデルを持ち、ABC Legal がプロンプト・ツール一覧・トリガーロジック・監査証跡・成果のフィードバックループを持ちます。
- **コストは仮定せず計測します。** 指標は効率比（efficiency ratio）で、エージェントが生む価値を運用コストに対して測ります。すべてのエージェントが実行ごとに自身の価値を時間と金額でデータウェアハウスに報告します。エージェントは J カーブを描きます。新しく大きなモデルで動いている間は赤字でも、チームが eval を書き、より安く速いモデルに移し、トークンを削るとプラスに転じます。支出は春を通じて上昇し、7 月には利用が伸び続ける中で下がりました。
- **信頼は与えられるものではなく獲得するものです。** 大半のエージェントは人が介在した状態で始まり、ジョブ画面や Slack チャンネルに推奨を投稿します。その反応がラベル付きデータセットとなり、eval とフロンティアモデル間のベンチマークに使われます。その業務で人と同等かそれ以上だと示して初めて自動モードに移り、その後も同じ計測フレームワークの中に留まって性能変化を監視されます。
