## 이 글이 뭔가요
직원 1,100명 규모의 미국 법률 문서 송달 기업 ABC Legal의 사례를, CTO Brandon Fuller의 이야기를 중심으로 전하는 글입니다. Claude Enterprise를 배포하자 여러 팀이 스스로 자동화를 만들기 시작했지만, 초기 에이전트들은 개인 데스크톱의 예약 작업으로 흩어져 있었습니다. Claude Managed Agents로 옮기면서 하나의 배포 구조, 공유 워크스페이스, 단일 감사·과금 지점, 그리고 개인 노트북이 아닌 클라우드에서 항상 켜져 있는 에이전트를 얻었습니다.

2026년 7월 기준으로 프로덕션 에이전트 50개 이상, 일부 에이전트가 담당하는 인간 업무 비용을 본격적인 최적화 전에도 최대 약 50% 절감, 전 부서에 걸쳐 약 310명이 Claude를 일상 업무에 사용하는 것으로 집계되었습니다.

글의 핵심은 운영 모델입니다. 모든 에이전트를 코드로 정의하고, 비개발자에게 풀 리퀘스트로 배포하는 법을 가르치며, Slack 반응을 병합된 프롬프트 변경으로 바꾸는 피드백 루프를 닫는 것입니다.

## 언제 유용한가요
- AI 도입 열기는 높은데 흩어져 있을 때 — 자동화가 개인 노트북에 살고, 무엇이 있는지·비용이 얼마인지·어젯밤에 돌았는지 볼 수 있는 공통 화면이 없을 때.
- 개발팀이 병목이 되지 않으면서 비개발자가 프로덕션 자동화를 만들게 하고 싶을 때.
- 에이전트에 관리 화면이 아니라 버전 이력, 코드 리뷰, 롤백, 감사 추적이 필요할 때.
- 에이전트 산출물에 대한 사람의 피드백은 있는데 그걸 개선으로 바꾸는 메커니즘이 없을 때.
- 어떤 업무에 에이전트를 붙일 가치가 있는지 방어 가능한 방식으로 판단해야 할 때.

## 핵심 포인트
- **모든 에이전트를 코드로 정의합니다.** "에이전트는 사실 구조화된 텍스트, 즉 프롬프트와 설정일 뿐이고, 텍스트인 것은 무엇이든 회사 전체가 보고 리뷰하고 개선할 수 있는 리포지토리에 담을 수 있습니다." 프롬프트, 도구 목록, 스케줄, 자격증명, 메모리가 모두 회사 소프트웨어와 같은 git 리포지토리의 설정 파일로 들어갑니다. 승인된 풀 리퀘스트를 거치지 않고는 아무것도 바뀌지 않습니다.
- **일주일 만에 만든 스타터 킷이 확산의 열쇠였습니다.** 전용 git 리포지토리에 담긴 두 개의 템플릿 — 하나는 이벤트 구동 에이전트용, 하나는 스케줄 에이전트용. 각 에이전트는 표준 구조를 가진 자기 폴더에 삽니다. JSON 설정 파일, Markdown 시스템 프롬프트, 배포 스크립트, 운영 문서. main 브랜치에 병합하면 자동으로 배포됩니다. 빌더는 리포를 클론하고 템플릿을 복사한 뒤 Claude Code에 무엇을 할 에이전트인지 말하면 설정·프롬프트·자격증명 저장소·메모리를 받습니다.
- **비개발자가 그 증명이었습니다.** 재무·마케팅·운영·개발에서 모인 15명 운영위원회(소프트웨어 개발자는 한 명도 없음)가 리포를 클론하고 Claude Code로 에이전트를 만들었습니다. 일주일 만에 15명 전원이 동작하는 에이전트를 갖게 되었고, 이들이 각자 팀을 교육해 한 달 만에 50개 이상이 돌았습니다. 각 에이전트는 이름과 소유자, 그리고 하나의 역할을 가집니다.
- **어려운 건 AI가 아니라 git이었습니다.** "PR이 뭔지 설명해야 했습니다." 업무 사용자가 리포 클론과 풀 리퀘스트에 익숙해지는 것이 진짜 장벽이었습니다.
- **에이전트는 Slack에서 감독받고, 그 반응이 학습 신호가 됩니다.** 사람이 산출물을 평가하는 에이전트에는 3역할 아키텍처를 씁니다. 하나의 워크스페이스·환경·자격증명 저장소를 공유하되 서로 다른 주기로 실행됩니다. Initial Agent는 실시간으로 일하고 각 행동의 감사 추적을 남깁니다. Harvester는 매시간 또는 매일 실행되어 스레드 답글과 이모지 반응을 레이블된 데이터 포인트로 바꿉니다. Tuner는 매주 실행되어 모델 가중치가 아니라 프롬프트나 설정 변경을 풀 리퀘스트로 제안하고, 사람이 검토해 병합합니다. 모든 에이전트에 필요한 건 아닙니다. 함대 대부분은 아무도 채점하지 않는 단일 작업 러너입니다.
- **"X-as-code"는 일반화됩니다.** 자매회사 Docketly에서는 약 145개 배송 룰셋이 관리 화면의 레코드가 아니라 git의 단일 YAML 파일이라, 배송을 튜닝한다는 건 파일을 고치고 PR을 여는 일입니다. 네 개의 에이전트가 루프를 이루며, 그중 넷째는 병합된 설정을 프로덕션 데이터베이스로 밀어넣습니다. 사람이 이미 승인한 것만 실행합니다. 잘못 라우팅된 배송을 지적한 이모지 반응이 그 주 안에 병합된 라우팅 규칙 변경이 될 수 있습니다.
- **플랫폼 선정 기준은 구체적이었습니다**: 버저닝, 관측 가능한 세션, 워크스페이스 단위 과금, 모델 선택, 메모리 프리미티브, MCP 연결, 그리고 돌봐야 할 인프라가 없을 것. Anthropic의 관리형 인프라가 실행 루프·세션·메모리·콘솔·모델을 소유하고, ABC Legal이 프롬프트·도구 목록·트리거 로직·감사 추적·결과 피드백 루프를 소유합니다.
- **비용은 가정이 아니라 측정합니다.** 지표는 효율 비율(efficiency ratio)로, 에이전트가 만든 가치를 운영 비용에 견줍니다. 모든 에이전트가 실행마다 자기 가치를 시간과 금액으로 데이터 웨어하우스에 보고합니다. 에이전트는 J-커브를 그립니다. 새롭고 큰 모델을 쓰는 동안은 적자였다가, 팀이 eval을 작성하고 더 싸고 빠른 모델로 옮기고 토큰을 다듬으면 흑자로 넘어갑니다. 봄 내내 지출이 오르다가 7월에는 사용량이 계속 늘어나는 중에도 지출이 떨어졌습니다.
- **신뢰는 주어지는 게 아니라 얻는 것입니다.** 대부분의 에이전트는 사람이 개입한 상태로 시작해, 작업 화면이나 Slack 채널에 추천을 올립니다. 그 응답들이 eval과 프론티어 모델 간 벤치마크에 쓰이는 레이블 데이터셋이 됩니다. 해당 업무에서 사람만큼 또는 그보다 낫다는 걸 증명한 뒤에야 자동화 모드로 전환되며, 이후에도 같은 측정 프레임워크 안에 남아 성능 변화를 감시받습니다.
