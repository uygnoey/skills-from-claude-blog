## この記事について
JetBrains Agent Systems の CTO、Vladislav Tankov 氏へのインタビュー。新しく出たフロンティアモデルをどう評価し、自社のどのワークロードを移すかをどう決め、顧客に届く前にモデルの周囲へどんな安全策を置くかを扱う。JetBrains はアクティブユーザー 1,250 万人、Fortune Global 100 のうち 88 社を顧客に持つため、展開の判断は実際に重い。

一貫する論点は、公開ベンチマークのスコアは答えではなく仮説だということだ。JetBrains は自社モノレポを含むプライベートリポジトリで大規模な評価セットを回し、モデルの実挙動が公開スコアと一致するかを確かめ、リーダーボードを 3 つ（最高品質、最小タスク単価、最速）別々に保って、ワークロードごとに異なる勝者を選べるようにしている。

## どんなときに役立つか
- 新しいフロンティアモデルが出たとき、公開ランキングではなく自社コードに基づいて「導入すべきか」に答える必要があるとき。
- すべてに 1 つの既定モデルを決めるのではなく、ワークロードごとにモデルを選び分けるとき。
- 完了タスクあたりのコストで下すべき判断を、トークン単価の比較で下してしまっているとき。
- 安全性について自組織が負うべき責任と、モデル提供者に合理的に期待できる範囲を切り分けるとき。
- セキュリティレビューに耐えるデータ保持の立場が必要なとき。

## 主なポイント
- **プライベートリポジトリで評価する。** モデルが学習に使えたはずのない作業から、自社の規約とビルドシステムを抱えたタスクを選ぶ。Tankov 氏の警告は、公開ベンチマークで高得点を取るようチューニングされていて実タスクでは崩れるモデルがある、というものだ。
- **リーダーボードは 1 つではなく 3 つ** — 最高品質、最小タスク単価、最速。1 本にまとめると、作業を振り分けるのに必要な情報が失われる。
- **トークン単価ではなくタスク単価。** Claude Fable 5 はトークン単価は高いが、複雑で長時間かかる作業ではステップが少なく、タスクあたりのコストは低い。
- **報告された数値。** Python の合格率は 44.3% で、Opus 4.8 の 28.2% に対しておよそ 16 ポイント差。直接比較では、Fable 5 は Opus 4.8 が落とした Python タスクを 18 件解き、2 件を落とした。解決までのステップはおよそ 22% 少なかった。
- **「実行はできるが誤答」の割合に重みを置く。** Fable 5 のコードは実行できた場合にテストを通過する頻度がはるかに高かった。実行できるのに誤った答えを返すコードは、検出するのに最も高くつく失敗である。
- **ステップ数は習慣のシグナル。** ある Java タスクで旧モデルは必要のない外部リソースを繰り返し取りに行こうとした。Tankov 氏はこの差を、より広い意味でのエンジニアリング習慣の良さと読む。
- **置き換えではなくルーティング。** Opus は働き手として残る — 仕事をやり遂げるとかなり確信できる。Fable 5 は、本当に優れた推論が必要なとき、ほとんどパートナーが必要なときのために取っておく。何度も試して通らなかったリッチテキストエディタのコンポーネント、テキストと画像の仕様から IDE 的アプリケーションを実装したり既存アプリを別のランタイム・フレームワーク・言語へ書き換えたりする長時間のエージェンティック実行などだ。
- **安全性はハーネスの問題。** JetBrains は最も安全なモデルを自ら作ろうとはしない。提供者側のレッドチーミングで十分と考え、自社の労力はモデルを取り囲む安全網 — 体系的な展開、インフラ、ハーネス設計 — に注ぐ。
- **モデルを自社製品に向ける。** 外部の脅威アクターが同クラスのモデルを使ってくるという前提のもと、JetBrains のソフトウェアに対してホワイトボックスのセキュリティテストを行う。
- **データ保持の立場を明示する。** 選好はゼロ保持。最も深刻なフラグ付き事案の調査に限定した保持は公正なトレードオフとして受け入れる。それがなければ分類器がどこで誤作動したのかを知る手立てがないからだ。緊張関係も明示される — 攻撃的な分類器は防御的セキュリティ作業をより困難にする。
- **この先**は、モデルの能力よりもソフトウェア開発のためのコックピットとして語られる。エージェントと人が協働する空間、そしてガバナンスと投資対効果の明確さである。
