# フロンティアモデルの評価と展開

フロンティアモデルがリリースされるたびに、ツールベンダーは同じ判断を迫られる。このモデルは
*自社にとって* 優れているのか、どのワークロードを移すべきか、そして顧客に届く前にモデルの周囲で何が
担保されていなければならないのか。本稿の土台は、JetBrains Agent Systems の CTO である
Vladislav Tankov 氏へのインタビューで、JetBrains が Claude Fable 5 をどう評価し、どう展開したかを
扱っている。同社はアクティブユーザー 1,250 万人、Fortune Global 100 のうち 88 社を顧客に持つ。

## 出発点

興味深い変化は、モデルの品質が上がったことではなく、社内の議論が終わったことだ。かつて懐疑派が
いた組織が、AI は定着するという前提を当然のものとして受け入れる段階に達し、未解決の問いはその
一段下に移った。どのモデルを、どの仕事に、どんな安全策のもとで使うのか。

この捉え直しがあるからこそ、以下は一回限りの導入判断ではなく、繰り返し実行できるプロセスになる。

## 評価は自社リポジトリで

公開ベンチマークのスコアは仮説である。公開ベンチマークで高得点を取るようチューニングされていて、
実際のタスクでは崩れるモデルもある。だから評価の第一の役目は、その公開スコアが自社のコードベースと
接触しても生き残るかを確かめることだ。

そこから導かれる実践:

- **プライベートリポジトリを使ったプライベートな評価セット。** 社内モノレポも含める。モデルが学習に
  使えたはずのない作業から抽出し、自社の規約とビルドシステムをそのまま抱えたタスクであること。
- **ベンチマークの主張を実タスクで検証する。** 両者の差はそれ自体が、そのモデルがどうチューニング
  されたかを示す情報になる。
- **リーダーボードは 1 つではなく 3 つ** — 最高品質、最小タスク単価、最速。ワークロードごとに勝者は
  異なり、順位を 1 本にまとめると、作業を振り分けるのに必要な情報がまさに失われる。

タスク単価のリーダーボードは特に強調に値する。トークン単価が高くても、複雑で長時間かかる作業では
より少ないステップで答えに到達するため、結果的に安く済むことがある。トークン単価での比較は、
最も賭け金の大きいワークロードにおいて逆方向を指し示してしまう。

## 何を測るか

| 指標 | 何がわかるか |
|---|---|
| 言語別の合格率 | 差の大きさと、それがどこに集中しているか |
| 直接対決の勝敗 | 一様な底上げなのか、偏ったトレードなのか |
| 実行はできるが誤答の割合 | 最も高くつく失敗モードへの露出 |
| 解決までのステップ数 | コストの乗数であり、エンジニアリング的判断力の代理指標 |
| 完了タスクあたりのコスト | 実際にルーティングを支配する数字 |
| レイテンシ | エディタ内の対話的利用で決め手になる指標 |

JetBrains のこのラウンドでは、Claude Fable 5 が Python タスクの 44.3% を通過し、Opus 4.8 は 28.2%
だった。Fable 5 は旧モデルが落とした Python タスクを 18 件解き、2 件を落とし、解決までのステップは
およそ 22% 少なかった。

見出しの数字よりも注目すべき結果が 2 つある。第一に、Fable 5 のコードは実行できた場合にテストを
通過する頻度がはるかに高かった。実行はできるのに誤った答えを返すコードは、検出するのに最も高くつく
失敗である。レビュアーの注意を消費し、本番まで届きうるからだ。第二に、ある Java タスクで旧モデルは
必要のない外部リソースを繰り返し取りに行こうとし、新モデルはそれを省いた。Tankov 氏はこれを、より
広い意味でのエンジニアリング習慣の良さと読む。合格率では決して表に出ない種類の発見であり、
ステップ数を別立てで記録しておく理由でもある。

## 全面置き換えではなく、作業のルーティング

導入は置き換えではなかった。両モデルとも異なる役割で現役に残った。

- **Opus は働き手。** Tankov 氏の言い方では、仕事をやり遂げるとかなり確信できるモデルだ。推論の
  深さより確実性が効く、日常的で量の多い作業の既定値として適している。
- **道筋が見えないときは Fable 5。** 彼の言葉では、本当に優れた推論が必要なとき、ほとんどパートナーが
  必要なときのために取っておく。具体的には、何度か試して通らなかったリッチテキストエディタの
  コンポーネントを、あるテックリードがほぼ一発で仕上げた。
- **長時間のエージェンティックな実験。** エージェントがテキストと画像による仕様を受け取って高度な
  IDE 的アプリケーションを実装し、既存アプリから仕様を逆生成したうえで、ほぼブラックボックスに近い
  設定で別のランタイム・フレームワーク・言語へ書き換えることもする。

ルーティングの判断は固定せず、リリースごとに開き直す。

## 展開の構え: モデルではなくネットを作る

JetBrains はモデル自体をより安全にしようとはしていない。表明されている前提は、プロバイダー側で
行われたレッドチーミングとアライメント作業があれば、そのモデルは安全だと信じるに足るというものだ。
展開する側の仕事は **モデルを取り囲む安全網** である。モデルをいじるのではなく、インフラとハーネスの
設計によって安全性を担保する、体系的な展開のやり方だ。

取り入れる価値のある帰結が 2 つある。

**モデルを自社製品に向ける。** 外部の脅威アクターが同クラスのモデルを自社に向けて使うという明示的な
前提のもとで、自社ソフトウェアに対してホワイトボックスのセキュリティテストを行う。エンタープライズや
規制業種の顧客を抱えるベンダーにとって、その脆弱性を先に見つけることがすべてである。

**データ保持について明示的な立場を取る。** 表明された選好はゼロ保持だ。受け入れられた妥協は、最も
深刻なフラグ付き事案の調査に限定した保持である。それがなければ何が要求され、分類器がどこで誤って
作動したのかを理解する手立てがない、という理屈であり、フロンティアの知能へアクセスするための公正な
トレードオフとみなされている。緊張関係は隠されずに明示される — 攻撃的なコンテンツ分類器は、企業自身の
防御的セキュリティ作業をより困難にする。

## この先の方向

語られたロードマップはモデルの能力そのものより — それは改善し続ける前提だ — その周囲の面に関する
ものだ。ソフトウェア開発のためのコックピットのようなもの、エージェントと人が協働する空間、そして
開発プロセスに対する実質的なマネジメント。期待される成果は、開発者がエージェントを通じてより多く
より良いコードを届けること、非技術職がソフトウェア制作でより大きな役割を担うこと、そして組織が
ガバナンスと投資対効果の明確さを得ることである。
