# 프런티어 모델 평가와 배포

새 프런티어 모델이 나올 때마다 툴 회사가 마주하는 판단이 있다. 이 모델이 *우리에게* 더 나은가,
어떤 작업을 이 모델로 옮겨야 하는가, 고객에게 닿기 전에 모델 주변에서 무엇이 보장되어야 하는가.
이 글의 근거는 JetBrains Agent Systems CTO Vladislav Tankov와의 인터뷰로, JetBrains가 Claude Fable 5를
어떻게 평가하고 배포했는지를 다룬다. JetBrains는 활성 사용자 1,250만 명과 Fortune Global 100 중 88개
기업을 고객으로 둔 회사다.

## 출발점

흥미로운 변화는 모델 품질이 좋아졌다는 사실이 아니라, 사내 논쟁이 끝났다는 점이다. 한때 회의론자가
있던 조직이 이제는 AI가 계속 남으리라는 전제를 당연하게 받아들이고, 열린 질문은 그다음 단계로
내려왔다. 어떤 모델을, 어떤 일에, 어떤 안전장치 아래에서 쓸 것인가.

이 재구성 덕분에 이 글의 나머지는 일회성 도입 결정이 아니라 반복 가능한 프로세스가 된다.

## 평가는 우리 리포지토리에서

공개 벤치마크 점수는 가설이다. 어떤 모델은 벤치마크에 잘 나오도록 튜닝되어 있고 실제 작업에서는
무너진다. 그래서 평가의 첫 번째 임무는 그 공개 숫자가 우리 코드베이스와 만나고도 살아남는지를
확인하는 일이다.

그에 따르는 실천:

- **비공개 리포지토리 기반의 비공개 평가 세트.** 회사 모노레포를 포함한다. 모델이 학습했을 리 없는
  작업에서 뽑아, 우리 컨벤션과 우리 빌드 시스템을 그대로 안고 있는 태스크여야 한다.
- **벤치마크 주장을 실제 작업으로 검증한다.** 둘 사이의 격차는 그 자체로 모델이 어떻게 튜닝되었는지를
  알려주는 정보다.
- **리더보드는 하나가 아니라 셋** — 최고 품질, 최저 태스크당 비용, 최고 속도. 워크로드마다 승자가
  다르며, 순위를 하나로 합치면 정작 작업을 라우팅할 때 필요한 정보가 사라진다.

태스크당 비용 리더보드는 특히 강조할 만하다. 토큰당 비용이 더 비싸면서도 복잡하고 오래 걸리는
작업에서는 더 저렴한 선택이 될 수 있다. 더 적은 단계로 답에 도달하기 때문이다. 토큰 단가 비교는
하필 가장 판돈이 큰 워크로드에서 반대 방향을 가리킨다.

## 무엇을 측정할 것인가

| 지표 | 알려주는 것 |
|---|---|
| 언어별 통과율 | 격차의 크기와, 그 격차가 어디에 몰려 있는지 |
| 정면 승패 비교 | 균등한 상승인지, 한쪽으로 기운 교환인지 |
| 실행은 되지만 틀린 비율 | 가장 비싼 실패 모드에 대한 노출도 |
| 해결까지의 단계 수 | 비용 배수이자 엔지니어링 판단력의 대리 지표 |
| 완료 태스크당 비용 | 실제로 라우팅을 지배하는 숫자 |
| 지연 시간 | 에디터 내 대화형 사용에서 결정적인 지표 |

JetBrains의 이번 라운드에서 Claude Fable 5는 Python 태스크의 44.3%를 통과했고 Opus 4.8은 28.2%였다.
Fable 5는 이전 모델이 놓친 Python 태스크 18개를 풀었고 2개를 잃었으며, 해결까지의 단계는 약 22% 적었다.

헤드라인보다 더 눈여겨볼 결과가 둘 있다. 첫째, Fable 5의 코드는 실행됐을 때 테스트를 훨씬 자주
통과했다 — 실행은 되지만 틀린 답을 내는 코드는 잡아내기 가장 비싼 실패다. 리뷰어의 주의를 소모하고
프로덕션까지 갈 수 있기 때문이다. 둘째, 어떤 Java 태스크에서 이전 모델은 필요하지도 않은 외부 리소스를
반복해서 끌어오려 했고 새 모델은 그냥 건너뛰었다. Tankov는 이를 더 나은 엔지니어링 습관 전반의 신호로
읽는다. 통과율로는 절대 드러나지 않는 종류의 발견이며, 단계 수를 따로 기록해 둘 이유이기도 하다.

## 전면 교체가 아니라 작업 라우팅

도입은 대체가 아니었다. 두 모델 모두 서로 다른 역할로 현역에 남았다.

- **Opus는 일꾼.** Tankov의 표현으로는, 이 모델이 일을 해낼 것이라고 꽤 확신할 수 있다. 추론의 깊이보다
  확실함이 중요한 일상적이고 물량이 많은 작업의 기본값으로 적절하다.
- **경로가 보이지 않을 때는 Fable 5.** 그의 말로는 정말 좋은 추론이 필요할 때, 거의 파트너가 필요한
  수준일 때를 위해 남겨둔다. 구체적으로는, 여러 번의 시도에도 되지 않던 리치 텍스트 에디터 컴포넌트를
  한 테크 리드가 거의 한 번에 완성했다.
- **장시간 에이전틱 실험.** 에이전트가 텍스트와 이미지로 된 명세를 받아 정교한 IDE 같은 애플리케이션을
  구현하고, 기존 애플리케이션으로부터 명세를 역으로 생성한 뒤 거의 블랙박스에 가까운 설정에서 다른
  런타임·프레임워크·언어로 다시 쓰기도 한다.

라우팅 결정은 고정하지 말고 릴리스마다 다시 연다.

## 배포 태세: 모델이 아니라 그물을 만든다

JetBrains는 모델 자체를 더 안전하게 만들려 하지 않는다. 명시된 전제는, 공급자 쪽에서 수행한 레드팀
활동과 정렬 작업이 모델을 안전하다고 믿기에 충분하다는 것이다. 배포하는 회사의 몫은 **모델 주변의
안전망**이다. 모델을 손보는 대신 인프라와 하네스 설계로 안전을 보장하는 체계적인 배포 방식이다.

받아들일 만한 두 가지 귀결:

**모델을 우리 제품으로 겨눈다.** 외부 위협 행위자가 같은 급의 모델을 우리에게 쓸 것이라는 전제 위에서,
자사 소프트웨어를 대상으로 화이트박스 보안 테스트를 돌린다. 엔터프라이즈와 규제 산업 고객을 상대하는
벤더에게는 그 취약점을 먼저 찾는 것이 전부다.

**데이터 보존에 대한 입장을 명시한다.** 선호는 제로 보존이다. 받아들인 절충은, 심각도가 가장 높은
플래그 사례를 조사하는 용도로 보존을 한정하는 것이다. 그것 없이는 무엇이 요청됐는지, 분류기가 어디서
잘못 동작했는지 알 방법이 없다는 논리이며, 프런티어 지능에 접근하기 위한 공정한 절충으로 본다. 긴장은
숨기지 않고 명시된다. 공격적인 콘텐츠 분류기는 회사 자체의 방어적 보안 작업을 더 어렵게 만든다.

## 앞으로의 방향

설명된 로드맵은 모델 능력보다는 — 그건 계속 좋아진다고 전제한다 — 그 주변 표면에 관한 것이다.
소프트웨어 개발을 위한 일종의 콕핏, 에이전트와 사람이 함께 협업하는 공간, 그리고 개발 프로세스에 대한
실질적인 관리. 기대되는 결과는 개발자가 에이전트를 통해 더 많고 더 나은 코드를 내보내는 것, 비기술
직군이 소프트웨어를 만드는 데 더 큰 역할을 하는 것, 조직이 거버넌스와 투자수익에 대한 명확성을 얻는
것이다.
