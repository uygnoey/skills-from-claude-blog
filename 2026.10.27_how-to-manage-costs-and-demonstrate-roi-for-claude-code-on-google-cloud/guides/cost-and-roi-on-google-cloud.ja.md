# Google Cloud における Claude Code のコストと ROI: コントロール -> トラッキング -> 証明

Google Cloud で Claude Code を運用するプラットフォームチーム向けの Anthropic のガイダンスを、方法論として整理しました。

## 1. 請求額がこうなる理由
Google Cloud の Claude は従量課金です。導入が利用を生み、利用が支払いになり、価値もそこに現れます。
コスト = タスクあたりのトークン × モデル単価。エージェント型ツールはファイルを読み、ツールを実行し、
タスク全体を推論するため、チャットよりタスクあたりのトークンが多くなります。タスクに合ったモデル選びが
もう一つの大きな制御手段です。可視性は Claude apps gateway と Google Cloud のサービスから得られます。

## 2. ツールボックス
| レイヤー | 機能 |
|---|---|
| Google Cloud | プロジェクト単位の課金、予算とアラート、支出上限(Preview)、BigQuery エクスポート、割り当て(モデルファミリー・ロケーションごとの毎分リクエスト数と入出力トークン)、プロビジョンドスループット |
| Claude apps gateway | 同じ `claude` バイナリに含まれるセルフホスト型サービスでプロジェクト内で稼働。IdP サインイン(例: Google Workspace)で全リクエストに検証済み ID。グループごとのモデル許可リスト。ユーザー・IdP グループ・組織単位の日・週・月の支出上限 |

## 3. レバー1 ― コントロール
制限ではなく誘導します。高コストのセッションは価値の高い作業をするパワーユーザーであることが多く、
無駄は高額利用者の中間層(定型作業に高価なモデル、忘れられた定期タスク)にあります。
- **支出上限**: ユーザー・グループ・組織単位。グループと組織の上限は共有プールではなく、各メンバーが継承する1人あたりの既定値。
- **しきい値アラート**: 75% と 95% を超えると CLI 内で警告、上限ではリセットまたは引き上げまで 429。Cloud Billing のアラートは管理者向け。
- **既定モデルと許可リスト**: IdP グループごとにサーバー側で強制。ほとんどの人は既定のまま使います。
- **Gateway 管理 API**: チケットなどから上限をプログラムで変更。

## 4. レバー2 ― トラッキング
- Claude Code OpenTelemetry: セッション、アクティブ時間、コード行数、コミット、PR、トークン、コスト ―
  ユーザー・チーム・モデル別、さらにスキル・プラグイン・エージェント・MCP サーバー別。コレクターまたは
  gateway 経由で OTLP 送信。
- Gateway テレメトリ: 送信先を一つ設定すれば全員に適用。検証済みメールと IdP グループでタグ付け。
- `OTEL_RESOURCE_ATTRIBUTES`(例: `department=engineering,cost_center=eng-123`)で Cloud Monitoring・
  Grafana・Splunk にコストセンター別ビュー。
- ダッシュボード: アクティブ開発者、直近24時間のセッション、トークン、ブロックされたリクエスト
  (上限引き上げのチケットフローと組み合わせる)。「Claude Code Monitoring」テンプレートは Cloud
  Monitoring コンソールからコピー可能。
- OTel クイックスタート: Cloud Logging・Monitoring に加え、イベント種別ごと(API リクエスト、ツール判断、
  ツール結果、アシスタント応答、フック実行)のパーティション化された BigQuery テーブルと、開発者・
  モデル別支出、ツールの成功率と遅延、フック待ち時間、ターン・セッション分析用の SQL。
- Cloud Billing → BigQuery: モデルとトークン種別で Claude の SKU を絞り込み。

## 5. レバー3 ― 証明
| 観点 | 例 | データ源 |
|---|---|---|
| 導入と利用 | 有効化ユーザー、日次・週次利用、継続率、パワーユーザー | OTel |
| 満足度 | 満足感、体感の時間短縮、出力への信頼、摩擦 | 導入前後のアンケート + 定期チェックイン |
| インパクト | 時間(PR オープン -> マージ、レビュー所要時間)、労力(PR あたりのレビュー往復・コメント・手戻り)、量(エンジニアあたり PR、デプロイ頻度、名前の付いた成果) | ソース管理 + チケットのベースライン |

**作業単位**: 定義した種類のマージ済み PR(Claude が作成し、人が出荷を判断)を、ラベル、チケット ID、
Claude の関与で特定して数えます。PR でない作業は、完了した一つの成果をそれが記録される場所で数えます。

**ネイティブテレメトリ**: 受け入れ率、変更行数、コミット、作成 PR、ユーザーあたり PR、成果単位あたりの
コスト。作成された PR はマージされた PR ではないため、GitHub・GitLab やチケットと突き合わせます。
プロンプトのログ記録はオプトインで、PR 以外の価値(インシデントを調査する SRE、デモ用データを作る
セールスエンジニア)を示します。

## 6. 参考となる成果
- Delivery Hero: 100 個の UI コンポーネントにわたるデザインシステム刷新を、約1週間ではなく数分で。
- Shopify: エンジニア以外も社内ツールを数日ではなく数分で構築。
- Fifth Dimension: 月 30 万行超、受け入れ率 98%。

## 7. はじめに
継続的なループを回します。組織全体の支出上限、既定モデル、モデル許可リストから始め、データが集まるに
つれて役割・チームごとに調整し、指標を価値と結び付けて関係者に報告します。
