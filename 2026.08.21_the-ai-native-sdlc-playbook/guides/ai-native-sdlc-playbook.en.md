# The AI-native SDLC playbook

A guide to transforming a software development lifecycle stage by stage, from the Applied AI team's
practices at Anthropic and with its customers.

## Code is no longer the bottleneck

Organizations have started using AI to write code at a speed unthinkable a year ago, yet the
processes around the code have not changed at the same pace. The same approval gates, reviews,
handoffs, and policies remain, stalling the productivity gains agentic coding was supposed to
deliver.

The traditional SDLC — plan, design, build, test, deploy, maintain — was designed to maximize
efficiency in an era when writing and implementing code was the most time-consuming and expensive
stage. PRDs, estimation rituals, and product security reviews existed to force alignment during what
could be weeks or quarters of development work. Its controls also assume every step is performed by
humans.

When build collapses to hours, three things become true:

1. **The bottleneck moves to the steps on either side of build** — plan, review and test, deploy —
   which still run at human speed.
2. **The controls stop matching reality.** Reviewing each line by hand made sense when a person wrote
   it; it cannot keep up once agents write most of the diff.
3. **Governance costs increase**, because exceptions still route through meetings and committees that
   meet weekly or monthly.

Security is the clearest case. Security teams are sized for human output, so when agents multiply
code output, either the review queue builds or code ships under-reviewed. A regulated organization
cannot accept either outcome, so its security and policy checks have to keep pace with the agents.

## What an AI-native SDLC is

The AI-native SDLC combines the old control objectives with new enforcement. Instead of a linear
flow, the process becomes a loop with AI embedded at each point, and handover between stages is
automated rather than manual.

| Stage | Traditional SDLC | AI-native SDLC |
|---|---|---|
| Plan | Requirements gathered by committee, distilled through workshops and sign-offs, written up by hand | Claude synthesizes pain points straight from the sources and captures them in `intent.md`, which is human readable and machine actionable |
| Design | Spec written by analysts, parsed by designers | Requirements and design compressed into one working session with an agent, guided by standards encoded as skills, versioned in git |
| Build | Tests and code handwritten; documentation written after development | Tests and code generated by AI; institutional knowledge maintained as versioned, machine-readable `CLAUDE.md` files and skills |
| Test | QA gates at stage boundaries | Continuous evals woven through implementation |
| Deploy | Humans review every line; governance happens in review cycles, often inconsistently | Layers of agentic review, with human review reserved for regulated and critical code; governance enforced as the AI acts, with hooks as approval gates |
| Maintain | Humans watch production for bugs | Agents monitor live deployments; any breached control band is diagnosed and written back into the loop as a new `intent.md` |

Most organizations sit somewhere between the two columns.

### The committed artifact is the thread

Each stage ends by writing an artifact to version control, and the next stage begins by reading it:
`intent.md`, `spec.md`, `plan.md`, the diff and its tests, the PR with its review findings, and the
incident record. For the early stages, markdown is the artifact because a product owner and an agent
can both read and act on the same file. From build onward, the artifact is code and its records.

The chain of commits is also the audit trail: who asked for what, what the agent produced, and who
approved it. Humans remain accountable for every decision that requires judgment — what shifts is
which artifacts human attention lands on.

An accepted `intent.md` triggers the requirements and design pass, an approved `spec.md` triggers plan
mode, a merged PR triggers the pipeline, and a breached control band in production writes the next
`intent.md`. First you prompt each step by hand; the end state is a loop in which each accepted
artifact fires the next gate.

## Stage 1 — Plan: capture intent

*Ideas stop waiting for someone to write them up.*

Traditionally, an idea passes through backlog entries, user stories, story points, and refinement
meetings before anyone can act on it. Ownership transfers at each handoff, so what reaches
engineering is several steps removed from what the originator meant.

Instead, the originator brainstorms with Claude and writes the result down as `intent.md` — a
proto-spec in their own terms, containing what is wanted, why, and under which constraints. No formal
language is required. Claude asks the questions an analyst would: scope, users, constraints, and what
success looks like. The originator corrects anything Claude misunderstood, then commits the file.

**Getting started.** No prerequisites. You need Claude access for people who are not engineers
(claude.ai or Cowork), an agreed template, and a shared version-controlled home the product owner
watches. For a single product the simplest home is an `intent/` folder in the product repo, keeping
the artifact chain next to the code derived from it. A dedicated intent repo is only worth the
overhead when intent spans many repositories.

Standing this up is a one-time task for the platform team, who decide who can write to it. Once the
repository exists, contributors without git experience commit through a version-control connector
from claude.ai or Cowork.

**A worked `intent.md`:**

```markdown
# Intent: claims status self-service
Author: J. Ortiz (claims operations). Status: draft.

## Problem
Customers phone the contact center to ask where their claim is.
Handlers spend roughly a third of call time on status-only queries.

## Proposed outcome
Customers see claim status, next step and expected date in the portal.

## Affected users and systems
Claims handlers, portal team, claims-core API.

## Constraints
No new PII in the portal session. Existing authentication only.

## Open questions
Do third-party loss adjusters need access too?
```

**Governance.** The evidence is the committed file, with author, timestamp, and full revision history
in git. The product owner approves, and the accept-or-reject decision is recorded as the merge or the
closing review.

**Measurement.** Leading: time from first conversation to a committed `intent.md`, expected to fall
from a multi-week elicitation cycle to hours. Lagging: the survival rate of intents into design, plus
changes made to `intent.md` after the first `spec.md` commit.

## Stage 2 — Design: requirements and design collapse

Requirements and design are traditionally separate phases run by separate teams. The separation exists
for accountability, but it is slow and lossy.

Both now happen in a single prompted session. Claude takes the accepted `intent.md` and produces a
requirements and design spec, constrained by the organization's skills for brand, security,
compliance, and UX, with areas of concern flagged. The product owner reviews the spec but does not
write it.

The prompt to start from:

```text
Read the attached intent.md and produce a requirements and design spec for
integrating it into our existing codebase. Apply the skills available to you so
the plan conforms to our brand guidelines, security policies and UX standards.
Document the spec fully as spec.md, ready to hand to the engineering team.
Describe clearly any areas of concern, especially where you cannot satisfy
contradicting policies.
```

Run it by hand at first, then codify it as an organization-level slash command, then make acceptance
of the intent the trigger for a non-interactive job that commits `spec.md` as a pull request. From
that point the product owner's first involvement is the review.

Work through the flagged concerns first — they are the points an analyst would have escalated — and
resolve each with its policy owner before engineering sees the spec. Commit `spec.md` alongside
`intent.md`; the pair records what was asked for and what was decided.

Front-end work is the clearest example of the collapse: the product owner mocks the design up in
Claude Design (beta) from the `intent.md`, iterates on the mock, then exports it to Claude Code to
build.

**Governance.** Live policy is read and applied while the spec is written, instead of being
discovered in a review weeks later. The spec, the prompt that produced it, and the skill versions in
force are all logged in version control.

**Measurement.** Leading: elapsed time between the `intent.md` and `spec.md` commits — two git
timestamps. Lagging: requirements rework after build starts, counted as `spec.md` commits dated after
the first `plan.md` commit for the same change.

## Stage 3 — Build: nothing is implemented without an accepted plan

### Plan mode as the default starting point

Traditionally, how a change will be made — which files, which tests — stays in the engineer's head or
at best a ticket comment. The first thing a reviewer sees is the finished diff, and by then rework is
slow.

Instead, work starts with a written plan Claude produces in plan mode, where it can read the codebase
without changing anything. Give Claude `intent.md` and `spec.md` and ask for a plan naming the files
that change, the order of work, and the tests that prove it. Interrogate it: what could this break,
which step is riskiest, what did you choose not to do? Iterate until an engineer who never saw the
conversation could implement the change from the plan alone, then commit it as `plan.md`.

```markdown
# Plan: claims status self-service (from intent.md 2026-06-02)
## Files that change
portal/src/claims/StatusPanel.tsx (new), claims-api/routes/status.py,
claims-api/tests/test_status.py
## Order of work
1. Add the status endpoint behind existing auth.
2. Panel against the endpoint.
3. Wire into the portal nav.
## Risks
The claims-core API rate-limits at 50 rps; the panel must cache.
## Proof
test_status.py covers the four claim states; screenshot matches the
approved mock.
```

With a solid plan, the implementation is often a single pass. When it departs from the plan, update
`plan.md` in the same commit — a hook can enforce the synchronization.

Plan mode enforces the design review itself: Claude cannot edit files until the engineer accepts the
plan, so changing course is still a matter of editing a document.

### Auto mode

Claude Code can also run in auto mode, applying each change without a per-edit prompt once the plan is
approved. As the guardrails mature — a tuned `CLAUDE.md`, skills that encode policy, hooks that block
unsafe actions, and a test suite Claude can run — auto-accept becomes the default for routine work: a
tight spec, a small blast radius, and code the tests already cover. The shift is away from watching
the agent edit and towards reviewing artifacts after longer autonomous sessions.

### `CLAUDE.md`

`CLAUDE.md` gives Claude the context a new joiner would need: conventions, commands, architecture, and
the mistakes the team sees most often. Knowledge that used to sit in people's heads and on wikis
becomes a file the agent reads at the start of every session.

Run `/init`, cut the generated file down to what a new joiner needs on day one, and check it in at the
repo root so the team shares one version and changes are reviewed like code. A working rule: when
Claude makes a mistake twice, the correction goes into `CLAUDE.md`. Keep it under a page — Claude reads
all of it at the start of a session, so anything stale takes up context for no benefit.

```markdown
# Payments service

## Commands
- Build: make build
- Test: make test (unit), make itest (integration, needs docker)
- Lint: make lint (runs in CI; fix before pushing)

## Conventions
- Java 21, Spring Boot 3. No new Lombok.
- Money is always BigDecimal, never double.
- Every endpoint needs an integration test in src/itest.

## Architecture
- api/ holds REST controllers, core/ holds domain logic,
  adapters/ talks to external systems.
- Kafka events are defined in schemas/; never edit generated classes.

## Things Claude gets wrong
- Do not bump dependency versions; the platform team owns them.
- The legacy v1/ package is frozen; changes go in v2/.
```

### Skills as institutional knowledge

Skills make institutional knowledge operational: explicit, version-controlled, applied broadly, and
updated centrally when policy changes. The rule of thumb — write a skill for institutional knowledge
that must be applied consistently; do not write one for what belongs in `CLAUDE.md` or a prompt.

Pick one piece of knowledge enforced inconsistently today, write it as a folder containing a
`SKILL.md` whose frontmatter says when it triggers and whose body says what to do, and ship it at
`.claude/skills/<name>/` or distribute it organization-wide through a plugin. Test that it actually
triggers by asking Claude to do the relevant task in different ways. When policy changes, change the
skill and have the policy owner sign it off; engineers pick up the new version in their next session.

```markdown
---
name: secure-api-review
description: Apply the API security standard. Use whenever creating or
  modifying an external-facing endpoint, reviewing API code, or
  generating an OpenAPI spec.
---

# Secure API review

When you create or change an API endpoint:

1. Authentication: every endpoint requires the gateway JWT;
   no anonymous routes outside /health.
2. Input validation: validate request bodies against the OpenAPI
   schema and reject unknown fields.
3. Audit: every state-changing endpoint emits an audit event with
   actor, action, entity and timestamp.
4. Data classification: fields tagged pii in the schema must never
   appear in logs or error messages.

Run the endpoint check script and include its output in your summary.
```

**A skill is a control, but an advisory one.** It makes Claude likely to apply the policy while the
code is written, and nothing forces a session to comply. A policy that must always hold needs
something deterministic behind it — a hook that blocks the action, or a review pass that re-checks the
policy at the PR. The skill makes violations rare; the hook makes them close to impossible.

### Hooks as build-time guardrails

Most of Claude's actions during implementation are file edits and shell commands, so build is where
hooks fire most often. Build-phase hooks block edits to protected paths such as generated classes or a
frozen package, run the formatter and linter after edits so drift never accumulates, and keep
credentials out of the diff.

Back any skill whose policy has to hold without exception. Keep build-phase hooks fast and scoped to
the changed file; heavier checks such as the full test suite belong at the commit or the PR. A hook
that asks a human for approval belongs with the deploy gates — an approval prompt during the build
puts a person back on the critical path of every parallel session.

### Parallel sessions and subagents

A parallel session is another full Claude Code instance working a separate task in its own git
worktree; the engineer steering them is the only thing they share. A subagent runs inside a single
session as a scoped helper with its own context window and tool limits, for jobs that recur across
tasks.

Split the work into tasks that touch different files, using the plan to see where the work is
independent — tasks that share files run in one session, one after another. Give each parallel task its
own worktree (`claude --worktree feature-auth` in one terminal, `claude --worktree fix-rate-limit` in
another). Two or three sessions is a sensible start; the practical ceiling is how many streams one
person can review properly.

Turn repeated jobs into subagents defined in `.claude/agents/` — a code simplifier that strips needless
complexity after the main agent finishes, a verifier that runs the app and checks behavior, a
researcher that explores the codebase and reports back without flooding the main context. Check the
definitions into git.

```markdown
---
name: verifier
description: Runs the app and checks the change works before the session
  reports done
tools: Bash, Read
---
Start the app with make run. Exercise the changed behavior and the two
nearest neighboring flows. Report what you ran, what you saw, and any
behavior that does not match plan.md. Do not fix anything; report only.
```

### Legacy systems and the source of truth

Existing processes already track these artifacts, just not in markdown. Work items may be in Jira,
requirements in a tool with regulatory traceability, designs in Figma, change approvals with a change
board. Those systems are hard to displace because auditors already accept them.

For every artifact the process produces, name **one** system as the source of truth and let everything
else hold a copy or a link. Three configurations work: the repo as the source of truth, with the legacy
system referencing files within commits; the legacy system as the source of truth, with Claude reading
the record at session start and writing the outcome back through an MCP connector; or linkage as the
minimum bar, where artifacts note the record ID and records contain the commit SHA. Linkage is a good
place to start, accepting that there are two sources of truth.

## Stage 4 — Test: verification moves inside the session

### Give Claude a feedback loop

The signal that code works traditionally arrives late — CI minutes later, a tester days later,
production weeks later. With an agent producing the code, a late signal means a person has to check all
of its output, and that person becomes the bottleneck.

Always give Claude a way to verify its own work: tests, a build, or a screenshot diff.

1. If checking the work takes a sequence of commands and some environment knowledge, wrap it in a
   single target that exits non-zero on failure.
2. List each command in the `CLAUDE.md` Commands section with an example of healthy output.
3. State a quantifiable target so Claude can check itself — "all tests in test_status.py pass", "the
   screenshot matches the attached mock", "the endpoint returns 200 with the new field".
4. For bug fixes, write the failing test first. Ask Claude to reproduce the bug as a test, run it, and
   confirm it fails for the reason you expect. Commit that test. Only then ask for the fix, without
   editing the test. A test that existed before the fix, and that the agent could not rewrite, is proof
   the bug is gone.
5. For UI work, close the loop with a visual check — give Claude a browser or screenshot tool and the
   mock, then let it implement, screenshot, compare, and adjust. Two or three rounds is normal.
6. Make verification part of "done", with the instruction in `CLAUDE.md`.

```markdown
## Verifying your work
- Build: make build (must finish with "Build succeeded")
- Test: make test (all green; never skip or delete a failing test)
- Lint: make lint (zero warnings)

Run all three before reporting any task complete, and paste the output.
If a test fails, fix the code, not the test.
```

The loop itself needs protecting: an agent fixing code must not be able to weaken the check on that
code. A hook that blocks edits to test files during a fix task does this; the alternative is to check
the diff in review and reject any change that touches a test.

Do not confuse the feedback loop with a verifier subagent. The loop runs throughout the task; the
verifier packages the final check in a fresh context window once the session believes the work is done,
so the verdict is not colored by the assumptions that produced the code.

### Continuous evals in CI

Evals are the AI-native equivalent of stage-gate QA: a suite that runs whenever the agent's
configuration changes. When a model is swapped in or a prompt rewritten, the suite says whether the
agent still does the work to the same standard. Treat it as a live suite — as models improve, cases that
once discriminated stop doing so, and new ones must be added from ongoing monitoring.

Collect 20 to 50 real tasks from recent work with their accepted outcomes, and write each as a prompt
plus the checks that define acceptable (tests pass, lint clean, behavior unchanged, policy followed).
Run the suite non-interactively in CI on a schedule and on any change to `CLAUDE.md`, skills, or hooks,
since that configuration steers the agent and deserves the regression testing code gets. Gate
configuration changes on the results: a skill change that drops the pass rate gets reviewed before it
merges. Every production incident gets an eval, written by the team that owned it, and stays in the
suite as a regression test.

```yaml
name: Agent evals
on:
  pull_request:
    paths: ['CLAUDE.md', '.claude/**']
  schedule:
    - cron: '0 2 * * *'
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install -g @anthropic-ai/claude-code
      - name: Run eval suite
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          for eval in evals/*.json; do
            claude -p "$(jq -r '.prompt' $eval)" \
              --allowedTools "Read,Edit,Bash(make test)" \
              --output-format json > result.json
            ./evals/check.sh "$eval" result.json
          done
```

## Stage 5 — Deploy: review both directions, gate the release

### AI in the PR review loop

Review capacity was planned around human output: a PR waits for a reviewer to read all of it, quality
varies with the reviewer's load, and the author chases while the backlog grows.

Claude both gives and receives reviews. All PRs get an identical set of passes with findings ranked by
severity, so human attention moves up a level — to whether the change does what the plan intended and
whether the risk is acceptable.

The managed Code Review service (research preview) is the fastest start: an admin enables it and selects
repositories. Run the review in your own CI with the `claude-code-action` when you need control of the
pipeline or want API calls routed through your own cloud agreement — Bedrock, Vertex, or Foundry.

The tech lead writes the review policy as `REVIEW.md` at the repo root:

```markdown
# Review instructions

## Passes
Run three passes and tag each finding with its pass:
- Bugs: logic errors, broken edge cases, subtle regressions
- Security: injection risks, authentication gaps, PII in logs
- Compliance: the change matches spec.md, plan.md and our design principles

## What Important means here
Reserve Important for findings that would break behavior, leak data
or breach a policy. Style and naming are nits.

## Cap the nits
Report at most five nits per review; summarize the rest as a count.

## Do not report
Generated files under src/gen/ and anything CI already enforces.
```

Findings do not approve or block a PR on their own; branch protection still requires approval from a
code owner. A platform engineer who wants to gate merges on findings reads the severity counts the check
run publishes as a machine-readable tally.

When a reviewer or the author tags `@claude` on a review comment, Claude addresses it and pushes the
fix, with the thread recording both request and change. For PRs Claude opened, teams wrap the loop in a
custom command that sweeps unresolved comments and failing checks until the PR is green and waiting only
on code owner approval.

Review findings feed back into `CLAUDE.md`: when a review flags a mistake a second time, the correction
goes into the file as part of that review, and because review reads `CLAUDE.md`, the mistake is caught
from the next PR onwards. Once a month the tech lead tunes the setup by rating findings and capping nit
volume.

**Separation of duties is preserved**: the agent that wrote the code has no way to approve it.

### Hooks as approval gates

A hook can also **ask**, pausing the action until a specific person approves — which is what release
gating needs. Engineering leadership, with change management and compliance, lists the human approval
gates that must survive: change management sign-off, release authorization, edits to protected paths.
The platform engineer expresses each as a hook that can allow, ask, or block.

Team hooks go in `.claude/settings.json` in git; non-negotiable hooks go in managed settings owned by
the platform or IT admin, where individual engineers cannot switch them off. A block should explain
itself — when a hook stops an action, the reason and the route to approval appear in Claude's output.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/production-gate.sh"
          }
        ]
      }
    ]
  }
}
```

```bash
#!/bin/bash
# Production deploys require a named release authorization
cmd=$(jq -r '.tool_input.command' < /dev/stdin)
if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
  if [ -z "$RELEASE_APPROVAL" ]; then
    echo "Production deploys need a release authorization." >&2
    exit 2   # exit 2 blocks the action; the message goes to Claude
  fi
fi
exit 0
```

Hooks are not deploy-specific: they run wherever Claude acts. They can block edits to migrations and
infra without a change ticket during build, and stop the agent editing test files during a fix task.

### Managed settings for a regulated enterprise

Deployed by the platform team via MDM or the admin console, and not editable by engineers. Deny rules
keep secrets out of the agent's context and block network egress through tools, while an allow list
pre-approves the safe inner loop so the deny list does not turn into prompt fatigue.
`disableBypassPermissionsMode` and `allowManagedPermissionRulesOnly` mean no engineer, project file, or
flag can widen the rules. The sandbox closes the gap permissions cannot — a tool-level deny does not
stop a shell command reaching the network, but an OS-level domain allowlist blocks egress outright, and
`failIfUnavailable` makes the sandbox a gate rather than a preference. A credentials block denies
sandboxed shell reads of `~/.ssh` and cloud credentials and strips named secrets from the environment.
`allowManagedHooksOnly`, `disableSideloadFlags`, `strictKnownMarketplaces`, and
`allowManagedMcpServersOnly` mean every skill, agent, hook, and MCP server arrived through the approved
marketplace, and `requiredMinimumVersion` refuses to start on a build the organization has not assessed.

Treat any such configuration as a starting point to tailor rather than a recommendation to copy. Every
deny trades against capability, and the right balance depends on the data classification of the repo.

### CI/CD integration and deployment

Pipelines traditionally run deterministic scripts, and anything needing judgment waits for a human.
Instead, run Claude non-interactively inside the pipeline for the judgment steps, in a sandbox with
scoped credentials.

Start with read-only judgment steps — triage a failed build, summarize a flaky test, draft the
changelog:

```yaml
- name: Triage failed build
  if: failure()
  run: >
    claude -p "Read the build log at out/build.log. Identify the most
    likely cause, say whether the failure looks flaky or real, and write a
    three-line summary for the PR thread." >> triage.md
```

Then add write steps behind the existing gates — fixing lint, updating generated docs, addressing review
comments via `@claude`. Anything the agent writes arrives as a PR through branch protection, and the
agent has no route to push to main. Agent jobs run in containers under a network policy with short-lived
scoped tokens and no production credentials by default.

Expose deployment through MCP so deploy, status, and rollback become tools scoped per environment — an
allowlist rather than a shell script with credentials. Tier the autonomy: in development the agent
deploys freely; in production the agent prepares the release and the release manager authorizes it, with
a hook enforcing the gate. Rollback should be the most rehearsed path in the pipeline, exercised
regularly in staging, because the maintenance loop calls it.

**The governing principle: the agent may act up to the production gate and cannot pass it.**

## Stage 6 — Maintain: close the loop

Maintenance is traditionally reactive. An alert fires at 3 a.m. and can be missed, a ticket sits in the
backlog until someone picks it up, and post-mortem actions may never reach the codebase if another fire
starts.

Instead, a trigger — a control-band breach, a ticket, a channel message, a schedule — invokes Claude
without a person in the path. Claude diagnoses, acts only through gated routes, and writes what it finds
as `intent.md`, which goes through the stages above. The stage runs headless, with an independent
confidence gate between stages — a deterministic check or an adversarial reviewing agent — deciding
whether the previous stage's output continues or is escalated to a human.

**Closing the loop, step by step:**

1. Pick one metric with a stable rolling baseline: CI test failure rate, post-deploy 5xx rate, or PR
   cycle time.
2. Write the detection script — typically mean and standard deviation over a rolling window with
   Western Electric or similar rules, so the bands catch slow drift as well as spikes. Version control
   and unit test it. **Detection stays entirely deterministic, with no model involved.**
3. Define response tiers in version-controlled config. At 1σ the script only logs; at 2σ it invokes
   Claude read-only to diagnose; at 3σ Claude may act, but only by opening a PR into the review gate or
   triggering a pre-approved runbook.
4. Trigger from a scheduled workflow, a webhook from the existing monitoring stack, or a cron job inside
   the network. Claude runs stateless — a non-interactive step on a CI runner, or an Agent SDK service in
   a sandboxed container — so a loop can begin and end without anyone starting it.
5. The agent writes its diagnosis as `intent.md` in the Stage 1 format, covering the anomaly and its
   evidence, a proposed outcome, the affected systems, and any open questions.
6. The service owner or on-call engineer triages: fix now, schedule, or dismiss. Dismissals tune the
   bands and reduce noise.
7. When a fix ships, add an eval for the incident so the class of issue is protected against going
   forward.

```yaml
metric: ci_test_failure_rate
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }
  2sigma: { action: diagnose, tools: "Read,Grep,Bash(gh run view *)" }
  3sigma: { action: propose, routes: [pull_request, runbook:rollback-deploy] }
```

What that buys in practice: when the CI test failure rate breaches 3σ, the agent quarantines the flaky
test or opens a revert PR and the review gate decides. When the post-deploy 5xx rate breaches 3σ with a
deployment in the window, the agent triggers the existing rollback pipeline. When PR cycle time trips a
drift rule, the agent writes a report for engineering leadership — which shows the harness works for
process metrics as well as production ones.

### Claude on call with Claude Tag

Incidents also arrive through workplace communication apps. A 10 p.m. Slack message on an incident
channel can now be actioned immediately: Claude Tag (public beta, currently in Slack) makes Claude a
member of those channels under its own identity, so each new incident gets a first responder and the
response itself becomes part of the loop and memory for future incidents.

The conversation and institutional knowledge stay in the channel. Anyone there can guide the response,
test hypotheses, and investigate in real time, with the channel history adding to the auditability.
Through MCP access, Claude verifies the metric is back at baseline, confirms it in the thread, and
writes the post-mortem to a version-controlled lessons file that future investigations can read.

Incidents are not the only work Claude Tag picks up. Tagged on a ticket over MCP or asked in the
channel, Claude triages the same way: a small, well-bounded fix arrives as a PR through the review gate,
and anything larger is written up as `intent.md` — at which point the loop starts feeding itself.

## Closing thoughts

Models and harnesses have become advanced enough for organizations to transform not just how they
produce code, but the entire software development lifecycle — while keeping human judgment central and
meeting the governance and regulation requirements of large enterprises.

The loop keeps running. Human judgement stays above it.
