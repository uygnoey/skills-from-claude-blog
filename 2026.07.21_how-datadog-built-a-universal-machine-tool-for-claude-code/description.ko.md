## 이 글이 뭔가요
Datadog 엔지니어들은 프로덕션 작업에서 Claude Code를 네 가지 범주로 사용한다. 국소적 변경, 대규모 리팩터링, 주요 시스템 교체, 그리고 완전히 새로운 시스템 구축이다. 이 방식이 확장되자 병목이 이동했다. Datadog의 엔지니어링 VP인 Sesh Nalla는 엔지니어링 업무의 감각이 어떻게 바뀌었는지 이렇게 설명한다. "이제 코드를 쓰는 게 아니라 일을 빚는 겁니다. 에이전트가 무엇을 봐야 하는지, 어떤 도구를 가져야 하는지, 성공이 무엇인지, 실패를 어떻게 감지할지를 결정하죠… 모두가 관리 체계에서 세 단계 승진한 것 같은데, 그들은 엔지니어라서 그런 걸 원한 적이 없습니다."

Datadog이 만든 구조적 해답이 **Temper**이며, 글은 이를 에이전트를 위한 "범용 공작기계(universal machine tool)"라고 부른다. 에이전트가 제어 로직을 애플리케이션 코드로 내놓는 대신 **명세(specification)** 를 내놓는다. 그러면 LLM 바깥의 결정론적 커널이 실행 전에 각 명세를 네 개의 독립된 계층으로 검증한다. 기호 추론, 완전 상태 탐색, 시드 기반 결함 주입을 곁들인 결정론적 시뮬레이션, 그리고 무작위 속성 테스트다. 모든 capability는 동작·데이터·인가라는 세 가지 계약으로 표현된다.

글은 Temper를 가능하게 만든 세 선행 프로젝트(Courier, BitsEvolve, Helix)를 짚은 뒤, Claude Code가 며칠 만에 대부분을 만들어낸 Kafka 대체급 스트리밍 시스템 Helix를 위해 Temper가 "다크 팩토리(dark factory)"를 돌리는 모습을 보여준다. 마지막은 Datadog 팀의 베스트 프랙티스로 마무리된다.

## 언제 유용한가요
- 에이전트가 팀이 리뷰할 수 있는 속도보다 빠르게 코드를 만들어내어, 생성이 아니라 검증이 출시를 제한하게 됐을 때.
- 에이전트가 실제로 무엇을 내놓아야 하는지 정할 때 — 임의의 코드인가, 결정론적 커널이 검증할 수 있는 명세인가.
- 제어 로직이 라우트·DB 제약·서비스 코드·백그라운드 잡·문서에 흩어져 있어 시스템의 상태 기계가 무엇인지 아무도 말할 수 없을 때.
- 매번 전체 CI 사이클을 돌리지 않고도 에이전트가 운영 동작을 안전하게 바꿔야 할 때.
- 자율적인 빌드·운영 루프를 만들면서 사람이 여전히 조율해야 하는 지점을 정할 때.
- 생성된 산출물이 사람이 머릿속에 담아둘 수 있는 크기를 넘어섰는지 판단할 때.

## 핵심 포인트
- **병목은 생성이 아니라 검증이라고 가정하라.** 에이전트는 이미 어떤 팀도 따라잡을 수 없는 속도로 코드를 만든다. 생성된 것과 증명된 것 사이의 간극에 실패 모드가 쌓이므로, 투자는 처리량이 아니라 그 간극에 들어가야 한다.
- **에이전트는 제어 로직에 대해 코드가 아니라 명세를 내놓는다.** 임의의 코드에 대해서는 증명 동반(proof-carrying)이 글의 프레이밍이다. 컴파일과 증명은 LLM 바깥에 둔다. 명세를 결정론적 커널에 넘겨서, 검증된 산출물이 곧 실행되는 산출물이 되게 한다.
- **네 개의 독립된 검증 계층.** 기호 추론이 각 가드의 충족 가능성과 각 불변식의 귀납성을 증명하고, 완전 상태 탐색이 도달 가능한 모든 상태를 방문하며, 결정론적 시뮬레이션이 시드된 결함 주입과 함께 프로덕션 코드를 돌리고, 무작위 속성 테스트가 약 1,000개의 유사난수 액션 시퀀스를 실행한다.
- **모든 capability는 세 가지 계약을 지닌다.** 동작(상태, 전이, 사전조건, 안전 속성), 데이터 계약(엔티티 타입, 속성, 액션을 기계가 파싱 가능한 형태로), 인가(기본 거부, 스코프 기반 승인과 보류 결정, 핫 로딩).
- **세 프로젝트가 Temper를 가능하게 했다.** Courier(2024)는 분산 큐잉 시스템으로, "어려운 것은 부품을 만드는 일이 아니라 부품 사이의 상호작용을 관측 가능하고 테스트 가능하며 검증 가능하게 만드는 일"이었다. BitsEvolve(2025년 9월)는 폐루프 진화 최적화기로, "소프트웨어의 일부가 살아 있는 유기체처럼 배양될 수 있다는 첫 조짐"이었다. Helix에서는 Kafka 대체급 시스템이 며칠 만에 나왔고 병목이 다시 이동했다 — 사람을 위해 만들어진 도구로 사람이 릴리스를 조율하는 지점으로.
- **Helix 다크 팩토리에서 Temper는 세 역할을 한다.** 관리형 에이전트를 위한 에이전트 컨트롤 플레인(세션, 역할, 작업 큐, 라이프사이클), 에이전트가 SDLC 도구(Git, CI, 배포)를 잇게 해주는 도구 빌더 계층, 그리고 데이터 플레인을 둘러싼 라이프사이클 표면인 Helix 컨트롤 API.
- **왜 그냥 CRUD 앱이 아닌가.** Claude Code는 CRUD 앱을 잘 만들지만, 거기서는 운영 모드 — 대개 상태 기계 — 가 암묵적으로 남아 라우트·제약·서비스 코드·잡·문서에 흩어진다. Temper는 그 상태 기계를 명시적이고 데이터 주도적으로 만든다. "에이전트는 임의의 코드가 아니라 정밀한 서술을 내놓습니다… 에이전트는 그것을 안전하게 동적으로 바꾸고, CI를 거치지 않고 핫 리로드할 수 있습니다."
- **모든 산출물을 사람이 이해할 수 있는 크기로 유지하라.** 생성된 산출물을 사람이 머릿속에 담을 수 없다면, 원점으로 돌아온 것이다.
- **이 방향이 가리키는 곳.** "이렇게 만들어진 소프트웨어는 피드백과 선택과 적응을 통해 기르고 배양하고 진화시킬 수 있는 유기체처럼 느껴지기 시작합니다."
