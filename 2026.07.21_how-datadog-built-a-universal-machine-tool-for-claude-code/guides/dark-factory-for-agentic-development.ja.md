# エージェント開発のためのダークファクトリーを築く

Datadog が「エージェントがコードを書く」から「エージェントが検証可能な仕様を書く」へ移行した方法と、それが構造的に何を要求するか。

## 1. フローの問題

エンジニアリングのフローは、かつては意図とコードの直接的な関係だった。問題を理解し、コードを書き、テストし、レビューし、出荷し、運用し、繰り返す。エージェントはその抽象度を、しかも急速に変えた。

Datadog のエンジニアリング担当 VP、Sesh Nalla は仕事が何になったかをこう語る。

> 「もうコードを書いているのではなく、仕事のかたちを作っているのです。エージェントが何を見るべきか、どんなツールを持つべきか、成功とは何か、失敗をどう検知するかを決めている……全員がマネジメントの階段を三段飛ばしで昇進させられたようなもので、彼らはエンジニアなのでそんなことは望んでいませんでした。」

Datadog のエンジニアは、限定的な変更、大規模リファクタリング、主要システムの置き換え、まったく新しいシステムの構築という四つのカテゴリーの本番業務で Claude Code を使っている。その規模になると「昇進」は比喩ではない。エンジニアの一日の中身が実際に変わっており、その下にある道具立ては以前の仕事のために作られたものだ。

> 「もっと構造的なものが必要だと感じたのが、まさにこの地点です。エージェントが私たちのシステムの、ミッションクリティカルなデータベースの大部分を作り運用するのであれば、この工作機械という概念に相当するものが必要になります。Temper が Datadog にとってのその工作機械です。」

## 2. Temper を可能にした三つのプロジェクト

**Courier（2024）** — 形式モデリングを重視して作られた分散キューイングシステム。教訓はこうだ。「難しかったのは部品を作ることではなく、部品どうしの相互作用を観測可能・テスト可能・検証可能にすることだった。」

**BitsEvolve（2025 年 9 月）** — フィードバックを伴う変異生成による閉ループの進化的最適化。教訓はこうだ。「ソフトウェアの一部が生き物のように培養されうる——変異とフィードバック、適応を通じて育てられうる——という、私にとって最初の兆しでした。」

**Helix** — Claude Code が数日でその大部分を作り上げた、Kafka 相当のストリーミングシステム。「信じられないことに、数日で完全に機能する Kafka 相当のシステムができていました。」そして制約が移動した。

> 「ボトルネックがまた動きました。エージェントはシステムの大部分を作れるようになった……しかしそのあと、人間が依然として、人間のために作られた道具と仕組みを通して、その成果を本番へ届けるために調整しなければならないのです。」

この一文がそのまま次に必要なものの要求仕様である。SDLC の道具立ては人間が運転することを前提にしている。ビルドが数日で終わるなら、人間のかたちをした調整の面が遅い部分になる。

## 3. Temper：エージェントが仕様を出し、カーネルが証明する

中核の反転はこうだ。エージェントは制御ロジックのためのアプリケーションコードを作らない。**仕様**を作る。そして LLM の外にある決定論的カーネルが、実行前にそれぞれを検証する。

コンパイルと証明をモデルの外に置くことには明確な理由がある。検証される成果物が、そのまま実行される成果物になるからだ。証明された記述を人が実装し直して食い違いが生まれる、という段階が存在しない。

### 四つの検証層

互いの死角を覆うよう、意図的に独立している。

1. **記号推論**が、各ガードが充足可能であり、各不変条件が帰納的であることを証明する。
2. **網羅的状態探索**が、到達可能なすべての状態を訪れる。
3. **決定論的シミュレーション**が、シード付き障害注入とともに本番コードを実行する。
4. **ランダム化プロパティテスト**が、およそ 1,000 本の擬似乱数アクション列を実行する。

決定論こそが、これをエージェントのループの中で使えるものにしている。失敗はシードとともに返ってくるので、エージェントは失敗の説明文ではなく、失敗した実行そのものを受け取る。

### 三つの契約

すべての capability が三つとも要求する。

- **振る舞い** — 状態、遷移、事前条件、安全性プロパティ。
- **データ契約** — エンティティ型、プロパティ、アクションを機械可読な形で。
- **認可** — デフォルト拒否、スコープに基づく承認と保留中の決定。

保留中の決定を備えたデフォルト拒否こそが、「エージェントがより多くの権限を求めている」を事故からレビュー可能な差分へと変える。

## 4. Helix のためのダークファクトリー

Helix のダークファクトリーにおいて、Temper は三つの役割を同時に果たす。

1. **エージェント制御プレーン** — マネージドエージェントのセッション、ロール、作業キュー、ライフサイクル。
2. **ツールビルダー層** — エージェントが Git、CI、デプロイといった SDLC ツールを橋渡しできるようにする。Helix の後に現れたボトルネックへの直接の答えである。
3. **Helix 制御 API** — データプレーンを取り巻くライフサイクル面。

三つ目の役割こそが、これをビルドパイプラインではなく工作機械にしている。エージェントのための制御プレーンと、彼らが作る製品の制御プレーンが、同じ明示的で検証済みの面だからだ。

## 5. なぜ単に CRUD アプリを作らないのか

Claude Code は CRUD アプリをうまく作る。異論はそこではない。異論は制御ロジックがどこに行き着くかにある。

> 「通常の CRUD アプリでは、制御ロジックはルート、データベース制約、サービスコード、バックグラウンドジョブ、ドキュメントに散らばっています……たいていは状態機械のかたちを取る運用モードが、コードベースの中で暗黙のままなのです。」

暗黙の制御ロジックは検証できないし、エージェントが安全に変更することもできない。変更すべき単一の成果物が存在しないからだ。Temper の答えはこうだ。

> 「Temper はその状態機械を明示的にします。エージェントは任意のコードではなく、正確な記述を生み出します……エージェントはそれを安全に動的に変更でき、CI を通さずにホットリロードできます。」

状態機械をコードではなくデータにすると、三つのことが帰結する。

- エージェントはコードベース全体を読まずに、制御ロジックのすべてを読める。
- 変更は五つのファイルにまたがる編集ではなく、境界の明確な差分になる。
- CI サイクルを消費せず、ポリシーのもとでホットリロードできる。

## 6. この先にあるもの

> 「エージェントがこの種の規律を備えた工場の中で自律的にソフトウェアを作れるのなら、ダークファクトリーで止まる必要はないのかもしれません。こうして作られたソフトウェアは、フィードバックと選択と適応を通じて育て、培い、進化させられる有機体のように感じられ始めます。」

## 7. Datadog チームのベストプラクティス

**本当のボトルネックは生成か、検証か。**
検証だと想定せよ。エージェントはすでに、どのチームもレビューしきれない速さでコードを生み出す。生成されたものと証明されたものの隔たりに障害モードが積み上がる。スループットではなく、そこへ投資せよ。

**エージェントは実際に何を出力すべきか。**
制御ロジックにはコードではなく仕様を、任意のコードには証明の同伴を。コンパイルと証明は LLM の外に置く——仕様を決定論的カーネルに渡し、検証される成果物がそのまま実行される成果物になるようにせよ。

**制御ロジックは明示的か、それともコードベースに散らばっているか。**
状態機械をルート、サービスメソッド、バックグラウンドジョブから引き出してデータにせよ。エージェントが読み、変更し、ポリシーのもとでホットリロードできる遷移テーブルに。

**それぞれの成果物を、人は頭の中に収めて理解できるか。**
できないなら、出発点に戻ってしまっている。生成されるすべての断片を、推論できる大きさに保て。
