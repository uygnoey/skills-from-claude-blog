# コーチできる人間とエージェントのチーム：Asana の教訓

Claude の「人間とエージェントのチーム」シリーズ第 3 弾です（前回までは Anthropic のマルチプレイヤー AI、エージェントの
コンテキストとしての Slack）。Asana の最高製品責任者 Arnab Bose 氏が、Work Graph® モデル — 担当者・貢献者・依存関係が
定義されたタスク、プロジェクト、目標、会話の関係網 — の中で AI エージェントをチームメイトとして運用する方法を語ります。

## 設計上の選択：エージェントも同じ作業モデルの中で働く
AI 用に新しいコンテキスト構造を追加するのではなく、Asana のエージェントは既存のモデルの中で働きます。役割が定義され、
タスクを割り当てられ、メッセージを読み書きし、人と並んでアクティビティフィードに現れます。ただしアクセスと共有には追加の
安全策があります。Asana 社員の標準 AI ツールは Claude で、Google Drive、Slack、Asana に接続されています。

## 4 つの実践

| 実践 | 意味 | 実践方法 |
|---|---|---|
| エージェントが動く前に仕事を構造化する | 人が Claude と一緒に非構造の入力（アイデア、Slack、会議録画、レポート、ドキュメント）をプロジェクトとタスクに変え、その後エージェントが永続メモリ・自身の認証情報・共有コンテキストで動く | 自分のアイデアから始める → Claude と議論する → 実行項目をワークグラフに記録する |
| エージェントごとに役割・ツール・アクセス範囲 | 役割（コンテンツライター、インサイトアナリスト、プロジェクトマネージャー、業務受付担当、キャンペーンアナリスト、キャンペーンコーディネーター）を中心に、組み込みスキルと連携を持つ。各自プロフィールページがあり、実効アクセスは呼び出した人の権限に制限される | 先に役割を定義 → アクセス範囲を決める → 利用者と管理者を分けて指名 |
| 一緒に働くことと訓練することを分ける | 共有メモリで複数ユーザーが過去の指示を再利用できる。誰でもタスクにフィードバックできるが、永続メモリへの反映・取り消し・削除は管理者と編集者のみ | 訓練する人と使う人を決める → 専門性に合う編集者を割り当てる → 働きながらメモリを育てる |
| エージェントの仕事を全員に見えるようにする | エージェントがタスクに調査計画と手順を投稿し、アクセス権のある人は誰でもコメントして方向づけられる | チームがレビューする場所にエージェントを置く → エージェントの仕事だと明示する → レビュアーがコーチする |

可視性が重要な理由について Arnab 氏は、1 対 1 のエージェントでは他のレビュアーはプロンプトもやり取りも分からないと述べます。
共有タスクなら依頼、反論、成果物が一か所にあり、レビュアーは成果物を生んだ指示そのものを修正できます。

## Asana の 3 つのエージェント業務
1. **Slack での製品 Q&A** — 質問はタスクになり、エージェントが承認済みガイダンスからソースリンク付きで回答します。製品の
   ギャップは製品チームの受付プロジェクトに登録し、同じ質問が繰り返されるとイネーブルメントチームのタスクを作ります。
2. **At-Risk Renewal ダイジェスト** — すべてのリスク更新タスクを読み、3 つの区分（ポジティブな動き、ネガティブな動き、
   推奨フォローアップ）で毎日まとめ、グローバル → 地域の順に毎朝カスタマー・収益部門のリーダーへ届けます。リーダーは
   追加質問をし、エージェントをコーチします。
3. **Command によるエンジニアリングサイクル計画** — エージェントがフィードバックから未計画ボードを埋め、人がサイクルに
   入れるものを決めます。Command は楽観・中庸・保守の完了予測を出し、チケットは人またはコーディングエージェントに
   割り当てられ、データは Asana の MCP サーバー経由で参照できます。

## まとめ
人とエージェントが共に使う 1 つの共有コンテキスト、貢献とアクセスを監査できるようエージェントごとの固有のアイデンティティ、
そしてチームの知識が積み上がるよう、エージェントが学んだことの永続的な記録。
