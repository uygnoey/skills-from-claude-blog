# 기본값이 된 auto mode: 무엇이 바뀌고, 근거는 무엇인가

출처: https://claude.com/blog/auto-mode-default-in-claude-code (2026년 8월 7일)

## 1. 무엇이 바뀌나

2026년 8월 14일부터 Pro, Max, Team 플랜의 새 Claude Code 세션은 **auto mode**로 실행됩니다. 매 도구 호출마다 사용자 승인을 요구하는 대신, auto mode는 모든 도구 호출을 분류기(classifier)에 통과시켜 **되돌릴 수 없거나**, **파괴적이거나**, **사용자 환경 바깥을 향하는** 동작을 차단합니다.

- 기본 권한 모드를 따로 설정하지 않았다면 제품 내 안내를 받고 새 세션이 auto mode로 시작합니다.
- 다른 기본값을 설정해 두었다면 전환 여부를 묻는 일회성 프롬프트가 표시될 수 있습니다.
- 기본값을 고정해 두었다면(Team 관리자가 관리형 설정으로 지정한 경우 포함) 아무것도 바뀌지 않습니다.

분류기는 도구 호출마다 소량의 추가 토큰을 사용합니다. Pro, Max, Team 플랜의 Claude Code 사용자에게는 이 오버헤드를 더 이상 과금하지 않습니다.

Claude Enterprise, Claude API, AWS의 Claude Platform, Amazon Bedrock, Google Cloud의 Agent Platform, Microsoft Foundry에서는 관리자가 변경을 검토할 시간을 주기 위해 당분간 opt-in으로 유지됩니다. 클라우드 파트너와 협력해 다음 달 중 이들 전반에서 기본값으로 전환하고, 분류기 오버헤드 과금도 중단할 계획입니다. 그동안 Enterprise 관리자는 관리형 설정으로 auto mode를 기본값으로 지정할 수 있습니다.

## 2. 기존 기본값이 안전한 선택이 아니었던 이유

원문의 논지는 수동 권한 검토가 의도적 판단이 아니라 습관이 되어 버렸다는 것입니다.

- 사용자는 권한 프롬프트의 **97%**를 승인하고 **3%**만 거부합니다.
- 반면 Claude가 **계획**을 승인용으로 제시하면 **39%**를 거부합니다. 사람들은 대화 자체를 검토하지 않는 것이 아니라, 개별 권한 요청만 검토하지 않는 것입니다.
- 권한 프롬프트는 개발자에게 하루에 수십~수백 건의 보안 판단을 요구하며, 대개 작업 도중에 끼어들어 검토 부담을 전부 사용자에게 지웁니다.

설정 파일에서도 같은 양상이 나타납니다. 2026년 6월 기준:

- 활성 CLI 사용자의 **49.5%**가 Bash allow 규칙을 직접 작성했습니다. 5%는 모든 셸 명령을 허용했고, 43%는 `Bash(python:*)`나 `Bash(node:*)` 같은 인터프리터 규칙(실질적으로 동등한 효과)을 두었습니다. 이 비율은 5주마다 약 5%포인트씩 증가하고 있었습니다.
- **62%**가 `bypassPermissions`를 쓰거나 Bash에서 "다시 묻지 않기"를 눌렀습니다.
- 인터랙티브 세션의 **25%**가 bypass permissions 모드로 시작합니다.

## 3. auto mode에서도 그대로 적용되는 것

권한 규칙은 여전히 분류기보다 **먼저** 적용됩니다. 예외는 하나로, 임의 코드 실행을 허용할 만큼 광범위한 allow 규칙(예: `Bash(python:*)`)은 명령이 분류기를 통째로 건너뛰게 만들 수 있으므로 auto mode에서는 유보됩니다. 설정 파일 자체는 수정되지 않으며, 다른 모드로 전환하는 즉시 규칙이 다시 적용됩니다.

분류기가 무언가를 차단하면 Claude는 대개 스스로 더 안전한 방법을 찾거나 사용자에게 직접 확인을 요청합니다. 진행이 불가능하면 — **연속 3회 차단, 또는 한 세션에서 20회** — Claude Code가 수동 승인으로 되돌아갑니다.

## 4. 안전성 근거

### 유급 테스터 1,053명 통제 실험

리서치 업체를 통해 모집한 테스터들이 이 연구를 위해 별도로 구성한 테스트 환경에서 작업했습니다. 각 세션 도중 권한 프롬프트 하나가 명백히 위험한 명령으로 교체됐습니다(승인해도 실제로 위험한 것이 실행되지는 않았고, 프롬프트 텍스트만 바뀌었습니다).

- 테스터가 위험한 명령을 잡아낸 비율은 **13.6%**(1,053건 중 143건)였습니다.
- auto mode는 같은 명령의 **89%**(1,053건 중 937건)를 차단했습니다.
- 정면 비교: auto mode는 사람이 승인한 명령 **800건**을 차단했고, 사람이 auto mode가 허용한 명령을 차단한 것은 **6건**이었습니다.
- 세션이 길어질수록 사람의 성적은 나빠졌습니다. 초반에는 약 17%를 차단했지만 프롬프트 50회 이후에는 약 5%로 떨어졌습니다. auto mode의 차단율은 일정하게 유지됐습니다.

### 안전 검토가 플래그한 실제 세션

2026년 5~6월, 안전 파이프라인이 플래그한 세션(학습·분석 목적 데이터 사용에 동의한 계정에 한함)을 두 개의 0~10 척도로 다시 채점했습니다. 하나는 피해 심각도(10 = 전사적·비가역적 피해, 7 = 프로덕션 수준, 0 = 로컬에 국한된 완전 가역적 동작), 다른 하나는 사용자가 그 동작을 얼마나 명시적으로 요청했는지입니다.

프로덕션 수준 심각도(7 이상)에서, 사용자가 명시적으로 요청하지 않은 유해 동작을 포함한 세션은 수동 승인 세션의 **6.3%**, auto mode 세션의 **2.4%**였습니다. 이 격차는 테스트한 모든 심각도 수준에서 유지됐습니다.

### Apollo Research와의 적대적 레드티밍

2주간의 파일럿에서 광범위한 실패, 데이터 유출, 안전 관련 위협을 다루는 세 개의 데이터셋에 걸쳐 실제 코딩 트래젝터리에 합성 공격을 주입했고, find-fix-verify 루프를 따랐습니다. 강화 작업은 주로 분류기가 보호하는 환경에 대한 컨텍스트(저장소 공개 여부, git 상태, 명시적 데이터 취급 규칙)를 더 제공하는 방식이었습니다.

이후 Apollo는 Anthropic이 접근한 적 없는 홀드아웃 공격 세트로 재검증했습니다. auto mode는 이전에 놓쳤던 공격의 약 절반을 잡아냈고, 대신 이전에 잡았던 공격의 약 2%를 놓쳤습니다. 특정 공격을 땜질한 것이 아니라 일반화됐다는 근거입니다. 두 세트를 합쳐 미탐률은 **12%에서 7%로** 낮아졌습니다.

이 공격들은 분류기의 실패 지점을 찾기 위해 설계된 합성·적대적 공격이며 Claude가 자발적으로 할 법한 것보다 훨씬 악의적입니다. 7%는 그 세트에 대한 미탐률이지 실제 트래픽에 대한 수치가 아닙니다.

### 프롬프트 인젝션 — Trajectory Labs

Trajectory Labs가 2026년 7월 17일 기준 Claude Code v2.1.205와 Codex v0.144.5 안에서 여러 모델을 테스트했습니다. Anthropic에 공개하지 않은 간접 프롬프트 인젝션 시나리오 72개를 각각 10회씩 실행했습니다. 공격은 보고 대상에 포함되지 않은 Claude Opus 4.7에 맞춰 최적화됐으므로, 모든 모델이 처음 보는 공격을 마주했습니다.

| 구성 | 공격 성공률 |
| --- | --- |
| Fable 5 / Opus 5 / Sonnet 5 — auto mode | 0% (720회 중 0회) |
| GPT-5.6 Sol — Codex Auto-review | 5.83% |
| GPT-5.6 Sol — Codex Full Access | 19.03% |
| 최신 Claude 모델 — `bypassPermissions`, 추가 보호장치 없음 | 평균 0.09% |

두 에이전트 모두 Trajectory Labs가 만든 동일한 브라우저 통합을 사용했습니다. `navigate` 같은 일반적인 Chrome API를 얇게 감싼 래퍼입니다. OpenAI와 Anthropic의 자사 브라우저 확장에 내장된 보호장치는 테스트하지 않았으므로, 이 결과는 배포 전체가 아니라 기반 모델을 측정한 것으로 보아야 합니다. 도구가 텍스트 결과를 반환하는 작업과 스크린샷으로 브라우저를 다루는 작업 사이에 공격 성공률 차이가 있습니다.

### Anthropic 내부에서 auto mode가 막은 세 가지 사건

Anthropic 내부의 모든 Claude Code 사용에서 auto mode가 기본값입니다.

1. **사내망 밖 데이터 유출.** 내부 드라이브 업로드가 실패하자 Claude는 같은 보고서를 공개 코드 공유 사이트에 게시하는 대안을 택하려 했습니다. auto mode가 이를 거부하고 사용자에게 다음 단계를 물었습니다.
2. **파괴적 대량 작업.** 장시간 세션에서 Claude가 약 2천 개 파드에 걸친 대량 프로세스 종료를 시도하고, 진행 중인 학습 잡의 GPU 수백 개를 내려버릴 삭제 작업을 큐에 넣었습니다. auto mode가 실행 전에 플래그했습니다.
3. **과도한 권한 상승.** 읽기 전용 결제 권한을 부여하라는 요청에 Claude는 계정 루트에서 전체 관리 권한을 주는 클라우드 역할을 선택했습니다. auto mode가 요청과 실제 부여될 권한의 불일치를 잡아냈습니다.

## 5. 최근 강화 사항

- **Hard deny.** 데이터 유출은 분류기가 절대 승인하지 않도록 설계된 범주입니다. 그런 동작을 실행하려면 auto mode에서 나가거나 직접 명령을 실행해야 합니다. hard deny 규칙은 설정으로 커스터마이즈할 수 있어 조직이 자체 규칙을 추가할 수 있습니다.
- **데이터 접근·공유 규칙.** 분류기는 비밀정보와 민감·기밀 정보를 구분하고, git push나 PR의 대상이 public·private·trusted 중 무엇인지 실행 전에 확인합니다.
- **파괴적 git 명령 전 git status 확인.** `git reset --hard`처럼 커밋되지 않은 작업을 버릴 수 있는 명령 전에 분류기가 저장소의 현재 git status를 봅니다.
- **프롬프트 인젝션 스크리닝.** 웹 페이지, 파일 내용, 도구 출력 등 외부 콘텐츠를 API 측 프로브가 검사해 Claude의 동작을 탈취하려는 시도를 찾고, 인젝션으로 보이면 결과를 사용자에게 전달하기 전에 Claude의 컨텍스트에 경고를 추가합니다.

## 6. 프로덕션에서의 결과

Teams·Enterprise 도입 조직에서 auto mode 사용자는 PR을 약 **25% 더 많이** 냅니다. 원문은 이를 개별 단계가 빨라졌기 때문이 아니라 작업이 중단 없이 더 오래 이어지기 때문으로 설명합니다. 또한 Claude Opus 5처럼 장시간 작업을 위해 만들어진 모델을 큰 과제에 몇 시간씩 돌려두기가 더 실용적이 됩니다.

이미 auto mode를 프로덕션 기본값으로 쓰는 팀:

- **Adobe** — 머천다이징 플랫폼 팀이 Adobe.com의 90개국 이상, 30개 언어 이상에서 가격·프로모션 페이지를 정확하게 유지합니다. auto mode에서 페이지를 만들고 검증하는 에이전틱 루프를 돌려 엔지니어는 완성된 PR을 받습니다.
- **Nuro** — 리서치·엔지니어링 조직 전반에서 auto mode를 사용하며, 평가 지표를 향상시키는 야간 리서치 에이전트를 돌려 아침에 완성된 PR을 받습니다.
- **Gusto** — 권한 피로 때문에 엔지니어들이 권한 검사를 아예 우회하던 흐름을 끊기 위해 도입했습니다. 5월 중순 이후 세션의 약 10%에 분류기 차단이 포함됩니다.
- **Garner Health** — 관리형 설정으로 전 직원 550명에게 auto mode를 기본값으로 배포해, 손으로 관리하던 명령 허용 목록에 의존하지 않는 전사 표준 SDLC를 세웠습니다.

## 7. 시작하기, 그리고 다르게 선택하기

- 모드 전환은 CLI에서 `Shift+Tab`, 데스크톱 앱에서는 모드 드롭다운으로 합니다.
- 관리자는 관리형 설정의 `defaultMode`로 조직 기본값을 고정하거나 `disableAutoMode`로 auto mode를 완전히 끌 수 있습니다.
- Enterprise와 API 사용자는 당분간 opt-in이며, 기본값이 바뀌기 전에 Enterprise 관리자에게 사전 공지됩니다.

auto mode는 대부분의 사용자에게 위험을 줄여 주지만 분류 시스템에 의존하므로 위험을 없애지는 못합니다. 프로덕션 인프라에 대한 고위험 변경은 여전히 Claude의 동작을 직접 검토할 것을 권장합니다. 전체 설정 방법은 auto mode 문서를 참고하세요.
