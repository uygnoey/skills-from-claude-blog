# 에이전트 규모 CI를 위한 무상태 테스트 영향 분석

CI 잡이 6개월 동안 약 25배 늘어난 뒤 Anthropic이 테스트 선택 서비스를 재설계한 방식을 바탕으로 한
아키텍처 가이드입니다.

## 에이전트가 CI를 압박하는 이유
- 엔지니어가 분기마다 내보내는 코드는 2021~2025년 대비 약 8배이며, 그중 약 80%를 Claude가 작성하고
  PR 리뷰·승인에도 크게 관여합니다. 리뷰가 빨라지면 압박은 CI로 넘어갑니다.
- 테스트는 약 10배, CI 잡은 6개월 동안 약 25배 증가했습니다.
- 에이전트는 더 작고 잘게 나눈 PR을 선호하고 밤과 주말에도 푸시해 활동량의 바닥을 끌어올립니다.
  사람의 승인 때문에 트래픽은 여전히 몰렸다 빠졌다 합니다.

## 리스너/셀렉터 모델
| 구성 요소 | 역할 |
|---|---|
| 리스너(listener) | 모든 CI 실행의 테스트 결과를 기록 |
| 셀렉터(selector) | 결과 이력을 읽어 PR마다 실행할 테스트를 선택(과거 성적, 패키지 관련성) |

리스너가 밀리면 선택은 오래된 데이터로 이뤄집니다. 잘못된 변경이 모두의 테스트를 깨뜨리고, 불안정한
의존성이 머지를 막고, 새로 추가되거나 고친 테스트가 실행되지 않습니다. 20분의 지연이 수만 건의
반영되지 않은 업데이트가 될 수 있습니다.

## v0가 확장을 멈춘 이유
단일 프로세스가 테스트별 이력을 들고 있었고 단일 writer가 필요해 수평 샤딩이 불가능했습니다. 패치가
버텨 준 기간은 매번 짧아졌습니다: 더 큰 머신(약 70일), 패키지별 샤딩(29일), 매일 재시작(하루 미만).

## 재설계
```
CI 실행 ──▶ 무상태 리스너 워커 ──append──▶ 저널 (인메모리 스토어)
                                              │ 몇 초마다
                                              ▼
                                  컨슈머가 테스트별 이력으로 롤업
                                              │
PR 생성 ──▶ 셀렉터 ──────── 이력 조회 ◀────────┘
```
- 어떤 워커든 어떤 결과든 처리하고 메모리에 아무것도 들고 있지 않으므로 수평 확장됩니다.
- 싱글턴보다 운영 비용은 더 들지만 확장과 메모리 프로파일링이 훨씬 쉽습니다.
- 엔지니어 한 명이 3주 만에 완료. 저널 크기와 워커 수 튜닝은 Claude가 대부분 자율적으로 했습니다.
- 전환과 튜닝 이후, 처리 대기 이벤트의 시간당 최대치가 평탄하게 유지됐습니다.

## 계획 원칙
1. 직접 만들든 사든, 두 분기 안에 25배 부하가 온다고 가정한다.
2. 예산이 허락하면 v0를 체감 규모의 10~20배로 설계한다.
3. 처음부터 상태를 프로세스 밖에 둔다.
4. 측정하고 카나리 변경을 할 수 없다면 핵심 서비스를 단일 인스턴스로 돌리지 않는다.
5. 서비스를 Claude의 눈과 귀가 되도록 계측하고, 들어온 CI 잡 수와 나간 잡 수가 같은지 확인한다.
6. 장기 실행 에이전트 세션으로 지연을 모니터링하고(Anthropic은 5만 잡에서 알림) 사건 사이의 맥락을
   유지한다.
