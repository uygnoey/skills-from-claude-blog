# 사용 사례에 맞는 Claude 모델 고르기

"이 워크로드에는 어떤 모델을 써야 하나요?"는 Anthropic이 가장 자주 듣는 질문 중 하나다. 모델 클래스와
버전이 늘어나면서 답도 그만큼 미묘해졌다. 이 가이드는 모델 패밀리, 선택할 때 던져야 할 질문, 그리고 그
답이 오래가게 만드는 실무 습관을 정리한다.

## 기본 권장안: 똑똑한 쪽에서 시작하라

미묘함은 잠시 접어두자. 기본 권장안은 **일반 출시된 모델 중 가장 지능적인 모델에서 시작해, 효과 수준
(effort level)으로 성능과 비용을 조절하는 것**이다.

이유는 두 가지다.

- **작업당 비용은 더 지능적인 모델이 오히려 더 낮은 경우가 많다.** 토큰당 단가가 더 비싸더라도, 특히
  낮은 effort에서 그렇다. 더 유능한 모델은 대부분의 작업을 더 적은 턴과 더 짧은 사고 시간으로 맞힌다.
- **작은 모델에서 시작하면 진단이 어려워진다.** 실패했을 때 그것이 모델의 실패인지 셋업의 실패인지
  구분하기 힘들어진다.

지연 시간이나 비용에 더 민감한 사용 사례가 생기면, 그때 하위 클래스를 시험해 보며 맞는 지점을 찾으면
된다.

반대 방향을 택하는 조직도 있다. 가장 비용 효율적인 모델에서 시작해 품질 기준을 넘을 때까지 클래스를
올려가는 방식이다. Anthropic의 모델 선택 문서는 두 방향 모두를 다룬다. 어느 쪽이든 괜찮다. 결과를
비교 가능하게 만드는 것은 일관성이다.

## Claude 모델 패밀리

Fable, Opus, Sonnet, Haiku로 이루어진 이 패밀리는 클래스마다 지능·속도·비용의 균형점이 다르다. 모델
클래스는 **도메인별로 특화되어 있지 않다.** 금융용 모델이나 과학용 모델 같은 것은 없다. 모든 Claude
모델은 코딩, 에이전트 작업, 지식 노동 전반에서 뛰어나도록 훈련된다. 클래스 간 차이는 **얼마나 어려운
문제를 안정적으로 감당할 수 있는가, 그리고 그 역량이 가격과 속도로 얼마를 요구하는가**이다.

### Mythos / Fable

전 도메인에 걸쳐 프런티어 역량을 갖춘 가장 유능한 클래스다. 특히 코딩, 장시간 실행되는 에이전트 작업,
그리고 지금까지 AI가 안정적으로 해내지 못하던 문제에 강하다.

이 클래스는 동일한 기반 모델을 두 가지 패키지로 제공한다. **Claude Mythos**는 이중 용도(dual-use)
사이버보안 및 생물학 업무를 다루는 신뢰된 조직을 위한 것이고, **Claude Fable**은 일반 대중이 안전하게
쓸 수 있도록 추가 안전장치를 함께 묶은 패키지다. 두 패키지 모두 안전한 사용을 위해 제한된 데이터 보존
(limited data retention)을 요구한다.

### Opus

추론 집약적인 엔터프라이즈 작업을 위한 강력한 클래스다. Opus 모델은 지식 노동 벤치마크인 **GDPval-AA**,
에이전트 코딩 벤치마크인 **Terminal-Bench 2.1** 등 주요 산업 벤치마크에서 꾸준히 선두권에 오른다.

정말 어려운 판단은 Opus와 Fable 사이다. 둘 다 코딩, 장시간 에이전트, 지식 노동에 뛰어나기 때문이다.
실제 상황에서는 Fable 같은 더 큰 모델이 벤치마크 점수가 비슷하더라도 지혜, 창의성, 글쓰기 능력에서 더
낫게 나오는 경향이 있다. 경험칙은 이렇다. **평가나 내부 테스트에서 Opus가 일부 작업에 고전한다면 답은
Fable이다. Opus가 이미 품질 기준을 넘는다면, 속도와 가격 프로필 덕분에 Opus가 더 나은 선택일 수 있다.**

### Sonnet

일상적인 작업을 위한 다재다능한 클래스다. 가장 넓은 범위의 범용 사용 사례에서 성능·비용·속도의 균형을
제공하며, 여기에는 **멀티 에이전트 오케스트레이션의 대량 서브에이전트**도 포함된다.

### Haiku

가장 저렴하고 가장 빠른 클래스로, **지연 시간과 비용이 중요한 고빈도 워크로드**를 위해 설계되었다.

## 클래스를 고르는 네 가지 질문

1. **이 작업은 얼마나 어려운가?** 시간이 많이 걸리거나, 여러 단계를 거치거나, 지금까지 풀리지 않았던
   문제라면 더 유능한 클래스가 적절하다.
2. **지연 시간 요구는 어떤가?** 모델이 고빈도 고객 대면 워크로드에 들어간다면, Sonnet이 최선인 경우가
   많다.
3. **접근 제약은 무엇인가?** Mythos는 Project Glasswing에 등록된 조직만 사용할 수 있고, 모든 조직이
   모든 클래스를 모든 역할에 열어두는 것도 아니다.
4. **단위 경제성은 어떤가?** 프로덕션 물량이 많다면 하위 클래스가 더 적절할 수 있다. 특히 평가 결과가
   해당 작업을 충분히 잘 수행한다고 보여줄 때 그렇다. 모델마다 토큰 단가가 다르고, 역량과 effort에 따라
   작업당 가격도 달라진다.

### effort는 두 번째 다이얼

effort 수준 역시 품질·속도·비용의 균형을 바꾼다. 상위 클래스를 높은 effort로 돌리면 최고 성능이 나오고,
**상위 클래스를 낮은 effort로 돌리면 때때로 하위 클래스보다 더 효율적**일 수 있다. "똑똑하게 시작해서
effort를 낮추는" 쪽이 "작게 시작하는" 쪽을 자주 이기는 이유가 이것이다. 하나의 축이 아니라 클래스 ×
effort 격자를 탐색하라.

## 강점 결합: 어드바이저 전략

작업 전체를 한 클래스로 돌릴 필요는 없다. **어드바이저 전략(advisor strategy)** 은 더 빠르고 저렴한
워커 모델이 더 지능적인 모델을 호출해 자신의 계획을 점검받고 결과물을 평가받게 한다.

실행 모델이 **필요할 때만 코칭받기** 때문에, 비용 대비 개선 폭이 크다. **SWE-bench Pro에서 Fable 5를
어드바이저로 둔 Sonnet 5는, 작업 전체를 Fable 5로 돌렸을 때 대비 63%의 가격으로 Fable 5 점수의 10%
이내**에 들어왔다.

## 평가와 벤치마크의 역할

역량이 충분한지 확인하는 흔한 방법은 두 가지다.

**표준 벤치마크**는 정답이 알려진 사전 정의 과제 모음이며, 흔히 특정 도메인에 맞춰져 있다. 클래스 간·
제공자 간 역량을 가늠하는 방향성 지표로 유용하다. 문제는 **포화(saturation)** 다. Opus나 Fable 같은
강력한 모델은 문제를 거의 다 풀어버리기 때문에, 정작 당신이 저울질하는 모델들 사이를 벤치마크가
변별하지 못하게 된다.

그럴 때의 답이 **커스텀 평가**다. 실제 워크로드에 모델을 투입하거나, 자체 평가로 시험하라. 보통은
프로덕션에서 뽑아낸 문제들을 큐레이션한 집합이며, **현재 도구가 부족한 어려운 작업들을 포함하고**,
성공 기준은 팀이 직접 정의한다. 프런티어 모델의 역량과 창의성이 나머지와, 그리고 서로 간에 갈라지기
시작하는 지점이 바로 여기다.

## 현명한 선택이란

모델 선택에 만능 해법은 없고, 그래서 여러 클래스가 존재한다. 결국 모델을 잘 고르는 최선의 방법은 각
클래스의 기본을 이해하고 자신의 사용 사례를 깊이 이해하는 것이다. 그것은 곧 **강한 평가 체계를 구축하고,
유지하고, 배포하는 일**이며, 워크로드·물량·모델 라인업이 바뀔 때마다 선택을 다시 점검하는 일이다.
