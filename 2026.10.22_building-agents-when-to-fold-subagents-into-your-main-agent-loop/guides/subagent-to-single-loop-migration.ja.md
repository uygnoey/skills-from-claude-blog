# サブエージェントから単一エージェントループへ

サブエージェントをメインエージェントループに統合する Anthropic の指針を、方法論としてまとめました。

## 1. なぜ重要か
大きな組織では、各チームが自前のエージェントを作り、その上に中央のオーケストレーターを置きがちです。
その結果、エージェント間のコンテキスト喪失、サブエージェントの乱立、矛盾したルールが混ざった
「フランケンプロンプト」、誰も管理しない局所的な評価、追加のレイテンシが生じます。スキルとツールを
段階的に開示する単一ループは、共有コンテキストを保ち、肥大化を防ぎ、より有能なモデルを活かせます。

## 2. それでもサブエージェントが適する場合
- 単一ループでコンテキスト肥大による性能低下が測定できるとき。
- 新しく使い捨てのコンテキストウィンドウで並列に進めるべき作業。
- 1つのシステムプロンプトではツール選択が難しい、または指示が矛盾するとき。
マルチエージェントを選ぶなら、最も単純なパターンから始め、問題の種類ではなくコンテキストで分割します。

## 3. 目標アーキテクチャ
モデルとコンテキストウィンドウは1つ。ターン・コスト予算と書き込みゲートを持つオープンなツールループ。
並列のツール呼び出しバッチの生の結果を同じモデルに返す。計画はコンテキスト内で書き、結果に応じて
修正する。手順はスキルに、強い制約と会話途中の参照はツールに置き、コードは安価でほぼ常に必要な
読み込みとツール内部の機械的処理にだけ使います。

## 4. 移行ステージ
1. **タスク完了評価** — 中央チームの共有エンドツーエンドセットとスキルごとのセット。まずゴールデン例
   10件。ルーブリック採点、ルーティング精度、その後はスキル・ツール選択の正しさ。
2. **ドメインエージェントの統合** — 互いの出力を連鎖させる、データを共有する、一緒に呼ばれるものから。
   利用の多いものを先に。
3. **残すサブエージェントはツールとして呼ぶ** — 共有レスポンススキーマ、メインエージェントが検証し会話を
   保持。サブエージェントがユーザーと直接話す必要があるときだけ完全なハンドオフ。
4. **1つずつ畳み込む** — プロンプトはスキルへ、API 呼び出しは MCP ツールへ。反転したタスクを比較し、
   各タスクを複数回実行。畳み込んだ版のスコアが悪い場合のみサブエージェントとして残します。

## 5. オーナーシップモデル
| 資産 | 担当 | 目安 |
|---|---|---|
| システムプロンプト、エンドツーエンド評価 | 小さな中央チーム | 新しいスキル・ツール・評価をすべて審査 |
| スキル | チームの DRI | 明確に区別され、よく作られ、評価と一緒に出す |
| MCP ツール | ドメインチーム | ユーザー意図単位でまとめる、約30〜50定義以下、遅延読み込みのツール検索 |
| ナレッジベース | ドメインチーム | 検索ツールの背後、またはスキルの参照ファイルとして |

## 6. ツール
`/claude-api build-eval`、`/claude-api prompt-audit`、`/claude-api hillclimb`、
`/claude-api cost-optimize`、`/skill-creator`、`/skill-doctor`、モックシステムでのデモ付き移行キット。

## 7. 原則
測定し、一度に1つだけ変え、効果が続くものだけを残す。
