# 本番で auto モードを運用する: Nuro・Gusto・Garner Health のパターン

出典: https://claude.com/blog/auto-mode-in-production（2026 年 8 月 7 日）

## auto モードが解くトレードオフ

auto モードは現在 Claude Code の既定設定です。エージェントが実行しようとするすべてのコマンドについて承認を求める代わりに、分類器（classifier）が各操作を評価し、有害になりうるものをブロックします。

この設計は、エージェンティックコーディングでよくあるトレードオフを解消します。

- **すべてのコマンドをレビューする**と人が判断のループに残ります。しかしセッションが数時間に及んだり並列に増えたりすると、その監督自体がボトルネックになります。
- **パーミッション確認を丸ごと省く**方が速いですが、それはプロンプトインジェクション、スコープの逸脱、ときおり起きる本番リソースの削除が通ってしまう経路でもあります。

社内評価では、分類器は開発者が手作業でパーミッションプロンプトをクリックしていく場合よりも多くの危険な操作を検出し、その性能は第三者によるレッドチーミングでも維持されました。セッションが止まる回数が減るため、Claude Code 全体の利用で見ると、Claude は従来の既定に比べて中断と中断の間に **9 倍長く**動作します。

## Nuro — より長く走る自律エージェント

汎用のレベル 4 自動運転技術を開発するフィジカル AI 企業 Nuro は、2025 年後半に Claude Code を導入し、3 月には社内で最も使われるエージェンティックコーディングツールになりました。

**auto モード以前の課題。** スタッフソフトウェアエンジニアの Kai Zhou は、社内向けの代替を試作していました。保留中の操作ごとに小さなモデルへ送り、定型的なものは 9 割方自動承認し、機微なものは Slack に流して人がレビューするフックです。これは現実の緊張に応えるものでした。エンジニアは承認プロンプトの子守りを嫌がる一方、会社のセキュリティと法務の観点では、パーミッションを丸ごと省くのは容認できないほど危険でした。auto モードが登場したとき、Kai はこのサイドプロジェクトを棚上げしました。

**現在の運用。**

- 自分が書くものすべてに auto モードを使っています。「コーディング作業の 100 パーセントで auto モードを使っています。たいていは auto モードのセッションを 3〜4 個並行で開いておいて、必要なときだけ見に行きます」。
- **例外は他チームに関わる作業です。** Claude Code が自分の代わりにプルリクエストをレビューするときは、インタラクティブモードに戻して 1 件ずつ確認してから出します。
- **無制限に走らせているわけでもありません。** Nuro はスキルを積極的に活用し、エンジニアは再帰削除のような最も危険なコマンドを設定で明示的に deny しています。分類器はそのガードレールの内側で判断します。

**より大きな効用は、エンジニアが退勤した後も走り続ける作業です。** Kai のチームは、自動運転スタックの評価指標を少しずつ改善していく長時間のリサーチエージェントを auto モードで動かしています。エージェントが自力で反復できる、明確で測定可能なシグナルを持つタスクです。夜のあいだにエージェントは、評価スイートが挙げた偽陰性を調べ、提案をまとめ、実験を回し、結果をもとに反復を続けられます。このやり方は明確な評価方法があるどのタスクにも広がります。指標そのものが、改善しているのか後退しているのかをエージェントに教えるからです。Nuro の別チームは、特定バイナリのメモリ使用量削減にこれを使っています。

> 「先日、午後 10 時にエージェントを起動したら朝の 5 時まで走り続けて、朝には PR を 3 本くれました。なかなかすごいと思います。こういうワークロードは auto モードでしか実現できません」。

## Gusto — より速く、より安全に PR を出す

中小企業向けテクノロジー企業の Gusto では、auto モードへの移行は先回りのセキュリティ強化として始まりました。

**AI Dev Tools チームの Martin Emde。** 彼はパーミッション疲れがチームの速度を落とすのを見てきました。auto モードは統制やセキュリティを犠牲にせず同じ速度をもたらし、エンジニアリング全体に定着してからはパーミッション全般の負担が目に見えて減りました。

- 12 月以降 2,425 件の Claude Code セッションを、auto モードを主軸に実行。
- 以前はフォルダアクセスの承認で止まっていたリポジトリ横断の作業が、中断なく走るように。
- GitHub・Slack・Jira から日次ノートをまとめるような無人ジョブが自走。
- 2026 年 5 月中旬以降、**セッションのトランスクリプトの約 10% に auto モードの拒否が含まれて**いました。正当なタスクを妨げずに分類器が実際に働いている証拠です。

> 「auto モードは、速度と統制のあいだにより安全なバランスをもたらしました。繰り返されるプロンプトをなくし、安全性を損なわずに生産性を上げられました。auto モードが適切なタイミングでブロックしているのが見えるので、速く動く自信が持てます」。

**AIT Cloud Engineering チームの Chad Kunsman。** 彼は逆方向から同じ結論に至りました。エンドポイント調査、ログ監査、コネクタ管理、複数の MCP サーバー越しのドキュメント取り込みといった彼の作業は、夜通しのマラソンではなく 20 分程度の短い作業です。彼が求めたのは長時間実行ではなく、悪いプロンプトやプロンプトインジェクションがすり抜けるリスクなしに bypass permissions の「手を離せる」テンポを得ることでした。

> 「プロンプトインジェクションへの防御があり、やっていることが依頼した内容と実際に合っているかを確認してくれることを考えると、bypass permissions より良い選択で、パーミッションプロンプトよりはるかに速いです」。

分類器が介入する稀な場面でも的確だと彼は言います。「止められたときは納得できたし、理由も説明してくれました。もともと頼んだことから逸れていて、確認してきたんです。まったく的外れではありませんでした」。

**彼が auto モードから抜ける場面。** セッションが本番インフラ（Terraform、AWS、稼働中 API への直接 POST）に踏み込むときは accept edits に切り替え、ツール呼び出しを 1 件ずつ自分で確認します。「節約できる時間と、エージェントが現実的に間違えうる範囲と、それがどれだけ壊滅的かを天秤にかける必要があります。結局、何が起きても責任を負うのは自分です」。

この判断はより広い多層防御の中で行われます。Gusto は MCP トラフィックを、ツールガードとプロンプト検査を備えたガバナンス付きプロキシ層に通し、auto モードが判断する前にエージェントが厳しく絞られた権限で動くようにしています。

## Garner Health — ソフトウェア開発ライフサイクル（SDLC）の加速

ヘルスケアテクノロジー企業の Garner Health は、2 月に全職種 550 名の従業員全員に Claude Code を展開しました。Salesforce、Zendesk、Snowflake を含む中核システムに接続されており、従業員は業務のうち最も反復的な部分の自動化に週 2 時間ほどを充てるよう促されています。

**auto モード以前は、** この規模には相応のオーバーヘッドが伴いました。プラットフォームエンジニアリングマネージャーの Evan Magnussen は、パーミッション管理を、承認コマンドの一覧を手作業で整備し、パイプでつないだコマンドが弾かれるのを眺める退屈な繰り返しだと表現します。

**現在は、** Evan と同僚の多くがコードベースの調査から MCP 経由の外部連携管理まで、すべてのセッションで auto モードを使っています。

> 「エンジニアリング組織全体のための標準化されたソフトウェア開発ライフサイクルを構築しました。これは auto モードがあって初めて可能になったものです。従業員はそれを肩の荷が下りたものとして受け止めています。もう何時間もエージェントを見張らなくてよいのです」。

**このライフサイクルは、標準化されたスキルのプラグインとして動きます。** エージェントがタスクを引き受け、アクセスできる文脈を探索し、コンテキストファイルをリポジトリにコミットし、Evan が「antagonistic research」と呼ぶ、自らの前提を突き崩す検証を行い、それから実装に移ります。人を待つのは、自力で見つけられない文脈が必要になったときだけです。リサーチ比重の高い工程は auto モード以前には不可能だった、と Evan は述べています。

**チューニング。** そのままの状態で、分類器にはほとんど調整が要りませんでした。Evan の唯一の調整は Nuro の Kai と同じで、Slack メッセージやメール送信のように他人とコミュニケーションする操作を auto モードが承認しないよう設定しています。「他人とやり取りするときに、Claude が自分の代わりに勝手に行動するのは個人的に好みません」。中核的な知的財産を扱うチーム——auto モード以前はパーミッションを省くことに最も懐疑的だったチーム——は、自分たちの仕事に合わせて分類器に注入されるプロンプトを、より許容的に、あるいはより厳しく調整することを学びました。

**他企業への助言。** 踏み込みつつ、エンジニアに力を与えながら安全な展開を担保できる適切な統制を築くこと。「全員それぞれ好きにワークフローを作れと言って、テレメトリがなかったら、それはとても危険でしょう。テレメトリがあり、比較的標準的なワークフローを整えてきたからこそ、はるかに大きな確信を持てます」。

## まねる価値のあるパターン

1. **まず設定でハードなガードレールを引く。** 分類器はあなたが定めた枠の内側で判断するのであって、枠の代わりにはなりません。
2. **分類器が見る前にツールを絞る。** ツールガードとプロンプト検査を備えたガバナンス付き MCP プロキシがあれば、エージェントはすでに厳しく絞られた権限で動きます。
3. **既定で 1 つだけ狭い調整を入れる。** 他人とコミュニケーションする操作は自動承認しない。3 チーム中 2 チームが独立に同じ結論に至りました。
4. **どのセッションが auto モードから抜けるかを事前に決める。** 自分の境界を越える作業と、本番インフラです。
5. **タスクの形を無人実行に合わせる。** 明確で測定可能な評価シグナルこそが、エージェントに夜通しの反復を許します。成果物はマージ済みの変更ではなく、レビュー用の完成した PR です。
6. **ワークフローを標準化してから計測する。** テレメトリは後回しの作業ではなく、全社展開を正当化する前提条件です。
7. **拒否率を見る。** セッションの約 10% に拒否が含まれるという水準は、正当な作業を妨げずに分類器が実際に働いていることの表れと読めます。
