# AI 기반 코드 현대화 준비하기

Anthropic 포워드 디플로이드 엔지니어들이 Notes from the Field 시리즈에서 정리한 방법론입니다. 규제 산업
기업의 핵심 시스템을 대규모로 현대화할 때의 준비 과정을 다룹니다.

## 왜 준비가 진짜 일인가

예전에는 몇 년짜리 전사 프로젝트였던 현대화가 이제 몇 달, 길어야 몇 주면 끝날 수 있습니다. 하지만 핵심
시스템을 신뢰할 수 있게 만드는 변경 관리·리뷰·승인 절차는 "사람이 변경을 쓰고 사람이 diff를 리뷰한다"는
전제로 만들어졌습니다. 에이전트가 변경을 쓰기 시작하면 병목은 변경을 만드는 쪽에서, 그 변경을 둘러싸고
조직을 움직이는 쪽으로 옮겨갑니다.

## 6단계

| # | 단계 | 산출물 |
|---|---|---|
| 1 | 목표 정의 | 현대화된 코드가 가져야 할 기술 스택과 동작 |
| 2 | 인증서(certificate) 작성 | 변경이 올바르다고 인정받기 위한 조건 |
| 3 | 승격 정책(promotion policy) 수립 | 인증된 변경이 생산 속도에 맞춰 프로덕션에 들어가는 경로 |
| 4 | 사전 준비물 갖추기 | 환경, CI/CD, 리뷰 인력, 승인 |
| 5 | 에이전트 워크플로 구축·개선 | 병렬 서브에이전트 작업 흐름으로 구성된 Claude Code 동적 워크플로 |
| 6 | 현대화 실행 | 작은 파티션에서 끝까지 검증한 뒤 확장 |

### 1. 목표 정의
**업리프트**(같은 스택의 버전 업), **트랜스폼**(동작은 그대로 두고 스택을 바꾸는 재작성), **리이매진**(동작을
바꾸며 새로 구축, 서면 동작 명세 필요) 중 하나를 고릅니다. 프로덕션 담당자는 보통 트랜스폼을, 코드베이스와
오래 함께한 엔지니어와 비즈니스 이해관계자는 리이매진을 원합니다. 초기에 합의하지 않으면 개별 변경이
"맞는지"를 둘러싼 논쟁으로 다시 돌아옵니다. 코드베이스를 매핑하고(code modernization 플러그인의 `assess`,
`map`, `extract-rules` 명령이 도움이 됩니다) 인터뷰와 내부 문서로 빈틈을 채운 뒤, 비즈니스 근거를 세웁니다.
대개 핵심은 비용 절감이 아니라 **리스크 감소**입니다.

### 2. 인증서 작성
모든 변경이 통과해야 하는 조건의 집합이며, 각 조건은 사람 없이 자동으로 확인할 수 있어야 합니다. 기존·Claude
작성 테스트, 커버리지 기준, 성능 범위, 새 컨텍스트에서 실행하는 Claude의 적대적 리뷰, 컴퓨터 사용 기반 UI
점검, 입출력 동등성, 상태·와이어 포맷 왕복, 스테이징 관찰 기간, 정적 분석·보안 스캔, 깨끗한 빌드 등에서
고릅니다. 업리프트는 기존 테스트에, 트랜스폼은 트래픽 리플레이·차등 테스트·프로덕션 병행 배포에,
리이매진은 명세에 기댑니다. 리뷰어와 함께 작성하고, 증거가 부족하면 Claude로 만들어 냅니다.

### 3. 승격 정책 수립
영향 범위(blast radius)와 에이전트 신뢰도로 리뷰 깊이를 등급화하고, 핵심 경로는 전수 리뷰를 유지합니다.
반복되는 플래그는 원인에서 고칩니다. 리뷰 출력 형식을 리뷰어와 함께 설계하고, 희소한 SME 시간은 가장 위험한
등급에 씁니다. 속도와 리뷰 깊이 사이의 위치를 정하고, 리더십이 정책을 사전에 공표해 프로덕션으로 새어 나간
버그의 책임을 공유하게 합니다.

### 4. 사전 준비물
원격 호스트와 테스트 용량, 텔레메트리·프로덕션 병행·리플레이 데이터, 근거 있는 의존성 맵, CI/CD 호환성 점검,
코드 프리즈·커뮤니케이션 계획, 의존 팀의 리뷰 시간, 승인된 모델 접근 경로, 최소 권한, 비밀값·개인정보
마스킹, PR과 에이전트 트랜스크립트의 추적성, 라이선스·취약점 점검. 다른 팀에도 자체 백로그가 있으니 일찍
대화를 시작하세요.

### 5. 워크플로 구축·개선
code modernization 플러그인에서 시작합니다. 목표·인증서·정책·코드베이스·문서·도구를 파일 시스템이나 MCP에
두어 프로젝트 지식 베이스로 삼습니다. 작은 범위에서 SME 리뷰와 함께 시범 적용합니다. 문제가 생기면 각
변경이 아니라 워크플로를 고칩니다.

### 6. 실행
작은 파티션 하나를 승격 정책까지 거쳐 끝까지 반영하고, 비용이 쌀 때 반복 개선한 뒤 확장합니다. 업리프트는
제자리(in place) 현대화도 가능합니다. 잎(leaf)에서 안쪽으로 파티션을 나누고, 한 번에 하나씩 프리즈해
현대화하며, CI/CD 게이트로 새 커밋이 완료된 파티션을 되돌리지 못하게 합니다.

## 비용
비용 요인은 읽어야 할 코드 대비 바꿔야 할 코드의 양, 인증서의 복잡도(규제 환경에서는 보통 검증이 더 큰
비중), 테스트 작성·수리, 동시 머지와의 조정 작업입니다. 파일럿에서 토큰을 측정해 비용 하한을 추정하고,
파일럿에서 보이지 않은 부분은 미지수로 둡니다. 비싼 검증은 싼 게이트 뒤에 두고, 기계적인 작업에는 Sonnet
같은 모델을, 어려운 변환과 적대적 리뷰에는 더 강한 모델을 쓰며, 모델 승격 시 재시도율을 살핍니다.

## 현대화 그 이후
코드 외에도 재사용 가능한 워크플로, 서면 인증서, 승인된 승격 정책, 변경별 증거 기록이 남습니다. 다음 업그레이드를
위해 플레이북으로 정리해 두세요.
