# AI 主導のコードモダナイゼーションに備える

Anthropic のフォワードデプロイドエンジニアが Notes from the Field シリーズでまとめた方法論です。規制業種の
企業における基幹システムの大規模モダナイゼーションの準備を扱います。

## なぜ準備こそが本当の仕事なのか

かつて数年がかりの全社プロジェクトだったモダナイゼーションは、いまや数か月、場合によっては数週間で終わります。
しかし基幹システムの信頼性を支える変更管理・レビュー・承認のプロセスは、「人が変更を書き、人が diff を
レビューする」という前提で作られています。エージェントが変更を書くようになると、ボトルネックは変更を作る
ことから、変更を中心に組織を動かすことへと移ります。

## 6 つのステップ

| # | ステップ | 成果物 |
|---|---|---|
| 1 | ターゲットを定義する | モダナイズ後のコードが持つべき技術スタックと振る舞い |
| 2 | 証明書(certificate)を作る | 変更が正しいとみなされるための条件 |
| 3 | 昇格ポリシーを決める | 認証済みの変更が生成ペースに合わせて本番へ届く経路 |
| 4 | 前提条件を整える | 環境、CI/CD、レビュー体制、承認 |
| 5 | エージェントワークフローを構築・改善する | 並列サブエージェントで構成した Claude Code の動的ワークフロー |
| 6 | モダナイゼーションを実行する | 小さなパーティションでエンドツーエンドに検証し、その後スケール |

### 1. ターゲットを定義する
**アップリフト**(同一スタックのバージョンアップ)、**トランスフォーム**(振る舞いを固定したままスタックを
書き換える)、**リイマジン**(振る舞いを変えて新規構築。書面の振る舞い仕様が必要)から選びます。本番運用側は
トランスフォームを、長くコードに関わってきたエンジニアやビジネス側はリイマジンを望みがちです。早期に合意
しないと、個々の変更が「正しいか」をめぐる議論として再燃します。コードベースをマッピングし(code modernization
プラグインの `assess`、`map`、`extract-rules` コマンドが役立ちます)、インタビューや社内文書で補い、
ビジネス上の根拠を固めます。多くの場合、決め手はコスト削減ではなく**リスク低減**です。

### 2. 証明書を作る
すべての変更が満たすべき条件の集合で、各条件は人手を介さず確認できる必要があります。既存テストと Claude が
書いたテスト、カバレッジ基準、性能の上限、新しいコンテキストで実行する Claude の敵対的レビュー、computer use
による UI 確認、入出力の同一性、状態やワイヤーフォーマットのラウンドトリップ、ステージングでの観察期間、
静的解析とセキュリティスキャン、クリーンビルドなどから選びます。アップリフトは既存テスト、トランスフォームは
トラフィックのリプレイ・差分テスト・本番並行デプロイ、リイマジンは仕様に依拠します。レビュー担当者と一緒に
作り、証拠が足りなければ Claude に作らせます。

### 3. 昇格ポリシーを決める
影響範囲(blast radius)とエージェントの確信度でレビューの深さを階層化し、クリティカルパスは全面的な人による
レビューを維持します。繰り返し出るフラグは原因から直します。レビュー出力の形式はレビュー担当者と設計し、
貴重な SME の時間は最もリスクの高い階層に充てます。速度とレビューの深さのどこに立つかを決め、経営層が事前に
ポリシーを示すことで、本番に漏れたバグの責任を共有できるようにします。

### 4. 前提条件
リモートホストとテスト容量、テレメトリ・本番並行環境・リプレイ用データ、根拠のある依存関係マップ、CI/CD の
互換性チェック、コードフリーズとコミュニケーション計画、依存チームのレビュー時間、承認済みのモデルアクセス経路、
最小権限、シークレットと個人情報のマスキング、PR とエージェントのトランスクリプトのトレーサビリティ、
ライセンスと脆弱性のチェック。他チームにも独自のバックログがあるため、早めに相談を始めます。

### 5. ワークフローを構築・改善する
code modernization プラグインから始めます。ターゲット・証明書・ポリシー・コードベース・ドキュメント・
ツールをファイルシステムまたは MCP に置き、プロジェクトのナレッジベースにします。小さな範囲で SME レビュー付きで
試行します。問題が出たら個々の変更ではなくワークフローを直します。

### 6. 実行する
小さなパーティションひとつを昇格ポリシーまで通してエンドツーエンドで反映し、安いうちに改善を繰り返してから
スケールします。アップリフトはインプレースでも可能です。葉から内側へパーティションを分け、一度にひとつずつ
フリーズしてモダナイズし、CI/CD のゲートで新しいコミットが完了済みパーティションを戻せないようにします。

## コスト
主な要因は、読む量と変更する量の比、証明書の複雑さ(規制環境では検証が大きな割合を占めがち)、テストの作成と
修復、並行するマージとの調整作業です。パイロットでトークンを計測してコストの下限を見積もり、パイロットで
見えなかった部分は未知数として扱います。高価な検証は安価なゲートの後ろに置き、機械的な作業には Sonnet などの
モデルを、難しい変換や敵対的レビューにはより強力なモデルを使い、モデルを切り替える際はリトライ率に注意します。

## モダナイゼーションのその先
コードに加え、再利用可能なワークフロー、書面の証明書、承認済みの昇格ポリシー、変更ごとの証跡が残ります。
次のアップグレードのためにプレイブックとして整理しておきましょう。
