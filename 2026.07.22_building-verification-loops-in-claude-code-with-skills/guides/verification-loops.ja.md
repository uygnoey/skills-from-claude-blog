# Claude Code でスキルによる検証ループを構築する

## エージェンティックループ

ほとんどのエージェンティックなコーディングセッションは一つのループをたどります。変更を依頼すると、
Claude が**コンテキストを集め**、**行動し**、**結果を検証し**、必要ならコンテキスト収集に戻ります。

検証とは、エージェントが応答する前に自分の作業を確かめることです。Claude はすでにその一部を自力で
行っています。コードベースの決定論的なシグナル — 型チェッカー、リンター、テスト、ランタイムエラー —
を観察しているからです。Claude が推論できない部分が、機能を手作業で確認するために*あなたが*踏む手順に
なります。

その手作業の手順は検証ループに変えられます。Claude Code における検証ループとは、Claude が作業を確認し、
修正を試みる反復プロセスです。つまりエージェントがテストやリンター、独自チェックを実行し、失敗したものを
直してから先に進む繰り返しのサイクルです。スキルとしてパッケージ化すれば、人が思い出すことに頼らず、
すべてのセッションが同じチェックを自動で適用します。

## まずは組み込みのループから

- **`/verify`** — アプリケーションをビルドし、実行し、変更を観察します。
- **ツールチェーン** — Claude はリンターなど、あなたが用意したツールのエラーコードや警告を捕捉して
  対応しようとします。正確なビルド・テストコマンドを `CLAUDE.md` に列挙しておけば、Claude が推論する
  必要はありません。
- **Code Review（リサーチプレビュー）** — 有効化したリポジトリの PR に自動レビューを走らせるマネージド
  なマルチエージェントサービスです。指摘を自分で直してプッシュするか、その指摘に `@claude` とコメントして
  ループを閉じられます（GitHub Actions の設定が前提です）。
- **GitHub Actions** — 検証スキルで Claude を呼び出すジョブを定義すれば、ローカルで実行しているのと同じ
  チェックがすべてのプッシュや PR で走ります。
- **スペック検証** — リポジトリ内の markdown スペックに対して各変更を検証し、違反の修正を試みるスキルです。
- **Claude Managed Agents のルーブリック（ベータ）** — 独立した採点エージェントを使って、結果をルーブリック
  に照らして検証します。失敗すると自動的に手戻りのループに戻ります。

## 自分で書く

既存プロジェクトでは、繰り返しが合図です。Claude が機能を実装するたびに同じ小さな修正をしているなら、
毎回自分がやっていることをすべて書き出しましょう。

新規プロジェクトなら、ベストプラクティス版を平易な言葉で、**初日の新しいチームメイトに手渡すつもりで**
書きます。

チェックそのものを言語化しづらいときは、まず Claude にベストプラクティスを尋ね、そこから編集してください。
あなたの版はいくつかの具体的な点で異なるはずで、その差分こそ書き留めたい内容です。

> **ヒント。** ここに入れるチェックが定性的である必要はありません。「バックフィル手順のないカラム削除
> マイグレーションは却下する」は、汎用リンターでは捕まえられないがプロジェクト固有のものなら捕まえられる
> 決定論的なルールです。手作業で強制し続けているものは何であれ、ループとして書き留める価値があります。

### スキルにする

最短経路は `skill-creator` プラグインをインストールし、Claude にインタビューさせることです。

```
/skill-creator Create a skill for verifying frontend changes end-to-end. Interview me about my workflow.
```

プロジェクト内の `.claude/skills/` に markdown ファイルを置いて手書きすることもできます。最も単純な検証
スキルは、数行の frontmatter と本文だけです。

```markdown
# .claude/skills/verify-log-hygiene/SKILL.md
---
name: verify-log-hygiene
description: Check that error logs include the request ID and never
  include the request body. Use when the diff touches error handling
  or logging.
allowed-tools: [Read, Edit, Grep]
---
Read the error-handling paths in the current diff.

For each log call on an error path, confirm it includes the request ID
and does not pass the request body, headers, or any user-supplied payload.

Report each violation with file:line, then fix it: add the request ID
where it's missing and strip the payload from the log call.
```

## チェックを実行場所に合わせる

### 単独実行（standalone）

成果物ができたあと、あなたが意図的に呼び出します。単独スキルが力を発揮するのは、毎回は当てはまらない
横断的なチェックです。コミット前のセキュリティスキャン、PR 前のアクセシビリティ監査、リポジトリ全体の
ライセンスヘッダー検証など。多くのワークフローから使いたいが、コード変更のたびに発火してほしくはない
チェックです。

代償は、呼び出すたびに思い出して 1 ターン使う必要があることです。毎回の変更のあとに実行しているなら、
単独実行を卒業した合図で、その手順は恒久的な居場所を得るに値します。

### 埋め込み（embedded）

成果物を作るスキルの一部として自動的に発火します。チェックは特定のワークフロー一つに属し、そのワークフロー
が頼まれなくても実行するようになります。最も単純な形は、生成側スキルの本文に 1 行を追記することです。

```
After creating the component file, run eslint on it and
address any errors before reporting completion.
```

埋め込みが効いているかは、新しいタスクでそのスキルを呼び出し、追記した手順が出力の一部として実行される
ことを確認すれば分かります。実行されないなら、スキルの description か前段の指示が、追記したチェックを
引き込めていません。

埋め込みが使えるのは編集できるスキルだけです。自分で書いたもの、あるいは `SKILL.md` が自分の管理下にある
プロジェクトレベルのインストールに限られます。組み込みスキルやプラグイン管理のスキル（更新時に上書き
される類い）はこのパターンの対象外なので、代わりにチェーンしてください。複数のワークフローにまたがる
チェックには埋め込みではなく単独実行が向いています。

### チェーン（chained）

一つのスキルが終わりに別のスキルを呼び、検証された受け渡しがいくつも連なってエンドツーエンドで走ります。
Anthropic の Claude Code チームのメンバーは日常的にこのパターンを使っています。`/code-review` がバグを
探し、`/simplify` が差分を整理し、`/verify` スキルがエンドツーエンドの挙動を確認し、変更が UI に触れて
いれば独自の `/design` スキルが `DESIGN.md` のガイドラインに照らして確認します。

チェーンは、変更できないスキルに検証を付け足す方法でもあります。元のスキルを呼び出し、続けて検証スキルを
呼び出すラッパースキルを作ります。

```markdown
# .claude/skills/safe-refactor/SKILL.md
Run /simplify on the current diff first.
When /simplify finishes, invoke /verify-no-public-api-changes.
```

習慣（「`/simplify` のあとは必ず `/verify` を回す」）だったものが、契約（「`/simplify` は終了時に必ず
`/verify` を回す」）になります。チェーンが開発サイクル全体を自走させ、あなたは何かがエスカレーションされて
きたときだけ関われば済みます。

各ステップが十分に独立していて、ときには一つだけ実行したいのなら、チェーンは見送ってください。チェーンは
柔軟性を自動化と引き換えにします。チェーン化した検証ループはトークン消費を増やしうるので、広く展開する前に
テストするのが賢明です。

### すべての PR で

自分の変更に対してチェーンが安定したら、同じ手順をすべての PR で走らせられます。同僚の変更も、チェーンを
呼び出すのを覚えていたかどうかに関係なく、あなたの変更と同じゲートを通ります。インフラは、すでに書いた
チェーンと同じものが一歩先に進んだだけです。同じスキル、同じルーブリック、同じ基準を、作成者の心がけに
依存せずに適用します。

ここで検証は個人のインフラであることをやめ、チームのインフラになります。ただしチェーンがまだ流動的な
うちは PR 全体のゲート化を控えてください。調整のたびにチーム全体に見えるイベントになります。

## プロセス

1. 今週いちばん多く行った手作業のフォローアップを選ぶ。
2. まず組み込みの `/verify` スキルを試し、自分のプロセスに役立つか確かめる。
3. 手順を平易な言葉で、初日の新しいチームメイトに手渡すつもりで書く。
4. `skill-creator` に渡すか、自分で markdown ファイルを `.claude/skills/` に置く。
5. 新しいタスクで呼び出し、チェックが出力の一部として実行されることを確認し、必要なら改善する。
6. スキルのチェーンを試し、エンドツーエンドの検証フローを作る。

Claude が従える形で書き留められるものが増えるほど、Claude の応答は初回から望むものに近づきます。もう
手直ししなくてよくなった修正は、どんなスキルにも書き留められない仕事へ注意を解放してくれます。
