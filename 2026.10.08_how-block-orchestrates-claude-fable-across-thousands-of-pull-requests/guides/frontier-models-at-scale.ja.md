# フロンティアモデルを大規模に効率よく安全に運用する

エンジニアリング組織全体にフロンティアモデルを与えつつ、コストとリスクの制御を失わないための、Block の
AI Capabilities チームの教訓です。

## 1. アクセスと効率
- 技術職なら誰でも最も高性能なモデルにフルアクセスできるようにし、チームが常に可能性の最前線で働けるように
  します。
- 効率を既定にします:タスクに合ったモデルを提案するツール(Block の自動セレクター)を作り、大小のモデルを
  組み合わせるマルチエージェントシステムを使います。
- フロンティアモデルは大きな問題(移行の設計、大規模オーケストレーション)に取っておき、コード変更の細部は
  小さなモデルに任せます。

## 2. スライダーではなくグリッドでベンチマーク
- xhigh effort のモデルは、同じモデルの medium とは別のモデルのように振る舞うことがあります。
- すべてのユースケースについて、すべてのモデルをすべての effort レベルでベンチマークします。
- 「この種のタスクにはこのモデルを high で既定使用」のような明確な推奨を示し、ツールで自動化し、専門家には
  その先を探索させます。

## 3. 多数のエージェントのためのツール
- 単一会話中心のインターフェースでは、数十のエージェントが同時に動く状況に追いつけません。Block は、複数の
  人と多数のエージェントがチャンネルやスレッドを共有するオープンソースのワークスペース Buzz を使っています。

## 4. 多層のセーフガード
| 層 | Block のやり方 |
|---|---|
| 人間による保証 | main へのマージ、本番デプロイ、フィーチャーフラグ変更は人間が担当。エージェントの変更はセキュリティチェックを経て、2人がデプロイを承認 |
| デフォルトで安全 | リモートワークステーション、拒否リストではなくネットワークの許可リスト |
| モデルループの外 | 作業インターフェースに組み込んだ安価なチェック — 正規表現、増えつつある小さな分類器 |
| 意図的に許可 | PR 作成、コードレビュー、ログや分析 DB の照会 |
| モデルのセーフガード | モデル自身の拒否傾向と Anthropic の安全分類器。Claude が二重承認の「回避」を拒否するかを Block がベンチマーク |

## 5. 保守のペースを保つ
PR が増えるほど技術的負債も速く溜まります。コードベースを毎日または毎週巡回し、整理・統合すべき箇所を探す
エージェントを動かします。

## 6. 知識を組織のものにする
人はローカルのスキルや文脈を蓄えます(例:フロントエンド開発者でない人でも Web フロントエンドで作業できる
スキル)。学んだことを文書化して共有システムに入れ、すべてのエージェント実行が最良の文脈を持てるようにします。
