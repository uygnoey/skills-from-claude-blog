# 에이전틱 코딩으로 스타트업 운영하기

빠르게 성장하는 12개 이상의 스타트업이 Claude Code를 중심으로 제품 개발
라이프사이클을 어떻게 조직했는지에 대한 서베이, 그리고 무엇부터 따라 해야 하는지.

원문이 던지는 근본적인 질문은 이것이다. 어떤 조직이 제품 개발 라이프사이클을
처음부터 Claude Code로 설계한다면 어떤 모습일까?

## 보고된 성과

| 회사 | 보고 수치 |
| --- | --- |
| ClickHouse | 출시 기능 30% 증가 |
| Omni | 엔지니어링 생산성 2~3배 |
| Clay | 버그 트리아지 100% 자동화 |
| Artemis Security | 주당 6,000개 이상의 PR |

## 다섯 가지 규칙으로 본 운영 모델

1. **모두가 출시한다(Everyone ships).** 동작하는 첫 버전을 만드는 장벽이
   충분히 낮아져서, 문제를 이해하는 사람이 직접 만든다.
2. **지루한 일을 자동화한다(Automate the tedium).** 라이프사이클의 기계적인
   80%는 에이전트가 맡는다.
3. **믿되, 검증한다(Trust, but verify).** 검증할 수 없는 것은 자동화할 수 없다.
4. **다시 만들 것을 전제로 만든다(Build for rebuilding).** 모델 역량이 발밑에서
   계속 변하므로, 스캐폴딩은 소모품으로 취급한다.
5. **프로토타입 → 도그푸딩 → 프로덕션화.** AI로 만드는 경험이 AI 제품을 만드는
   법을 가르쳐 준다.

규칙 2와 3은 한 쌍이다. 3 없이 2만 도입하면, 겉보기에는 맞아 보이지만 실제로는
아키텍처에서 벗어난 그럴듯한 코드가 쌓인다.

## 조직적으로 달라지는 것

**핸드오프 사슬이 무너진다.** Heidi는 기존 경로를 "고장 난 전화기 문제"라고
부른다. 아이디어 → PM → 디자이너 → 엔지니어로 넘어가는 사이 본질이 사라지고 몇
주가 흘렀다. 이제는 문제를 이해하는 사람이 직접 PR을 올리고, 전문성이 필요한
부분에서만 디자이너와 엔지니어를 부른다.

**분업은 그대로 남는다.** 마케터는 여전히 마케팅을, 개발자는 여전히 개발을
한다. 모두에게 열리는 것은 0→1 단계다.

**기여에는 길이 필요하다.** 공식적인 자리가 없으면 비개발자의 기여는 개인의
의지에 맡겨진 채로 끝난다. Clay는 분기 리뷰를 통해 프로토타입이 정식 로드맵에
진입하도록 한다. Omni는 Claude가 생성한 프로토타입 전용 Slack 채널을 운영하고,
"모두가 출시한다"의 짝으로 "모두가 고객과 대화한다"를 실천하며 엔지니어를
의도적으로 고객 앞에 세워 피드백 루프를 단축한다.

**표준은 공유 파일로 옮겨 간다.** 팀의 기준과 컨텍스트를 담은 재사용 가능한
지시문 파일인 스킬(Skill)은, 개발이 민주화되어도 제품이 하나의 응집된 결과물로
남게 해 준다. 디렉터리나 사내 플러그인 마켓플레이스를 통해 공유하라. Emergent의
태도는 그대로 가져올 만하다. 에이전트가 빠르게 검증하고 스스로 궤도를 수정할 수
있다면, 컨텍스트 파일이 조금 낡아 있어도 괜찮다.

## 기술적으로 달라지는 것

**Claude를 사실의 원천에 연결하라.** 보지 못하는 것은 이해할 수 없다. 팀이
도구와 Claude 사이에서 복사·붙여넣기를 하고 있다면 MCP를 쓰고, 성숙한 커맨드라인
도구(`gh`, `kubectl`, `bq`, `psql`)가 이미 있고 엔지니어와 동일한 사실의 원천을
보게 하고 싶다면 CLI를 쓰라. 후자가 토큰 효율이 좋은 경우가 많다.

**컨텍스트를 계층화하라.** 바뀌면 안 되는 것은 루트 `CLAUDE.md`에. 저장소의 특정
영역에서 항상 적용되는 관례는 하위 디렉터리 `CLAUDE.md`에. 필요할 때 불러 쓰는
절차적 워크플로는 스킬에.

**반복 업무에 에이전트를 붙여라.** ClickHouse의 플레이키 테스트 에이전트와
테스트 커버리지 에이전트는 해당 저장소의 2위·3위 기여자다. Clay는 최초 분류부터
수정 제안까지 버그 트리아지를 자동화했다. Translucent의 리뷰어는 변경 사항 전체에
팬아웃해 여러 각도에서 검토한 뒤 결과를 종합한다.

**SDLC 바깥도 자동화하라.** 가장 흔하게 자동화된 비개발 프로세스는 셀프서비스
데이터 분석이었다. 사내 분석 에이전트, 사용 데이터와 함께 보는 피드백 분류,
서브에이전트를 활용한 수천 건의 법률 문서 요약, 클레임 데이터의 이상 징후 탐지,
병원 재무 데이터의 상시 모니터링 등이다.

**결정론이 필요한 부분에는 게이트를 걸어라.** 훅(Hook)은 라이프사이클의 고정된
지점에서 실행되며, 모델이 무엇을 판단하든 상관없이 항상 동작한다. 린트를 통과하지
못한 쓰기를 차단하거나, 커밋 전에 테스트 통과를 요구하거나, 무언가 샌드박스를
떠나기 전에 시크릿을 제거하는 식이다. 다이내믹 워크플로는 분리된 컨텍스트 윈도와
명확한 목표를 갖고 결정론적으로 순서를 제어한다. 긴 작업에서 Claude가 성급하게
완료를 선언하거나 목표에서 이탈할 위험이 있을 때는 `/goal`이 도움이 된다.

**재구축을 싸게 만들라.** git worktree를 쓰면 하나의 오브젝트 스토어를 공유하는
별도 체크아웃에서 v1 옆에 v2를 나란히 돌릴 수 있다. 각각에 대해 평가를 돌리고,
새 쪽이 이길 때만 머지하라. 규모 있는 재작성 전에는 플랜 모드를 켜서, 코드가
쓰이기 전에 아키텍처 이탈을 잡아라.

## 검증은 선행 투자다

Artemis Security는 배포 속도의 공을 에이전트가 아니라 테스트 인프라, 코드베이스
구조, 지식 시스템에 돌린다. 그것들을 제대로 구조화하면 모든 기여가 복리로
쌓인다는 것이다.

구체적인 실천:

- **불변식을 문서로 남긴다.** 완전한 자율성이 아키텍처 이탈로 이어진 뒤,
  Zingage가 작성한 "이 팀이 사고하는 방식" 567줄.
- **자기 완결적 종료 조건을 가진 루프.** 플레이키 테스트 에이전트는 테스트를
  다시 돌려 스스로 수정 결과를 검증한다.
- **원칙을 고치는 전문가 리뷰.** Cainex는 감사자의 교정 내용을 버전 관리되는
  에이전트 지시문에 반영하고, 골든 세트와 무작위 샘플로 백테스트한다. "예시가
  아니라 원칙을 고쳐라." 첫 버전은 과적합되어 패치만 쌓였고, 그래서 한 번의
  변경에 들어갈 수 있는 개별 사례 수에 상한을 두었다.
- **여러 개의 평가 세트를 유지한다.** 직관에 의존하던 팀이 무너지는 지점은,
  사용자가 "바뀐 뒤로 더 나빠진 것 같다"고 말하는데 추측 말고는 확인할 방법이
  없을 때다.

## 도입 순서

1. 루트 `CLAUDE.md`의 불변식을 쓰고, Claude를 실제 도구에 연결한다. 이것 없이는
   이후 모든 것이 표류한다.
2. 가장 리스크가 큰 유스케이스에 대해 골든 세트와 평가 스위트 하나를 만든다.
3. 반복적이면서 스스로 검증 가능한 작업 하나에 에이전트를 붙인다. 플레이키
   테스트가 표준적인 첫 선택이다.
4. 비개발자에게 0→1 경로를 열고, 프로토타입이 우선순위를 얻는 자리를 만든다.
5. 매번 동일하게 실행되어야 하는 단계에 훅을 건다.
6. 첫 재구축에 worktree와 플랜 모드를 쓰고, 끝까지 마무리한다. 재구축은 옛 경로가
   사라져야 끝난 것이다.
