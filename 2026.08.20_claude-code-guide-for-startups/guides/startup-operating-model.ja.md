# エージェンティックコーディングでスタートアップを動かす

急成長中の十数社のスタートアップが、Claude Code を中心にプロダクト開発ライフ
サイクルをどう組み立てているかのサーベイと、まず何を真似すべきか。

原文が投げかける根本的な問いはこうだ。ある組織がプロダクト開発ライフサイクルを
ゼロから Claude Code で設計したら、どんな姿になるのか。

## 報告された成果

| 企業 | 報告値 |
| --- | --- |
| ClickHouse | 出荷機能が30%増加 |
| Omni | エンジニアリング生産性が2〜3倍 |
| Clay | バグトリアージを100%自動化 |
| Artemis Security | 週6,000件以上のPR |

## 五つのルールで見る運用モデル

1. **全員が出荷する。** 動く最初のバージョンを作る障壁が十分に下がり、問題を
   理解している本人が作れるようになる。
2. **退屈な作業を自動化する。** ライフサイクルの機械的な80%はエージェントが
   担う。
3. **信頼せよ、ただし検証せよ。** 検証できないものは自動化できない。
4. **作り直す前提で作る。** モデルの能力は足元で動き続けるので、足場は使い捨てと
   して扱う。
5. **プロトタイプ→ドッグフーディング→プロダクト化。** AI で作る経験こそが、AI
   プロダクトの作り方を教えてくれる。

ルール2と3は対になっている。3 抜きで 2 だけを導入すると、一見正しく見えるのに
実際にはアーキテクチャから逸脱した、もっともらしいコードが積み上がる。

## 組織面で変わること

**ハンドオフの連鎖が崩れる。** Heidi はかつての経路を「伝言ゲーム問題」と呼ぶ。
アイデア → PM → デザイナー → エンジニアと渡るうちに本質が失われ、数週間が過ぎて
いた。いまは問題を理解している本人が PR を出し、専門性が必要な部分だけデザイナー
やエンジニアを巻き込む。

**分業は残る。** マーケターは引き続きマーケティングを、開発者は引き続き開発を
行う。全員に開かれるのは 0→1 のステップだ。

**貢献には道筋が要る。** 場がなければ、非エンジニアの貢献は個人の意欲任せで
終わる。Clay は四半期レビューでプロトタイプを正式なロードマップに乗せる。Omni は
Claude が生成したプロトタイプ専用の Slack チャンネルを運用し、「全員が出荷する」
の対句として「全員が顧客と話す」を実践して、エンジニアを意図的に顧客の前に立たせ
フィードバックループを短くしている。

**標準は共有ファイルへ移る。** チームの基準とコンテキストを記述した再利用可能な
指示ファイルであるスキルは、開発が民主化されてもプロダクトを一体感のあるものに
保つ。ディレクトリや社内プラグインマーケットプレイスで共有するとよい。Emergent の
姿勢はそのまま採用する価値がある。エージェントが素早く検証して軌道修正できる限り、
コンテキストファイルが多少古くても構わない。

## 技術面で変わること

**Claude を真実の源につなぐ。** 見えないものは理解できない。チームがツールと
Claude の間でコピー＆ペーストをしているならMCPを使い、成熟したコマンドラインツール
（`gh`、`kubectl`、`bq`、`psql`）がすでにあり、エンジニアと同じ真実の源に対して
作業させたいならCLIを使う。後者はトークン効率が良いことが多い。

**コンテキストを階層化する。** 変えてはいけないものはルートの `CLAUDE.md` へ。
リポジトリの特定領域で毎回適用される規約はサブディレクトリの `CLAUDE.md` へ。
必要なときに呼び出す手続き的ワークフローはスキルへ。

**繰り返し作業にエージェントを充てる。** ClickHouse の不安定テスト用エージェントと
テストカバレッジ用エージェントは、同リポジトリの第2位・第3位のコントリビューター
だ。Clay は初回仕分けから修正提案までバグトリアージを自動化した。Translucent の
レビュアーは変更全体にファンアウトし、複数の観点からの検討結果を統合する。

**SDLC の外も自動化する。** 最も多く自動化されていた非エンジニアリング業務は
セルフサービスのデータ分析だった。社内分析エージェント、利用データと突き合わせた
フィードバック分類、サブエージェントによる数千件の法務文書の要約、請求データの
異常検知、病院財務データの継続的なモニタリングなどである。

**決定論が要る部分にはゲートを置く。** フックはライフサイクルの固定された地点で
発火し、モデルの判断に関係なく必ず実行される。リントに通らない書き込みをブロック
する、コミット前にテスト成功を必須にする、何かがサンドボックスを出る前にシークレット
を除去する、といった具合だ。ダイナミックワークフローは、分離されたコンテキスト
ウィンドウと絞り込まれた目標のもとで決定論的な順序制御を与える。長いタスクで Claude
が早々に完了と判断したり目標から逸れたりしそうなときは `/goal` が役に立つ。

**作り直しを安くする。** git worktree を使えば、単一のオブジェクトストアを共有
しつつ、独立したブランチの別チェックアウトで v1 の隣に v2 を走らせられる。両方に
評価を回し、新しい方が勝ったときだけマージする。規模の大きい書き直しの前にプラン
モードを使えば、コードが書かれる前に逸脱を捕まえられる。

## 検証こそが前提となる投資

Artemis Security は、デプロイ速度の要因をエージェントそのものではなく、テスト
インフラ、コードベースの構成、ナレッジシステムに帰している。それらを正しく構造化
すれば、あらゆる貢献が複利で積み上がるという主張だ。

具体的な実践:

- **不変条件を書き出す。** 完全な自律性がアーキテクチャの逸脱を生んだ後に
  Zingage が書いた、「このチームの考え方」567行。
- **自己完結した停止条件を持つループ。** 不安定テスト用エージェントは、テストを
  再実行して自らの修正を検証する。
- **原則を改善する専門家レビュー。** Cainex は監査担当者の訂正をバージョン管理
  されたエージェント指示に反映し、ゴールデンセットとランダムサンプルでバックテスト
  する。「例ではなく原則を直す」。最初のバージョンは過学習してパッチが積み上がった
  ため、一度の変更に入れられる個別事例の数に上限を設けた。
- **複数の評価セットを維持する。** 直感で回してきたチームの限界は、ユーザーから
  「変更後に悪くなった気がする」と報告されても、当て推量以外に検証手段がないと
  気づいた瞬間に訪れる。

## 導入の順序

1. ルート `CLAUDE.md` の不変条件を書き、Claude を実際のツールにつなぐ。これが
   なければ、以降のすべてが漂流する。
2. 最もリスクの高いユースケースについて、ゴールデンセットと評価スイートを一つ
   立ち上げる。
3. 繰り返し発生し、かつ自己検証可能なタスク一つにエージェントを充てる。不安定
   テストが標準的な最初の選択だ。
4. 非エンジニアに 0→1 の道を開き、プロトタイプが優先順位を得られる場を作る。
5. 毎回同一に実行される必要がある工程にフックを掛ける。
6. 最初の作り直しに worktree とプランモードを使い、最後までやり切る。作り直しは
   古い経路が消えて初めて完了する。
